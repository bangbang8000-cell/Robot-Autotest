## 2. 结论先行

### 2.1 一句话结论

**做，但要做「领域层」而不是「第二个 RF 仪表盘」。** 三件套负责「跑」和「看」，新平台负责「谁、凭什么、按什么顺序、在哪台设备上跑，以及证据是否完整可交付」——这部分三件套一行代码都没覆盖。

### 2.2 六条硬结论

1. **并行执行必须自建。** RoboScope 0.16.1 的执行队列 `task_executor.py` 固定 `max_workers=1`，`RunCreate` 里的 `parallel` 字段只落库不生效。以它为执行内核，「用例并行」需求**无法交付**。
2. **RoboScope 的执行 API 不要接。** 证据见 §4.2。它的价值在报告渲染、AI 修复建议、计划调度、Webhook，这部分可直接复用，省 6-8 周前端工作量。
3. **robotdashboard 只做报告聚合。** 包名 `robotframework-dashboard` 2.5.0，定位是 "Output processor and dashboard generator"，无执行、无用户、无租户概念。把它当「看板」用是对的，当「平台」用会返工。
4. **参考工程可直接复用数据模型，不可复用执行器。** 8001 平台 59 张表、26,459 行 Python 里有成熟用例/证据/租约模型；但执行器是单 worker 串行 + Windows 文件锁，且**入口无鉴权**，照抄即埋雷。
5. **真正的技术难点不是 Spring Boot，是「设备资源互斥 + 双存储一致性」。** 并行跑 4 条用例，若都打到同一台 DUT 的同一个口，测出来的数全是废的；MariaDB 存元数据、`output.xml` 存产物，两边对不齐就出不了对外报告。
6. **149 撑不住 4 并发。** 3350 MB 内存要同时装 Spring Boot、MariaDB、RoboScope、robotdashboard 和 4 个 robot 进程，实测前测算余量仅约 25%（§5.3）。要么扩到 8 GB，要么并发压到 2。

### 2.3 可行性评分

| 维度 | 权重 | 得分 | 评分依据 |
|---|---:|---:|---|
| 技术可行性 | 25% | 85 | 全部组件开源、许可证宽松（Apache-2.0 / MIT）；集成面清晰（REST + 进程 + 文件） |
| 工程可行性 | 20% | 70 | 3 人 6 个月可交付；参考工程可省 4-6 周；但并行与双存储有返工风险 |
| 基础设施就绪度 | 20% | 60 | 149 单机、内存吃紧；群晖 Git 通道未开；148 不可达；出网可用是加分项 |
| 生态与许可证 | 15% | 90 | 四款依赖均为宽松许可，可商用、可闭源二次开发，仅需保留声明 |
| 投入产出 | 20% | 75 | 复用约 45% 管理面能力，自研集中在领域层，ROI 合理 |
| **加权合计** | **100%** | **76** | 0.25×85 + 0.20×70 + 0.20×60 + 0.15×90 + 0.20×75 = **75.75** |

**评级口径**：≥80 可直接立项；70-79 有条件立项；60-69 需重做方案；<60 不建议。本次落 **有条件立项**。

### 4.2 关键证据：RoboScope 不能作为并行执行内核

`POST /api/v1/runs` 的请求体 `RunCreate` 确实带 `parallel: boolean`，字段齐整（`required: repository_id, target_path`，另有 `parallel / max_retries / timeout_seconds / variables / advanced_config / tags_include / tags_exclude`），看接口会误以为支持并行。

但后端实际执行路径是 `task_executor.py`，线程池 `max_workers=1`，`runs.parallel` 只写库不参与调度。**这是接口存在、能力不存在**的典型陷阱。项目既有记录已就此明确标注为"假并行"。

**推论（重要）**：若立项方案写成"调用 RoboScope 的 runs 接口实现并行"，验收时 100% 失败，且返工点在别人的代码里，我们只能 fork。这是本报告最需要决策层看清的一条。

### 5.3 并行模型与容量测算（核心）

**并行粒度**：用例级。`pabot --processes N`，按 suite 分片；同一用例的多次重试**不得**并行。

**资源互斥**：必须引入租约表，粒度是"设备 + 端口/链路"，不是"设备"。

```sql
-- 借鉴 8001 的 execution_leases(resource, job_id)，扩为带时效与排他
CREATE TABLE resource_lease (
  resource_key VARCHAR(128) NOT NULL,   -- 例: DUT-01/mlx5_0
  job_id       CHAR(36)    NOT NULL,
  acquired_at  DATETIME(3) NOT NULL,
  expires_at   DATETIME(3) NOT NULL,
  PRIMARY KEY (resource_key)
);
```

调度器先取租约再派发，取不到则排队；进程崩溃由 `expires_at` 兜底回收。**没有这张表，并行就是把数据跑脏。**

**149 内存测算（3350 MB 为基线）**：

| 组件 | 常驻内存（估） | 备注 |
|---|---:|---|
| Spring Boot（含连接池） | 700 MB | `-Xmx512m` 起步 |
| MariaDB | 500 MB | 小实例 |
| RoboScope | 350 MB | 实测占位，含 uvicorn |
| robotdashboard | 120 MB | 仅生成/查询时 |
| pabot 主进程 + 4 × robot | 800 MB | 每 worker 约 200 MB |
| OS + 缓存 | 400 MB | |
| **合计** | **≈ 2,870 MB** | 对 3,350 MB 余量 **≈14%** |

**结论**：3,350 MB 上跑 4 并发会持续触发 swap，执行时间抖动、看门狗误杀概率上升。**建议**：内存扩到 **8 GB**（4 并发安全余量约 60%），或降级为 **2 并发 + RoboScope 不常驻**。这是本报告唯一一条硬性资源建议。

> 注：内存数值为规划测算，非压测实测（149 的 SSH 口令本次未通过，无法取 `free -m`）。M2 阶段必须用真实压测数据回填本表。

### 5.4 双存储模型（最易返工处）

| 数据 | 存储 | 理由 |
|---|---|---|
| 项目/用例/集合/租约/审计 | MariaDB | 事务、并发、多租户隔离 |
| `output.xml` / `report.html` / `log.html` / 原始命令流 | 文件系统（按 `RUN_ID` 分目录）+ 索引入 MariaDB | RF 生态只认文件；强行入库会破坏 `robot` 复跑 |
| 看板聚合指标 | robotdashboard 的 SQLite（只读旁路） | 不参与事务，坏了可重建 |

**一致性规则**：`RUN_ID` 是唯一关联键（延续本项目既有 metadata 定规）。流程固定为「产物先落盘 → sha256 → 回填 MariaDB → 才允许出报告」，任何一步失败则任务置 `unknown`，**不自动重跑**（沿用 8001 已验证的处置原则）。

### 5.5 报告与证据链

必须继承本项目 2026-10-31 定规：每条 `output.xml` 带 **10 项 metadata**（`CASE_ID` `RUN_ID` `QA_PROJECT` `DUT` `LINK` `SW_BUILD` 必填，`BASELINE` `OPERATOR` `STARTED_AT` `CASE_KIND` 推荐）。这是"能否对外出报告"的门禁，不是可选项。

在 Spring Boot 侧做成**入库前校验**：解析 `output.xml` → 校验 10 项 → 缺项则拒绝入库并回报错误码。让不合规的报告根本进不了库，比事后补文档可靠。

| GitHub API | `https://api.github.com/` → **200**，0.46 s | 出网正常，可用 GitHub 托管仓库与 Actions |

| `execution_leases` | ★★ 资源租约雏形 | 扩为带 `expires_at`（§5.3） |
| `devices`（含 `ssh_profile`、`identify_evidence`） | ★★ 设备与身份核验 | 凭据改密文列 + 权限收敛 |
| `audit_log` | ★★ 审计 | 加 `actor_id`、`project_id` |
| `execution_plans`（冻结命令 + sha256） | ★★ 命令冻结与可追溯 | 直接沿用思路 |

### 6.2 明确不采纳

| 项 | 原因 |
|---|---|
| `worker.py` 执行器 | 单 worker 串行 + Windows 文件锁，与 N7 冲突 |
| 免密入口 | 与 N4（多用户）直接冲突 |
| `data/` 全部 1.5 GB | 混有包库、阶段产物；需按类筛，不可整体迁移 |
| 26,459 行代码整体移植 | Python→Java 无收益；只搬**模型**与**规则**，不搬实现 |

## 11. 决策建议

1. **批准按方案 B 立项**：自研编排层 + RF/pabot 执行内核 + RoboScope 报告旁路。
2. **先决后建**：§9.1 的 6 项前置条件全部关闭再开 M1；其中「149 扩容」与「群晖 Git 打通」最容易被跳过，也最容易在 M2/M4 反咬。
3. **砍需求换确定性的地方**：报告渲染不要自研，直接用 RoboScope；用例导入不要重做，直接兼容 8001 的 461 条存量。
4. **把并行当作独立课题**：M2 单独设 2 周 spike，先证 4 并发加速比 ≥2.5x，再谈上层功能。做不到就如实降级为 2 并发，别把不确定性拖到 M5。
5. **不建议现在动 147/148**：147 已进入退役，148 不可达；在 M0 之前引入第三台机器只会增加变量。
