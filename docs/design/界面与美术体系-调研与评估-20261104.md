## 0. 结论先说

**判定：骨架已经立住，皮肤基本没有。综合 2.1 / 5。**

拆开看是这个样子——这不是「做得差」，是**一张桌子四条腿装好了但桌面没铺**：

| 层 | 现状 | 分 |
|---|---|---:|
| 色彩与主题 | 两层 token、亮暗双套、跟随系统、首帧防闪、对比度可机检 —— 这套做法是对的 | 3.5 |
| 字体与排版 | 49 处字号写了 10 种值，无字阶、无等宽字体 | 1.5 |
| 间距与栅格 | 32 处 padding 写了 22 种值，无栅格 | 1.5 |
| 图标与品牌 | **零图标、零 logo、零 favicon**；主题切换按钮是个 emoji 字符 | 0.5 |
| 组件与交互状态 | 按钮只有 1.5 套；**全应用 hover / focus / transition 均为 0 处** | 2.0 |
| 数据可视化 | 手写 SVG 折线与 div 柱状，能用但缺轴、缺 tooltip、缺空图 | 2.0 |
| 双语能力 | 体系 4 分（409 键对齐、零硬编码、守门通过），版式 1 分（未验证） | 2.5 |
| 治理工具 | 3 个守门脚本都在跑，但都有盲区 | 3.0 |

**三条最要紧的话：**

1. **有一个正在生效的缺陷，必须在下一次验收前修掉**：`var(--muted)` 被引用 **21 处**，但 `theme.css` 从未定义它（只定义了 `--text-muted`）。结果是**全应用所有辅助文字退化为正文色**——表头、字段标签、统计卡片的说明行、图表坐标轴标签、时间戳，全部失去弱化层级。两个守门脚本都放它过去了（详见 §3 D1）。这是「美术体系」最该先修的一条，因为它不显眼、但影响每一个页面。
2. **零 hover / 零 focus / 零过渡，这不是审美问题，是可访问性问题**。全仓 `:hover` 0 处、`:focus` 0 处、`transition` 0 处。键盘用户按 Tab 走一遍，屏幕上没有任何东西告诉光标在哪（WCAG 2.4.7 不达标）；鼠标用户也得不到「这个能点」的确认。这条比「好不好看」严重得多。
3. **不要重做，要补三层**。现有 token 结构、i18n 基线、守门脚手架都是对的，重来一遍是浪费。缺的是：字阶 / 间距 / 圆角三套尺度、一套图标、一套组件、一套图表+表格规范、一个品牌标识、一个能看的规范页。这些是**叠加**，不是重写。

**一句话判据**：做完之后，界面在 1440 和大屏 1920 上都站得住；英文界面不撑破任何一列；每个可点元素都有悬停与焦点反馈；菜单和状态一眼能认出图形；换个人来做新页面，不需要问「字号用几号、间距用多少」。

## 2. 现状盘点

### 2.1 色彩与主题 —— 3.5 / 5，做对的部分要说清楚

做对的（这些不要动）：

- **两层 token 结构**：`primitives`（`--gray-900`/`--blue-400`…）只描述「这是什么颜色」，`semantic`（`--bg`/`--panel`/`--accent`…）描述「用在哪」，组件只允许用第二层。这是成熟做法，很多团队做了三年还是散着写 hex。
- **亮色不是把暗色反过来**：`--accent` 在亮色下压深到 `#1567c9`，注释里写了「`#3fa7ff` 在白底只有 2.2:1」。说明当初是按对比度算的，不是调色调出来的。
- **三态 + 跟随系统 + 首帧防闪**：`useTheme.ts` 挂 `matchMedia` 监听（不是启动读一次），`index.html` 内联脚本在挂载前写 `data-theme`。
- **可机检**：`check_contrast.py` 实跑 40 组组合全过（暗 20 组 / 亮 20 组），正文 15.27:1、辅助 6.37:1。

不足的：

- **语义层不完整**：缺 `--surface-hover`（悬停底色）、`--surface-selected`（选中底色）、`--focus-ring`（焦点环）、`--accent-hover`/`--accent-active`。这直接导致 §3 的 D2——**没有变量可用，就只能不做交互态**。这两件事是一个因果链，不是两个独立缺陷。
- **状态色只有三档**（ok/fail/warn），缺 `info` 与 `neutral` 的正式语义（`--neutral-soft` 只有一个值，用于趋势图「取消」段，用途太窄）。
- **图表色只到 4 个系列**，没有「同色系深浅」用于双轴或对比。

### 2.2 字体与排版 —— 1.5 / 5

```
font-family: 'Segoe UI', 'Microsoft YaHei', system-ui, sans-serif;   ← 全应用唯一一处
```

| 事实 | 数字 | 问题 |
|---|---|---|
| 字号取值 | **49 处 / 10 种**（10, 11, 12, 13, 14, 15, 18, 20, 22, 28） | 11/12/13/14/15 五档挤在 5px 内，肉眼分不出，等于没有层级 |
| 使用频次 | 13px × 18、12px × 16（占 70%） | **实践已经收敛到 12/13，只是没写成 token** |
| 字重 | 400 / 500 / 600 / 700 四档 | 工具型界面用不到 700，两处 700 是随手写的 |
| 行高 | 大量未显式声明，走浏览器默认 | 中文默认行高偏紧，长段落与日志块会显得挤 |
| 等宽字体 | **无** | 见下，这是测试平台的硬伤 |

**等宽字体缺失是这份评估里最被低估的一条。** 这个产品的表格里全是 `run_20261104_1041`、`10.202.54.106`、`2026/11/04 10:41:00`、`eth0-eth0`。用比例字体渲染，字符宽度不一致，一列 ID 扫下来眼睛要重新对位；对比两个近似 IP（`.106` 和 `.107`）时更难。测试/运维类工具几乎都用等宽字体处理这类字段，不是审美偏好，是扫读效率。

另外 `'Segoe UI'` 打头意味着 Windows 上英文走 Segoe、中文回落雅黑，两种字面骨架不同，混排时基线和中宫高度会有轻微跳变。这不是致命问题，但既然要建体系，字体栈应该显式规定「拉丁优先字体 + 中文优先字体」的顺序，而不是靠回落碰运气。

### 2.3 间距、圆角、栅格 —— 1.5 / 5

| 属性 | 现状 | 目标 |
|---|---|---|
| `padding` | **32 处 / 22 种取值**（2,3,4,6,8×2,10,…24,40） | 8 档 4 基数 |
| `gap` | 39 处 / 9 种（1,3,4,6,8,10,12,14,16） | 同上，收敛到 1/3/4/6/8 → 4/8/12 |
| `border-radius` | 27 处 / 6 种（2,4,6,8,10,999） | 4 档（4/6/8/999） |
| 栅格 | 无；主内容区只有 `body` 的 20px padding | 12 栏或 8pt 栅格 + 内容最大宽度 |

**22 种 padding 说明的是同一个问题**：每做一个新卡片，作者是「看着调」而不是「查表取」。这不能怪谁——**没有表可查**。这不是靠 review 能解决的，只能靠 token + 守门。

主内容区无 `max-width`：`app-main` 是 `flex:1`，表格 `width:100%`。1440 上尚可，1920/2560 上表格会拉得很宽、行内视线跨度过大（当前内容不满是因为列少，一旦列多就铺满，`ReportDetailView` 有 10 列以上）。需要一条「内容区最大宽度 + 超宽表格独立横向滚动」的规则。

### 2.4 图标与品牌 —— 0.5 / 5

这是缺口最大的一块，而且不是「少画几个图标」的量级：

| 项 | 现状 |
|---|---|
| SVG 图标资产 | **0 个**（全仓无 `.svg`，无 `public/` 目录） |
| 菜单图标 | 无。6 个一级菜单 + 1 个子入口全是纯文字 |
| 状态图标 | 无。状态全靠文字徽标（「已完成」「失败」） |
| 操作图标 | 无。删除/编辑/刷新全是文字链接，靠 `→` 字符当箭头（10 处） |
| 主题图标 | `◐` `☀` `☾` 三个 Unicode 字符 |
| favicon | 无（浏览器标签显示默认空白页图标） |
| Logo | 无。品牌位是一行 15px 文字「AIDC自动化测试」 |
| 空态插图 | 无。空态是虚线框 + 一句话 |

`◐` 这条值得单独说：它在某些字体里是「半圆」、在某些环境里渲染成方块或双色圆，而且**它同时表示「跟随系统」这个状态**——用户看到的是一个不认识的符号。三态主题应当用「显示器 / 太阳 / 月亮」三个图标 + 明确的选中态。

**没有图标的后果不是「丑」，是「慢」**：熟练用户靠图形定位菜单（肌肉记忆 + 形状识别），纯文字列表每次都要读字。这个产品的一级菜单只有 7 个，影响有限，但报告页里的树形结构、状态标记、操作按钮就没有这个余量了。

### 2.5 组件与交互状态 —— 2.0 / 5

按钮现状（实测 class 使用统计）：

| 类 | 使用次数 | 状态 |
|---|---:|---|
| `btn btn-ghost` | 35 | 有定义 |
| `btn`（主按钮） | 21 | 有定义 |
| `link-btn` | 13 | 有定义 |
| `link-btn danger` | 7 | 有定义 |
| `btn btn-ghost danger` | **1** | **无定义** —— 危险按钮和普通按钮长得一模一样 |
| `editor-host__btn` | 3 | 另一套（编辑器包内），与主按钮不共享 |

问题清单：

- **`.btn` 自带 `margin-top: 10px`**，然后在 `.toolbar .btn`、`.pager .btn`、`.app-header-right .btn`、`.page-head-actions .btn`、`.inline-form .btn` 五处写 `margin-top: 0` 把它压掉。这是典型的「基类错位」——按钮的间距属于容器，不属于按钮。每新增一处容器就要再补一条覆盖，早晚漏。
- **只有 primary / ghost 两档**，缺 `secondary`（描边实底）、`danger`（危险实底）、`size`（sm/md）。所以「导出 PDF」「删除」「保存」在视觉上是同一权重。
- **`btn-ghost danger` 未定义**：`PlansView.vue:360` 的删除计划按钮，写了个不存在的类名，实际渲染与普通 ghost 按钮无差别。**破坏性操作没有任何视觉警示**。
- **零交互态**：`:hover` 0、`:focus` 0、`:focus-visible` 0、`transition` 0。按钮、链接、输入框、表格行、菜单项全部没有反馈。
- **输入框无 focus 环**：`input` 只有 `border: 1px solid var(--border-strong)`，没有 focus 样式，聚焦后与未聚焦无区别。
- **无表单校验态**：只有 `ErrorLine` 在表单下方显示错误，字段本身不标红。
- **无 Toast / Dialog / Drawer / Tooltip 组件**：删除靠 `window.confirm`（浏览器原生弹窗），与整体视觉断裂；趋势图数据提示靠 SVG `<title>`（原生 tooltip，有 1 秒延迟且样式不可控）。

### 2.6 数据可视化 —— 2.0 / 5

两套图表，都是手写：

| 图表 | 实现 | 能力 | 缺什么 |
|---|---|---|---|
| 30 天执行趋势（总览） | `div` 堆叠柱（`trend-bars`） | 完成/失败/取消三段堆叠、图例 | **无 y 轴刻度**（看不出数量级）、无 hover 高亮、无点击跳转 |
| 通过率趋势（报告页） | 手写 SVG 折线（`TrendChart.vue`，720×250） | 多系列、基线虚线、偏离点标黄、点可点击 | 无 tooltip（`<title>`）、无区域缩放、无导出、单点不连线、x 轴只有首末两个标签 |

做对的：系列色走了 `var(--chart-N)`，且注释里写明「SVG presentation attribute 里 `var()` 解析行为不确定，所以用 `:style` 绑定」——这是踩过坑之后的正确写法，知道这个细节的人不多。

不足的：**没有任何「图表规范」**。什么时候用柱、什么时候用线、y 轴从 0 还是从 min 起、空数据画什么、单位放哪、颜色顺序谁先谁后，全凭实现时决定。第二个图表作者来写就会不一致。

### 2.7 双语版式 —— 2.5 / 5（体系高、版式低）

体系是好：**411 键 × 2 严格对齐**（`check_i18n.py` 口径；本次逐键解析能取到 409 个纯字面量，差的 2 个是含插值的写法）、零硬编码中文、四项检查全过。这比大多数同类项目强。

但**版式一条都没验过**。实测：

```
可比键 409 个，英文/中文字符数平均 2.77×，中位 2.67×，287 个键超过 2 倍
最极端的短文案：
  缺项      → Missing metadata      8.00×
  凭据      → Credentials           5.50×
  用例      → Test Cases            5.00×
```

换算成像素宽度要打折（中文字符约 1em 宽，拉丁平均约 0.5em），**净膨胀约 1.38 倍，即需要预留 +40% 宽度**——但这个 +40% 目前没有任何地方为它留过：

- 侧栏固定 `200px`，`Test Cases` 在 13px 下约 68px，勉强放得下，但菜单若加图标（20px + 8px 间隙）就只剩 160px 可用；
- 表格 `table-layout` 默认 `auto`，列宽由内容决定，英文下长表头（`Description`/`Capabilities`/`Trigger type`）会把操作列挤出去；
- 按钮无 `min-width`、无 `white-space: nowrap`，`Submit for review` 这类会换行成两行；
- 日期格式未统一，`2026/11/04 10:41:00` 在中英下都是这个格式（好事），但 `formatDateTime` 用的是 `Intl`，需确认 en 下没变成 `11/4/2026, 10:41:00 AM`（宽度差 40%）。

**结论**：双语不是「翻译完了」，是「翻译完了但版式只按中文设计过」。英文界面一定会出现换行、截断、横向滚动——这不是猜测，是 2.77× 的必然结果。

### 2.8 治理工具 —— 3.0 / 5

已有三个脚本，都在跑，都通过：

| 脚本 | 查什么 | 本次实跑 |
|---|---|---|
| `check_colors.py` | 组件内不得出现 hex | `[PASS] 46 个文件无硬编码色值` |
| `check_contrast.py` | 两套主题 40 组对比度 | 全 PASS（暗 20 / 亮 20） |
| `check_i18n.py` | 键集相等 / 无硬编码中文 / 无同值漏译 / 键引用完整 | 全 PASS（411 键、42 文件、0 处中文） |

**但三个脚本都有盲区，而 `--muted` 就是漏网的那条鱼**：

1. `check_colors.py` 只拦 **hex 字面量**，不拦 `var(--不存在的名字)`。→ D1 漏网。
2. `check_contrast.py` 只算 **变量表里已定义的组合**，未定义的引用它根本不知道存在。→ D1 再次漏网。
3. `check_i18n.py` 只查键集与硬编码，**不查文案长度**。→ 英文撑破版式它管不着。
4. 三者都不查 **交互态是否存在**。→ D2 全部漏网。
5. `check_contrast.py` 的解析器按 `data-theme='dark'` 子串**归并**变量块——现状无碍，但只要加入 `[data-accent=…]` 变体块，就会把同主题的默认值覆盖掉（实测：`--accent` 从 `var(--blue-400)` 变成 violet 的 `#ac7df5`，脚本仍打印 PASS）。→ D15，必须先修再加色。

上一份评估的 A-22 已经写过一句很到位的话：「**验证工具自己也会说谎**」。这次是第二次验证。

## 3. 缺陷清单

严重度：**P0** = 影响每个页面且用户可见；**P1** = 影响一致性与效率；**P2** = 打磨项。

| # | 级别 | 现象 | 证据 | 修法 | 归属 |
|---|---|---|---|---|---|
| **D1** | **P0** | `var(--muted)` 引用 21 处，`theme.css` 未定义 → 辅助文字退化为正文色 | `_stat_tokens.py`：未定义 token `--muted` ×21，分布在 `main.css`(13)、`ReportDetailView`、`SuiteTree`、`TrendChart`、`ReportsView` | ① 统一改名为 `--text-muted`（推荐，与 theme.css 一致）；② 同时改 `CONVENTIONS-frontend.md` §8 里写错的 token 名（错误源头）；③ 加 `check_tokens.py` 防复发 | S0 |

## 4. 目标体系（要建什么）

### 4.1 五条设计原则

给这个产品定调，后面所有取舍都回到这五条：

1. **信息密度优先于留白**。这是天天用的工具，不是官网。宁可一屏多两行，不要为了「呼吸感」把表格撑到要滚动。
2. **状态可辨优先于含蓄**。PASS / FAIL / SKIP 必须在 3 米外靠颜色和形状分出来（行业惯例：失败用红、通过用绿；这是测试工具，与股市红绿无关）。
3. **双语等权**。英文不是中文的翻译版，是并列的一等公民。任何布局必须在两种语言下都成立。
4. **暗亮等价**。不是「暗色做完再调个亮色」，两套都是主场，对比度必须各自达标。
5. **数字可扫读**。ID、IP、时间、耗时一律等宽 + 右对齐（数字列），让眼睛能纵向对齐。

### 4.2 Token 三层

在现有两层上加第三层，**不改前两层的名字**（避免又一次 113 处改动）：

```
primitive（固定色板，只出现在 theme.css）
    ↓
semantic（--bg / --panel / --text-muted / --accent …，组件只用这层）
    ↓
component（--btn-h / --row-h / --card-pad / --focus-ring，只为组件服务）
```

**本期要新增的 semantic / component token**：

| token | 用途 | 暗 | 亮 |
|---|---|---|---|
| `--surface-hover` | 表格行/菜单项悬停 | `#1f2c3a` | `#f0f3f7` |
| `--surface-selected` | 选中行/选中项 | `--accent-soft` | `--accent-soft` |
| `--focus-ring` | 焦点环 | `#7cc6fe` | `#1567c9` |
| `--accent-hover` / `--accent-active` | 主按钮两态 | 亮一档 / 暗一档 | 暗一档 / 再暗一档 |
| `--info` / `--info-soft` | 信息态（区别于 warn） | 蓝系 | 蓝系 |
| `--row-h` / `--row-h-dense` | 表格行高 44 / 36 | | |
| `--control-h` | 控件统一高 32（sm 28 / lg 36） | | |
| `--card-pad` | 卡片内边距 16（compact 12） | | |

### 4.3 字体与字阶

```css
--font-sans: -apple-system, 'Segoe UI', 'PingFang SC', 'Microsoft YaHei',
             'Noto Sans SC', system-ui, sans-serif;
--font-mono: 'JetBrains Mono', 'Cascadia Mono', 'Consolas', 'SF Mono',
             'DejaVu Sans Mono', monospace;
```

**等宽字体的使用边界**（写死，不留解释空间）：RUN_ID、设备 IP/序列号、链路标识、文件路径、命令行、日志正文、表格中的数值列（配 `font-variant-numeric: tabular-nums`）。**正文与标题不用等宽。**

**字阶 6 档**（依据：现有实践已有 70% 落在 12/13，把事实固化成 token）：

| token | 值 | 用途 | 现有归并 |
|---|---|---|---|
| `--fs-2xs` | 11px | 图表轴标签、角标、密集视图补充信息 | 11×4（保留） |
| `--fs-xs` | 12px | 辅助文字、表头、字段标签、徽标、页脚 | 12×16（保留） |

| `--fs-lg` | 20px | 页面标题 | 20×1（保留） |
| `--fs-xl` | 28px | 指标数值（统计卡片） | 22、28 → 28 |

> 为什么不学 Ant Design 的 12/14/16 三档：这个产品的表格有 10 列以上（`ReportDetailView` 59 个 class），14px 正文会让一行只放得下 6 列。13px 是为密度选的，不是随手写的。

### 4.4 间距 / 圆角 / 阴影 / 层级

**间距 8 档**（4 基数）：`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40`

映射规则（现有 22 种 padding 怎么归并）：
- 2、3 → 4；6 → 8；10 → 12；14 → 16；其余已是标准值。
- 组件内边距固定：输入/按钮 `8 / 12`，卡片 `16`，卡片头 `16 / 12`，页面体 `20 24`。

**圆角 4 档**：`--r-sm: 4`（输入框内元素、徽标）/ `--r-md: 6`（按钮、输入、标签页）/ `--r-lg: 8`（卡片、表格容器、弹层）/ `--r-full: 999`（胶囊徽标）。
现有 2 → 4，10 → 8。

**阴影 2 档**：`--shadow-sm`（卡片，亮色下 `0 1px 2px`）/ `--shadow-lg`（弹层、下拉，`0 8px 24px`）。暗色下 `--shadow-sm: none`（保持现状，这是对的）。

**层级 z-index 表**（现在没有，弹层一多必打起来）：`dropdown 100 / sticky-header 200 / drawer 300 / modal 400 / toast 500`。

### 4.5 图标体系（已拍板：lucide）

**决策（2026-11-04 大师拍板）**：引入 **lucide** 图标库，替代原方案「自绘 22 个 sprite」。自绘方案作废；原 22 个图标的语义清单保留，作为「要哪些图标」的需求清单。

**实测底数**（lucide-vue-next@0.577.0，本机实际安装 + esbuild 打包测量，复现方式见 §9）：

| 项 | 实测值 |
|---|---|
| 许可 / 运行时依赖 | ISC / **零依赖**（peer 仅 `vue >= 3.0.1`），与「不加 UI 框架依赖」的约定不冲突 |
| 导出图标数 | 5842（含别名）；本产品所需 26 个全部存在 |
| **正确用法**（命名导入 22 个，tree-shake 生效） | min 后 **7.7 KB** / gzip **2.8 KB** |
| **错误用法**（`import *` 全量） | min 后 **683 KB** / gzip **156 KB** —— 相差 **247 倍** |
| node_modules 磁盘占用 | 36 MB（只影响安装，不进构建产物） |

结论：**风险不在库，在导入姿势**。tree-shake 生效时它比自绘 sprite（约 4–6 KB）只大 2 KB 左右，完全可接受。

**四条硬规矩**（违规可被 ESLint / `check_tokens` 拦截）：

1. **只许命名导入**。禁止 `import * as icons`、禁止动态字符串拼图标名——两者都会让 tree-shake 失效，把 156 KB 拖进首屏。
2. **统一线宽 1.5**。lucide 默认 `stroke-width: 2`，比现有界面粗一档；在 `AppIcon.vue` 里统一传 `:stroke-width="1.5"`，全应用不许出现第二个值。
3. **收敛到 `AppIcon.vue` 单一出口**。组件内部持有一张显式映射表（`name → lucide 组件`，仍是命名导入），业务侧只写 `<AppIcon name="server" :size="20" />`；禁止业务代码直接 import lucide——否则图标使用无法统计、全局改名无处可搜。
4. **尺寸三档**：16（行内文字旁）/ 20（菜单、按钮）/ 24（页头、空态），不许出现其他值。

**清单映射**（语义名 → lucide 组件，全部实测存在）：

| 组 | 映射 |
|---|---|
| 菜单 6 | `overview → LayoutDashboard`、`assets → Server`、`cases → ListChecks`、`runs → Play`、`reports → FileText`、`admin → Settings` |

### 4.8 图表规范

### 4.9 双语版式规范

| 规则 | 依据 |
|---|---|
| 任何容器按 **英文宽度 = 中文 × 1.4** 预留 | 实测 2.77× 字符数 × 0.5em/字符 ÷ 1em/字符 |
| 按钮 `white-space: nowrap` + `min-width: 88px` | `Submit for review` 不能折行 |
| 日期统一 `yyyy-MM-dd HH:mm`（英文也不用 `MM/DD/YYYY`） | 列宽稳定 + 审计可读；避免 `11/4/2026, 10:41:00 AM` 撑破 40% |
| 数字千分位、百分比固定 1 位小数 | `93.6%` 不写成 `93.61%` 或 `94%` |
| 中文 `letter-spacing: 0`；拉丁 `0.01em` | 中文字距天然均匀，加字距会散 |
| 长英文用 `hyphens: none` + `overflow-wrap: break-word` | 不靠断词解决，靠预留宽度 |
| 菜单项允许换行两行，但固定 `min-height: 36` | 加图标后可用宽只剩 160px |
| **每个页面都要出一张 en-US 截图**（1920 + 1440） | 唯一能发现撑破的办法 |

### 4.11 强调色体系（多套可选，2026-11-04 新增需求）

**需求（大师 2026-11-04）**：亮暗两套主题都需要一个「突出的色」——当前选中的菜单、重点文字、主按钮、焦点位置要一眼能认出来；并且这个色要做成**多个可选**。

#### 需求拆开是两件事

1. **强调色的语义固定**：不管选哪种颜色，「选中 / 当前 / 重点」这个含义必须由同一组 token 表达。加的不是 5 套配色，是 5 套**同一 token 契约**的取值。
2. **可选 ≠ 自由**：不提供取色器，只提供预设。每个预设的两套主题取值是按对比度**算出来**的（证据见下）；用户随手挑一个 `#777`，整个强调色体系瞬间不可读，且守门矩阵无法为任意色值担保。

#### token 契约（6 个 × 2 主题 × N 预设）

| token | 用途 | 现状 |
|---|---|---|
| `--accent` | 强调文字 / 图标 / 实底 | 有（目前只有一套蓝） |
| `--accent-soft` | 选中底、徽标底、表格选中行底 | 有 |
| `--accent-contrast` | 实底上的文字（暗色反黑 / 亮色反白） | 有 |
| `--accent-hover` / `--accent-active` | 主按钮两态 | **无，新增** |
| `--focus-ring` | 焦点环（= accent，保证换色后焦点依然可见） | 无，随 D2 一起补 |

#### 四个预设 + 两个被否掉的候选（全部实测）

blue **保留现有值不动**（已达标且有余量：暗 5.11 / 亮 4.83）；其余按「与 blue 相同的可读性余量」用 OKLCH 求解（对每个色相求「恰好达标」的亮度），五个预设观感重量一致。

| 预设 | 暗 `--accent` / soft | 亮 `--accent` / soft | 与状态色最近 ΔE | 判定 |
|---|---|---|---|---|
| **blue**（默认） | `#3fa7ff` / `#17324d` | `#1567c9` / `#e8f1fd` | 0.24（vs ok） | **保留现值** |
| **cyan** | `#00a4c9` / `#082a34` | `#00738f` / `#e1f7ff` | 0.16（vs ok） | 收 |
| **indigo** | `#828afe` / `#202339` | `#5a5ccd` / `#eff2ff` | 0.28（vs ok） | 收 |
| **violet** | `#ac7df5` / `#282037` | `#804fc4` / `#f4f0ff` | 0.31（vs ok） | 收 |
| ~~teal~~ | `#00a7a7` | `#007576` | **0.115（vs ok 绿）** | **不收**：会被读成 PASS |
| ~~fuchsia~~ | `#d86dd0` | `#a63ea1` | **0.149（vs fail 红）** | **不收**：会被读成 FAIL |

**为什么没有绿 / 橙 / 红**：这个产品的核心阅读对象是 PASS / FAIL / WARN。强调色一旦落进状态色相 ±40° 内，选中菜单就会和测试结果抢语义。红绿黄三族（ok 154.6° / fail 22.0° / warn 82.7°）整体排除，写入规则。

**对比度实测**（下限：文字 4.5 / 非文字 3.0；方法：OKLCH 求解 + WCAG 相对亮度）：

| 组合 | 四预设实测范围 | 判定 |
|---|---|---|
| accent 文字 / soft 底（选中菜单做法 A） | 亮 4.83–4.92 · 暗 5.11–5.18 | PASS |
| accent-contrast / accent（主按钮文字） | 亮 5.46–5.50 · 暗 6.26–6.38 | PASS |
| accent / bg · panel · surface-2（重点文字） | 最低 4.83 | PASS |
| hover / active 两态对 label | 最低 5.80 | PASS |
| focus-ring / bg · panel（非文字 ≥3 即可） | 最低 5.08 | PASS |

#### 选中菜单的两种做法（都实测过）

- **做法 A（推荐）**：soft 底 + accent 文字 + 左侧 3px accent 竖条。对比 4.83–5.18；「色块 + 竖条 + 颜色」三重编码，色弱用户也可辨。
- **做法 B（更重）**：accent 实底 + 反白文字，5.46–6.38。留给「当前正在执行的运行」这类需要最强权重的场景；默认菜单不用，太吵。

#### 三条联动规则（防止换色引发语义漂移）

1. **状态色不联动**：`--ok / --fail / --warn` 与强调色彻底解耦。用户选 violet，「失败」不会变紫。
2. **图表色不联动**：`--chart-1..4` 保持固定。图表色是**数据身份**（图例含义）——上周报告里蓝线是「通过率」，换色后蓝线变成别的含义，这是事故。
3. **品牌位不联动**：logo / favicon 用固定色，不随用户偏好变。

#### 实现与持久化（复用主题那条链，一处都不要新造）

- CSS：`:root[data-theme='dark'][data-accent='violet'] { --accent: …; }`；不写 `data-accent` 即默认 blue。
- 持久化三层与主题完全同构：`localStorage.accent`（首帧生效）→ `index.html` 内联脚本在挂载前写 `data-accent`（**这段要同步扩展**，现有注释已写明「改一处要改两处」）→ 服务端偏好键 `accent`（跨设备，`preferenceApi` 现成可用）。
- 切换入口：设置页放五枚色板（不是下拉，点击即换）；`useTheme.ts` 旁加一个同构的 `useAccent.ts`，模块级单例、可单测。

#### 对守门脚本的连锁影响（本期最硬的工程约束）

对比度校验矩阵从 2 主题 × 20 组 = 40 组，扩为 **76 组**（新增 4 预设 × 2 主题 × 5 组 accent 相关组合）。**且必须先修 D15**：`check_contrast.py` 按 `data-theme` 子串归并变量块，加入 `[data-accent=…]` 块后会覆盖同主题默认值——实测把 `--accent` 从 `var(--blue-400)` 覆盖成 violet 的值后，脚本照样打印 PASS。不先修，五套强调色的对比度就是「看起来都验了，实际只验了最后一个块」。

## 5. 治理（让体系不退化）

### 5.1 现有三个脚本的盲区

| 脚本 | 盲区 | 本次漏掉的 |
|---|---|---|
| `check_colors.py` | 只看 hex 字面量 | D1（`var(--muted)` 未定义） |
| `check_contrast.py` | 只算已定义组合 | D1（引用不存在的变量它不知道） |
| `check_i18n.py` | 不查文案长度 | D11（英文溢出） |
| `check_contrast.py` | 按 `data-theme` 子串**归并**变量块 | D15（accent 变体块覆盖默认值，实测假绿） |
| 三者 | 不查交互态是否存在 | D2（零 hover/focus） |

### 5.2 新增三个脚本

| 脚本 | 检查项 | 失败条件 |
|---|---|---|
| `check_tokens.py` | ① 所有 `var(--x)` 必须能在 `theme.css` 找到定义；② `font-size`/`padding`/`gap`/`border-radius` 的 px 字面量必须命中白名单；③ token 命名必须符合 `--<类别>-<语义>` | 任一未命中 |
| `check_states.py` | 对 `{btn, link-btn, input, select, tab, app-nav-item, table tbody tr}` 每类必须有 `:hover` 与 `:focus-visible` 规则；`transition` 覆盖率 ≥ 80% | 缺任一 |
| `check_i18n_layout.py` | 中文 ≤6 字的键，英文长度比 > 2.2× 时列出，要求在 `docs/design/i18n-layout-baseline.md` 里有对应处理说明 | 有未登记项 |
| `check_contrast.py` 升级 | 解析按「(主题 × 强调色)」分组、不再合并；每预设跑 5 组 accent 相关组合 | 校验矩阵 40 → 76 组；漏一组即 FAIL |

三条都遵循 A-22 的原则：**带自检**。`check_tokens.py` 必须打印「扫描到 N 个 var 引用、M 个定义」并在 N<50 时直接判定脚本自身故障（防假绿）。

### 5.3 设计系统页（living styleguide）

`/dev/styleguide`，dev 与 admin 可访问，**生产默认不挂载**。

内容：全部 token（色板/字阶/间距/圆角/阴影，标注 token 名与两套主题的值）→ 全部组件（每个变体 × 每个状态）→ 表格与图表样例 → 双语对照（同一区块中英并排）。

**它是唯一真源**：以后新做页面，先看这个页，不再问「用几号字」。

### 5.4 评审卡点

写进 `docs/process/`：

1. 新页面提交前，必须附 **中/英 × 亮/暗** 四张截图（当前只有中文亮色截图，等于只验了四分之一）。
2. 新增任何颜色必须是 token，且 `check_tokens.py` 通过。
3. 新增交互元素必须有 hover + focus 态（`check_states.py` 通过）。
4. 新增文案必须同时进 zh/en，且中文 ≤6 字的要过长度检查。

## 7. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **S0 拖进 v0.2 验收** | D1/D2 是「已完成」资产的返工，会被当成范围蔓延 | 独立成 `UX-01b` 小包，只动 `main.css` + 6 个交互类，**不改任何业务逻辑**，半天内可验 |

| **lucide 导入失控** | 某处图省事写 `import *` 或动态拼图标名，tree-shake 失效 → 首屏 +156 KB（实测） | 收敛到 `AppIcon` 单一出口 + ESLint 禁 `import *`；给图标 chunk 定体积预算（> 15 KB 报警） |
| **强调色被扩成自由取色器** | 「让用户随便挑颜色」的提议迟早会出现 | 只收 4 预设；守门矩阵只为预设担保；新增预设必须走 §4.11 的求解与实测流程 |
| **换色动了数据语义** | 图表色 / 状态色与强调色联动，历史报告图例含义漂移 | §4.11 三条联动规则写进约定；PR review 卡点 |
| **英文版式回归代价高** | 每个页面要重排 | 只在 S3 集中做一轮，避免每版都改一版布局 |
| **设计系统页变成第二份真源** | 组件改了页没改 | 页面直接从 `theme.css` 与组件 props 渲染（不手抄值），并加 `check_states` 兜底 |
