| 排序 | 判据 | Naive UI 2.45.3 | Element Plus 2.14.7 | 采信 |

## 1. 试点范围与隔离方式

| 页面 | 覆盖难点 | 试点实现 |
|---|---|---|
| 登录页 | 表单组件、暗色还原、双语 | Input / Button / 密码框 / 校验提示占位；亮暗 × 中英可切 |
| 用例页 | 10 列宽表、批量勾选、分页、密度 | 10 列 + 12 行 + 批量条 + 分页 + 舒适/紧凑行高切换；亮暗 × 中英可切 |

| 候选 | 版本 | 主题注入方式 | 入口 |
|---|---|---|---|
| **Naive UI**（第一候选） | 2.45.3 | `NConfigProvider :theme-overrides`，由 `naiveOverrides()` 从 token 生成 | `pilot-naive.html` |
| **Element Plus**（对照） | 2.14.7 | `applyElementTokens()` 把 token 写成 `--el-*`，另引入 `element-plus/dist/index.css` | `pilot-element.html` |

两个候选各自独立 Vite 入口与产物目录，避免互相污染 tree-shaking 与体积测量。
`src/theme.css` 是**从主仓 `frontend/src/styles/theme.css` 直接复制**的，试点不另写一份色值——「token 唯一真源」这条判据靠文件级复制保证，不靠人自觉。

## 2. 四个评审维度的实测结果

### 2.1 产物体积（✅ 本轮实测）

命令：`cd docs/design/pilot && npm install && bash measure.sh`（各候选独立 `vite build`，`gzip -9`）。
原始表：`docs/evidence/v0.3/ux04-pilot-measure-20261104.tsv`。

| 候选 | JS raw | JS gzip | CSS raw | CSS gzip | **合计 gzip** | build |
|---|---:|---:|---:|---:|---:|---|
| Naive UI 2.45.3 | 508,718 B | **153,376 B** | 4,300 B | 1,403 B | **154,779 B（≈151 KiB）** | 4.92 s，1 个 >500 KB chunk 警告 |
| Element Plus 2.14.7 | 358,122 B | **125,491 B** | 365,594 B | 48,993 B | **174,484 B（≈170 KiB）** | 6.28 s，1601 modules |

**读这两行必须带三条限定**，否则会误判：

1. 这是**独立试点入口的完整产物**（含 vue runtime + 库 + 试点页），不是「接入现有应用后的净增量」；现有应用已有的 vue runtime 会被复用。
2. Element Plus 的 365 KB CSS 是 `dist/index.css` **全量样式**；按需引入可显著下降，本次为控制变量未做逐组件 CSS 优化。Naive UI 是 CSS-in-JS，无独立样式文件——这是两库的固有差异，不是接入方式的优劣。
3. 按计划 §2.2 步骤 0 原文，**组件库 chunk 预算应在试点实测后由评审定**，本报告只给数，不先验拍预算，也不据此判谁达标。

### 2.2 与 semantic token 的对接成本（✅ 本轮静态实测）

| 项 | Naive UI | Element Plus |
|---|---|---|
| 适配层形态 | 一个 `naiveOverrides()` 对象（约 20 行） | `ELEMENT_MAP` 15 条 + `applyElementTokens()` 写 CSS 变量 |
| 注入点 | `NConfigProvider :theme-overrides` | `<html>` 上 15 个 `--el-*` 变量 |
| 切主题 | `computed` 显式依赖 `theme.value` → 重读 token | `watch([theme, lang])` → 重绘 token |
| 库自带色值 | 无独立 CSS，全部由 JS 主题对象覆盖 | **全量 CSS 内含库自有色值**，靠 `--el-*` 覆盖；覆盖不到的属性仍可能露出库色 |
| 硬编码色值 | 0 | 0 |

`python3 check_pilot.py` → **PASS**：6 个试点自写文件、0 硬编码色值、24 个输入 token 全部在 `theme.css` 有定义、两版 `App.vue` 均经过 `tokenAdapter`（单向派生）。
`python3 check_pilot.py --self-test` → **PASS**：注入 `#ffffff` 必红且点名命中行、还原字节一致后必绿。

> 一次守门自咬已修正：初版把 `--el-*` 这些**输出变量**当成「输入 token」去 `theme.css` 找定义，误报 15 处。
> 收窄为只检查输入侧后转绿。守门自己造假红，比没有守门更浪费评审时间。

**静态层面的倾向性事实**（不是结论）：Naive UI 的主题对象不引入第二套 CSS 真源；Element Plus 需引入全量样式，
「无第二真源」这条判据要靠 `--el-*` 覆盖完备性保证，覆盖表越长风险越高。是否构成否决项由评审定。

### 2.3 暗色还原度（⏳ 待现场）

- ✅ 已可机检：亮/暗两套 `--bg/--panel/--text/--accent` 等 token 由 `theme.css` 切换，适配层在切换后重读，取色链路闭合。
- ⏳ 未做：**中/英 × 亮/暗四态截图与取色比对**。试点可本地预览（`npx vite --config vite.naive.config.ts`），
  但本轮没有自动截图，也没有替大师做「还原度够不够」的视觉判断。四张截图与 `check_contrast.py` 取色结果需在评审现场采集。

### 2.4 表格密度可控性（⏳ 待现场）

| 能力 | Naive `NDataTable` | Element `ElTable` | 试点用法 |
|---|---|---|---|
| 行高双档 | `size="small\|medium"` | `size="small\|default"` | 两版均接了舒适/紧凑切换 |
| 粘性表头 | 需配 `flex-height` + 固定高度 | `height` 属性 | **本轮未验证**，两版都用容器滚动 |
| 容器级横滚 | `:scroll-x="1180"` | 外层 `overflow-x:auto` + `min-width` | 已接，1440/1920 观感待截图 |
| 批量勾选 | `:checked-row-keys` + `@update:*` | `@selection-change` | 两版均接 |

代码层面两库都提供了行高档位与横向滚动所需的能力，**没有出现「做不到」的硬阻塞**；是否达到可接受密度仍待 1440/1920 截图。
