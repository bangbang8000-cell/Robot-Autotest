# ADR-0001 · monorepo 单体仓库 + 目录即边界

- **状态**：已采纳
- **日期**：2026-11-02
- **决策人**：大师（G0 纪要）
- **约束范围**：全仓，v0.1 起

## 背景

平台由三块强耦合的产物组成：后端 `backend/`（Spring Boot）、前端 `frontend/`（Vue 3）、
以及衍生自 RoboScope v0.16.1 的编辑器 `packages/editor/`。

耦合点在于**接口契约频繁变**：v0.2~v0.5 期间，后端 DTO 与前端类型同一天改好几次。
如果拆成多个仓库，「改一个字段」要提两个 PR、等两次评审、还要处理版本对齐。

## 选项

| 选项 | 优点 | 代价 | 结论 |
|---|---|---|---|
| ① 多仓（backend / frontend / editor 各一仓） | 权限与发布完全独立 | 一次接口变更跨仓协调；版本号要对齐三处 | 不选 |
| ② **monorepo，各侧独立构建** | 一次 PR 改完契约两侧；统一版本号 | CI 必须做路径过滤，否则改文档也跑全量 | **选** |
| ③ monorepo + 独立构建产物流（release 仓） | 仓库最干净 | 多一轮搬运，产物追溯变复杂 | 不选 |

## 决定

采用 **②**：一个仓库，三个可独立构建的子目录。边界靠**目录 + ArchUnit**，不靠仓库权限。
`packages/editor` 是唯一的「外来代码区」，业务代码不得反向依赖它。

## 后果

- 正面：一次 PR 可同时改后端 DTO 与前端类型；`git log` 一处看全改动。
- 负面：CI 需要路径过滤（只跑受影响侧），配置比多仓复杂；仓库体积增长更快。
- 复核触发条件：仓库总量超过 50 MB（NFR-v0.1-04），或编辑器衍生产物需要独立发版时。
