# ADR-0013 · 执行安全分级与开发期禁跑令

- **状态**：已采纳
- **日期**：2026-11-04
- **决策人**：**大师**（本次会话四项裁定）｜ 记录与实现：学徒（AI）
- **约束范围**：全部版本的用例执行域（EXE）、自动化（PLN）、试点（HRD）；台账导入（CAS-03 / ENV-04）

## 背景

平台承接的历史资产是**测试用例台账**（计划书里写作「461 条」，实际在手的
`基本功能导入测试v0.2.6.0.1.xlsx` 为 **226 条**，`TN-IMP-001~226`）。这批用例面向真实网卡、
真实交换机、真实服务器，**不是可以随便重跑的单测**。

2026-11-04 实测 226 条的动作面（见下文实测表）：**32 条命中高危**、**89 条含写操作**。
典型如：

| 用例 | 真实动作 | 台账里写的命令 |
|---|---|---|
| `TN-IMP-211` | PDU 切断 GPU01 全部 AC 输入，**连续 200 轮** | `cat boot_id` / `lspci` / `ethtool` / `ping` |
| `TN-IMP-054` | **逐档改交换机端口速率**再恢复 | 只读查询 |
| `TN-IMP-079` | 关闭 UFO offload（`ethtool -K`） | `ethtool -k`（读） |

也就是说：**命令列只写了采样命令，真正的动作写在步骤和标题里。** 若平台把台账导进去就
「点执行」，会在无人值守时把生产测试链路刷掉、断掉、甚至断电。

同时，平台自身的开发验证确实需要「跑一次」来证明执行域可用——但**要验的是程序，不是用例**。
这两件事此前在计划里混在一起（EXE-07 的验收写「4 并发压测」、CAS-03 写「461 条导入」）。
本 ADR 把两者彻底分开。

## 决定

### 1. 用例按四级标注，标注依据是「真实动作」而非「作者描述」

| 级别 | 含义 | 判据 |
|---|---|---|
| **L0** | 只读 | 命令逐段命中只读白名单，且步骤/标题/交换机列均无动作特征 |
| **L1** | 可逆写 | 改 IP / 改 offload / 改 ring / 启停服务 —— 能改回来 |
| **L2** | **高危·不可逆** | 改交换机配置、刷固件 BIOS、装卸驱动、重启断电（含 PDU）、删除格式化、断链、ethtool 自检 |
| **LX** | 无法判定 | 命令列为空或含白名单外动作。**不授 L0 资格**，交人工补判 |

判定工具：`tools/classify_cases.py`（**白名单制**，不是黑名单制——黑名单永远漏，
漏的那条可能就是刷 BIOS）。

### 2. 开发期禁跑令

> **在 G5（报告域门禁）通过之前，禁止在真实 DUT / 真实交换机上执行任何台账用例。**

- 验证程序能力，只允许**临时项目 + 合成脚本 + L0 用例（≤10 条）**；
- 真实台账只做**导入**（读 Excel 入库、字段对账、重导幂等），**不做执行**；
- `L2` **任何阶段都不允许自动执行**，即使解禁后也必须人工在场逐步确认；
- `LX` 在人工补判前一律按 L2 对待。

### 3. 解禁阶梯（G5 之后）

| 阶段 | 允许范围 | 附加条件 |
|---|---|---|
| G5 通过后 | 合成用例全量 + L0 批量 | 平台可留证据；先在维护窗口 |
| L0 稳定 2 轮后 | L1 抽样（每类 ≤3 条） | 人盯首轮，记录变更前后状态 |
| 试点阶段（HRD-03） | L2 准入名单 | 逐条审批 + 现场值守 + 可回滚预案 |

## 实测数据（2026-11-04，226 条）

```
L0   10   只读，可作开发期验证用例
L1   89   可逆写（其中 52 条是 ethtool -K/-L/-G 改 offload/队列/ring）
L2   32   高危：改交换机 21 / 重启断电 5 / 刷固件 3 / 装卸驱动 1 / ethtool 自检 1 / 断链 1
LX   95   无法判定（74 条命令不在白名单、21 条命令列为空）
```

证据：`docs/evidence/v0.2/cas03-classify.log`、`cas03-ledger-classification.csv`（逐条含判定规则与依据）。

**L0 的 10 条**：`TN-IMP-002 / 016 / 017 / 021 / 025 / 027 / 029 / 046 / 048 / 049`
（BMC I2C 识别、CPU 兼容、OS 兼容、PCIE 信息、光模块 DDM/信息、混插、指示灯、Advertised Modes、介质类型）。

## 三个漏判案例（写下来是为了不再犯）

判定逻辑迭代了四轮，每一轮都是因为「机器判绿了、人一看不对」：

| # | 漏判 | 根因 | 后果若未发现 |
|---|---|---|---|
| 1 | 52 条 `ethtool -K/-L/-G` 被判 L0 | ethtool 读/写靠**大小写**区分（`-k` 读 / `-K` 写），正则用了 `re.I` | 开发期就把 52 条改 offload/队列/ring 的用例当只读放跑 |
| 2 | `TN-IMP-211`（PDU 断电 200 轮）被判 L0 | 只看命令列，真实动作在**步骤列** | 无人值守下连续断电机 200 次 |
| 3 | `TN-IMP-079/131`（开关测试）被判 L0 | 只看命令列，动作写在**标题**里 | 「开关」测试只跑了读命令，验收假通过 |

因此定死两条：

- **四列扫描**（标题 / 步骤 / 交换机 / 命令）缺一不可，`--l0-only` 只是初筛；
- **L0 必须人工逐条复核签字**，机检结论不得直接当放行依据。本次 10 条已人工看过命令原文。

## 后果

- **正面**：开发期有了明确的「可以跑什么」清单，不再靠临场判断；L2 的 32 条被显式隔离；
  「验证程序」与「验证产品」分家，合成用例可随时回归、不依赖设备在线。
- **负面（必须承认）**：**真实链路的适配问题会推迟到 G5 之后才暴露**。若前端的用例展示、
  参数化、断言解析对真实台账格式有假设错误，要到解禁后才打得出来。
- **补偿**：① `CAS-03` 导入后，用 L0 的 10 条在**临时项目**里走一遍「读台账→生成脚本→只读执行」；
  ② 台账字段映射的真实缺陷（命令列不全、动作写在标题里）本身纳入 CAS-03 的对账报告。
- **不可援引为通例**：本条只限制「在真实设备上执行台账用例」。CI 单测、集成测试、
  合成用例回归**不受影响**，也不会因本条降低任何既有 KPI。
