## 1. 为什么用「最小 Spring 上下文」而不是 `@SpringBootTest`

`CaseImportIT` 的写法是手工 `new CaseImportService(...)`，没有代理，注解等于注释。
要让 `@Transactional` 真的生效，只需要三样东西：数据源、事务管理器、被事务拦截的 Bean。

所以本测试用 `AnnotationConfigApplicationContext` + `@EnableTransactionManagement` 起一个
**只有 6 个 `@Bean` 的上下文**（`DataSource` / `JdbcTemplate` / `DataSourceTransactionManager` /
`TestCaseRepository` / `AccessControlService` / `AuditService` / `CaseImportService`），
**不起 Boot、不起 Web、不跑 Flyway**，连的仍是真 MySQL（ADR-0002：不用 H2）。

好处：3 秒内跑完，且证明的是「注解在 Spring 代理下确实回滚」，而不是「我在测试里又套了一层事务」。

## 2. 四条用例与读数

| # | 用例 | 断言 | 实测读数 |
|---|---|---|---|
| 1 | `整批回滚`：先入库 `TN-TX-EXIST`，再提交 `[NEW-1, NEW-2, EXIST, NEW-3]` | 抛 `CONFLICT`，且库里只剩 1 行（前两行随事务消失） | `BusinessException(CONFLICT)`；`COUNT(*)` = 1 ✅ |
| 2 | `访客角色拒绝`：项目内 `viewer` 角色（矩阵无 `IMPORT:EXECUTE`） | 抛 `FORBIDDEN`，0 行落库 | `BusinessException(FORBIDDEN)`；`COUNT(*)` = 0 ✅ |
| 3 | `非成员拒绝`：用户存在但不是该项目成员 | 抛 `FORBIDDEN`，消息 `无权访问该项目`（不泄露项目是否存在） | 同上 ✅ |
| 4 | `并发导入`：两线程（`CountDownLatch` 同时放行）导同一批 5 个编号 | 只有一批成功；失败那批整批回滚；库里恰好 5 行 | 成功批 `imported=5`，失败批 `BusinessException(CONFLICT)`，`COUNT(*)` = 5 ✅ |

并发用例连跑 3 次，3/3 一致（每次都打印一行，便于在 `run_it.sh` 日志里核对）：

```
[CAS-03 并发] 成功批 imported=5 | 失败批异常=com.qa.autotest.common.BusinessException | 库里行数=5
```

判定依据不是「两个线程都报错」，而是**库里恰好 5 行**：无论谁先提交，落库的要么是完整的 5 条，
要么是 0 条，不存在「各插一半」。

## 3. 顺带查出的一个缺陷（已修）

首次跑并发用例时，失败那批抛的是：

```
00:36:32.563 WARN org.mariadb.jdbc.message.server.ErrorPacket -- Error: 1062-23000:
Duplicate entry '4-TN-TX-C-1' for key 'test_case.uk_test_case_project_code'
[CAS-03 并发] 成功批 imported=5 | 失败批异常=org.springframework.dao.DuplicateKeyException | 库里行数=5
```

数据是安全的（唯一键 + 回滚兜住了），但**异常类型不对**：`commit` 只用 `codeExists` 做预检，
并发时两边都能通过预检，真正挡住重复的是唯一键 `uk_test_case_project_code`；
`DuplicateKeyException` 没人翻译，会落到 `GlobalExceptionHandler` 的兜底分支，
对外是 **500「服务内部错误」**——一个「有人同时在导同一批编号」的正常竞态，被报成了服务故障。

修法（与同仓既有写法一致：`RunService:131`、`CiTriggerService:106` 都捕获这个异常）：

- `CaseImportService.commit` 的插入循环外包 `try/catch (DataIntegrityViolationException)`，
  翻译成 `BusinessException(ErrorCode.CONFLICT, "并发导入冲突：编号已被另一批次占用，请重新预览后再提交")`；
- 抛的仍是 `RuntimeException`，`@Transactional` 照常整批回滚，不留半批；
- 用例 4 的断言随之收紧为「失败批必须是 `CONFLICT`」，即 409，不再是 500。

## 4. 本测试仍未覆盖（别读成覆盖了）

1. **HTTP 层**：没有 Web 层，断言的是服务层 `ErrorCode.FORBIDDEN`；`403` 状态码与响应体
   由 `GlobalExceptionHandler` 决定，未在此验证。
2. **并发规模**：只测两个线程、单机单实例。多实例部署下的竞态（连接池、隔离级别差异）未测。
3. **Excel 解析**：不涉及（`commit` 直接吃 `ImportRow`，解析链路由 `CaseImportIT` 覆盖）。
