回滚日志逐条打印 20 个 down 脚本（`V7_4` → `V1__baseline`），末尾只剩
`flyway_schema_history`（`flyway-undo.log`）。

### 4.2 一个必须写清楚的设计事实（不是故障，是容易踩的坑）

`db-undo.sh` **只删业务表、不动 `flyway_schema_history` 的行**（ADR-0003 明文：回滚后表数为 1）。
因此**回滚后再跑 `db-migrate.sh` 是空操作**：Flyway 认为 20 个版本都已应用，直接返回
"up to date"，库里业务表仍是 0 张——第三步读数已实证（`tables=0, history_rows=20`）。

要真正重建，必须走 `db-reset.sh`（`DROP DATABASE` + `CREATE` + migrate），即第四步。
`artifacts/run_it.sh` 与 CI 走的就是 reset 路径，所以集成测试不受影响。

**建议（P1，未改代码，留待判定）**：`db-undo.sh` 末尾补一行提示
「已回滚，历史表仍保留全部版本；要重建请跑 `db-reset.sh`，直接 migrate 是空操作」，
避免下一个人把「migrate 成功但 0 表」当成迁移脚本坏了。

### 4.3 第一轮失败的定位（留痕）

第一轮（22:35）`boot-check PING200=0`、三个 `flyway-*` 全 `EXIT=1`（6ms 即退）。
根因同一个：脚本 `source ~/.config/robot-autotest/env` 时**没有 `set -a`**，
`CRED_MASTER_KEY` / `DB_PASSWORD` 未导出到子进程。

- 启动：`Caused by: java.lang.IllegalStateException: 缺少环境变量 CRED_MASTER_KEY（32 字节 base64）`（`boot.log` 第一轮）
- 迁移：`[db] 缺少环境变量 DB_PASSWORD（仓库不存放任何口令，见 AGENTS.md §9）`（`flyway-migrate-1.log` 第一轮）

补 `set -a` 后全部复跑通过（`exit-codes.txt` 第 14~20 行）。
**结论：不是产品缺陷，是预检脚本自身的错**；`artifacts/run_it.sh` 的做法是对的（它就带 `set -a`）。
