v2.0 解决的是「编辑器怎么进来、报告与计划怎么自研」。本版补的是两件 v2 没做的事：

1. **把 8001 当成一个可解剖的信息架构标本**，而不是只当成"可借鉴的表结构"。v2 只说了"57 表可借鉴"，没有回答"它的菜单为什么长这样、页面怎么组织、能不能直接抄"。
2. **把工程约束文档化**。v2 只有技术方案，没有回答"以后谁来改、按什么规矩改、怎么防止改烂"。

### 1.3 一项必须先说清的核查结果

**8001 的前端源码不在交付物里。** 这是本版最重要的单条事实，直接决定了"复用"二字的边界：

## 2. 结论先行

### 2.1 一句话结论

**8001 是一部很好的"信息架构反面教材 + 页面模式正面样例"。** 它的页面模式值得照做，它的菜单结构千万不要照抄。

### 2.2 十条硬结论

1. **菜单结构不能抄。** 8001 的一级菜单已膨胀到 **13 个**（§3.2），技术域（以太网 / RDMA / QoS / 虚拟化 / 卸载 / GPU / 维护）全部平铺成一级。照抄等于把它的失控复制过来。
2. **而且它自己还在改。** 10-26 到 10-27 三天内，菜单至少重排了 **4 版**（§3.3）：`计划与执行` 分组消失、`结果与证据` 改名 `详细测试过程`、`占用与身份` 改名 `资源可用性`、新增 `性能基线`。一个连作者都在改的信息架构，不具备"照抄"的资格。
3. **页面模式才是真资产。** 5 种可复用的页面骨架（§4.1），有真实的 class 证据（`tc-hero` / `grid-2` / `card` / `tc-kpi` / `tablewrap` / `dropzone`），可以直接转成 Vue 组件规范。
4. **最值钱的设计只有一条：双列结果并置。** `Excel历史结果` 与 `平台本轮结果` 两列并排，KPI 直接显示"尚无本轮结果 226"（§4.3）。它不让历史通过冒充本轮通过——**这和我们 metadata 定规是同一个思想**，必须继承。
5. **前端代码复用度为 0。** 源码不存在；即便存在，原生 HTML+JS 也无法迁移到 Vue 3。所谓"借鉴代码"在 8001 这条线上，实际只能借鉴**设计、契约、数据**。
6. **API 与数据可借鉴但必须重写。** 49 个 API 模块 / 187 个端点 / 57 张表（§4.4），是完整的领域模型；但 Python 实现与 Java 技术栈不同，只能按契约重写。
7. **技术域占掉了 45% 的 API 模块。** 49 个模块里约 22 个（以太网、RDMA、QoS、DPDK、XDP、VFIO、KVM、GPU…）是技术域专用。这是菜单膨胀的根因，也是新平台必须做"技术域下沉"的直接依据（§6.4）。
8. **新平台应收敛到 6 个一级菜单**（§6.2），技术域改为"用例集上的标签 + 用例库的分类轴"，不占一级导航。
9. **两份 Agent 规范的最大价值不在内容，在形式**：禁止项 + 操作步骤 + 交付前检查清单。新平台要建 **三份**文档（§8.3），而不是把现有 `AGENTS.md` 写成大杂烩。
10. **工期由 30 周调整为 31 周**（+1 人月）：新增信息架构重设计（0.5 人月）与文档体系（0.5 人月）。这不是坏消息——把 IA 想清楚，能省掉后期返工。

### 2.3 评分（维持 77，但结构变了）

| 维度 | 权重 | v2.0 | **v3.0** | 变化原因 |
|---|---:|---:|---:|---|
| 技术可行性 | 25% | 88 | **88** | 编辑器结论不变 |

### 3.4 信息架构诊断：五个问题

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| **IA-1** | **一级菜单过载** | 13 个一级菜单，超过人眼扫视上限（经验值 7±2） | 新用户找不到入口；老用户靠记忆点位置 |

### 3.5 可借鉴 / 不可借鉴

| 对象 | 判断 | 理由 |
|---|---|---|
| 一级菜单的**具体分组** | ❌ 不可借 | 13 个一级本身是失控结果，且三天改四版 |

## 4. 8001 功能区实现逻辑

### 4.1 五种页面模式（可直接转成组件规范）

从截图与 `layout-narrow.html` 的真实 class 命名反推，8001 的功能区只有 5 种骨架，全部页面都是这 5 种的组合：

| 模式 | 骨架 | 真实 class 证据 | 典型页面 |
|---|---|---|---|
| **A 台账列表页** | hero 标题 → 筛选栏 → 表格 → 行内操作 | `panel`、`card`、`tablewrap`、`btn ghost small` | 设备资源、执行记录与证据 |
| **B 看板页** | hero → 4 宫格 KPI → 双列结果表格 | `tc-hero`、`tc-kpis`、`tc-kpi` | 测试总表看板、采集记录分析 |
| **C 工作台页** | 卡片网格（2 列）→ 策略/分组/身份筛选 → 多选表格 → 批量操作 | `grid-2`、`cardhead`、`dropzone` | 资源工作台、用例导入与评估 |
| **D 步骤向导页** | 步骤条（1→4）→ 当前步表单 → 任务卡片列表 | 步骤编号块 + `card` 列表 | 资源计划与任务执行 |
| **E 规范页** | 单卡片 + 分节编号条目 | `card` + 有序列表 | 测试与恢复原则 |

### 4.2 模式 A：台账列表页

以「设备资源」为例，结构是固定的四段：

```
┌ hero：DEVICE & RESOURCE（英文小标）
│       设备资源（中文大标）
│       管理连接信息，识别真实设备，为后续环境构建准备资源。（一句说明）
├ KPI 行：设备总数 12 | 已识别 12 | 凭据已配置 12 | ...
├ 折叠区：批量导入资源 / 单台添加·修改（两个并列的折叠面板）
└ 卡片：资源列表 共 12 台，其中 12 台凭据完整
        ├ 搜索栏：搜索设备（按名称/IP/厂商/型号）+ 设备类型下拉
        ├ 提示行：导入或保存后会自动连接设备识别类型/厂商/型号，结论带证据；
        │         识别失败会在"识别"列给出原因
        └ 表格：主机名 | 地址 | 类型 | 厂商 | 型号 | 算法档位 | 凭据 | 识别 | 操作
                操作 = 详情 / 编辑 / 删除（删除为红色）
```

**实现逻辑的三个要点**：

1. **数据自证**：表格里的"识别""凭据"不是人工填的，是后端连接验证后回写的，且失败必须给出原因。这避免了"看起来配好了其实没连上"。
2. **统计与列表同源**：`共 12 台，其中 12 台凭据完整` 与 KPI 的数字来自同一查询，不会出现"上面写 12、下面列 10"。
3. **危险操作视觉降级**：删除按钮用红色 + 行内独立位置，与"详情/编辑"区分。

### 4.3 模式 B：看板页（最有价值的一页）

以「测试总表看板」为例：

```
┌ hero：TEST CASE BOARD / 测试总表看板 /
│       按总表查看历史结果、详细流程与平台新执行结果。环境信息请在环境与拓扑查看。
├ 卡片：筛选栏
│       批次下拉（基本功能导入测试v0.2）
│       搜索（编号、测试项或分类）
│       历史状态下拉（全部历史状态）
│       分类下拉（全部分类）
├ KPI 四宫格
│       总表测试项 226   全部类别，含专项项目
│       Excel历史通过 156  导入标签，非本轮通过   ← 注意这句限定
│       平台本轮通过 0     原始输出完整验收结果
│       尚无本轮结果 226   未沿用历史通过         ← 缺口直接显示
├ 行：显示 226 / 226 项 · 历史与本轮结果独立保存
└ 表格：测试编号 | 测试项目·分类 | Excel历史结果 | 平台本轮结果 | 操作
        TN-IMP-001  BMC/BIOS网卡资产识别  跳过  未测试  [流程/结果]
        基本功能测试 / BMC/BIOS识别测试
```

**这一页为什么值钱**：

- "Excel历史通过 156" 下方小字写明"**导入标签，非本轮通过**"——用一行小字堵死了"拿历史结论充当轮证据"的路。
- "尚无本轮结果 226" 直接显示缺口，而不是显示一个漂亮的通过率。
- 两列结果独立保存，互不覆盖。

**这正是我们 metadata 十项定规要解决的问题**（谁、何时、哪台设备、哪条链路、什么版本）。8001 用 UI 表达，我们用 metadata 表达，两者应合并：**看板显示本轮结论，metadata 证明本轮结论**。

### 4.5 执行功能区：最复杂、也最值得学的一页

「资源计划与任务执行」是 8001 交互最重的页面，暴露了它的执行模型：

| 要素 | 实现 | 可借鉴性 |
|---|---|---|
| 步骤条 | `1. 选择设备与网卡` → … → `4. 整组自动连续执行` | ✅ 强 |
| 计划生成 | "尚未生成计划；选择资源后点击检查并生成计划" | ✅ 强（先预览后执行） |
| 执行规则 | "整组自动连续执行 · **每例三遍**" | ✅ 可借为可配置策略 |
| 失败处理 | "失败、未知或环境不满足时停止，未接入项单独列出缺口" | ⚠️ 串行可行，并行需改 |
| 任务卡片 | 卡片网格：任务名 + 时间 + 短 ID + 成功徽章 | ✅ 强 |
| 批量操作 | 全选 / 删除选中 / 清除选择，删除前提示"会同步删除事件、计划、用例执行记录、证据索引和测试集条目，原始证据文件保留，操作不可撤销" | ✅ 强（删除影响面明示） |
| 删除护栏 | "已删除 0 个平台任务及数据记录；1 个未删除：任务属于未结束的测试集批次，请先完成或取消该批次" | ✅ 强（部分失败要逐项说明） |
| 高级调试 | 折叠的"开发调试（高级）" | ✅ 强（把危险能力收进折叠区） |

**这页体现的三条工程原则，比页面本身更有价值**：

1. **删除前必须说明影响面**，且要能"部分成功 + 逐项说明原因"，不能一句"删除失败"。
2. **高级/危险能力放折叠区**，不与主流程平级。
3. **执行规则的文字就在界面上**（每例三遍、失败即停），不藏在文档里。

## 5. 借鉴与复用的定量结论

### 5.1 三类资产的复用度

| 资产类别 | 复用度 | 说明 |
|---|---:|---|
| **前端代码** | **0%** | 源码不存在；即使存在，原生 HTML+JS 无法迁移到 Vue 3 |
| **后端代码** | **0%**（直接）/ **高**（设计） | Python → Java，只能按契约重写 |
| **数据表结构** | **高（80%）** | 57 表设计合理，改 MariaDB 语法即可；但需按双模模型调整用例域 |
| **页面模式** | **高（可直接组件化）** | 5 种骨架，有 class 证据 |
| **业务规则** | **很高** | 双列并置、缺口显性化、删除影响面、每例三遍 |
| **测试数据** | **中（部分）** | 461 条用例台账可导入；12 台设备记录可参考，不含凭据 |

### 5.2 一句话回答"是否可以充分借鉴和复用"

**借鉴可以充分，复用不能充分。**

- 说"借鉴充分"，是因为它的**领域模型（57 表）、页面模式（5 种）、业务规则**成熟度很高，抄设计能省 4-6 周。
- 说"复用不充分"，是因为**一行代码都拿不过来**：前端没有，后端语言不通。任何"直接复用代码"的预期都会落空。

这个结论必须让评审看见，否则会按"复用"去排期，然后在 M2 发现要重写。

## 6. 新平台信息架构设计（本版核心产出）

### 6.1 设计原则

1. **一级菜单收敛到 6 个**，遵循"一次测试活动的生命周期"，不按技术领域切。
2. **技术域降级为标签**：以太网 / RDMA / QoS / 虚拟化 / 卸载 / GPU 等，作为用例的 `domain` 标签与用例库的分类轴，出现在筛选器与用例树上，**不占导航位**。
3. **规范文档不进导航**，进"帮助中心"（页面右下角入口 + 独立路由）。
4. **"待开发"不进菜单**，进路线图页面。
5. **一个功能只有一个入口**（解决 IA-2）。

### 6.2 一级 / 二级菜单方案

| # | 一级 | 二级 | 对应 8001 的哪些页 | 说明 |
|---:|---|---|---|---|
| 1 | **总览** | 平台首页；我的待办 | 工作台 / 平台总览 | 补"我的待办"（待评审用例、失败待分析） |
| 2 | **资产** | 设备与端口；环境与拓扑；凭据 | 设备与资源 + 环境与拓扑 | 合并"资产"与"环境"，因为二者是"我有什么、我能搭什么" |
| 3 | **用例** | 用例库；用例集；导入与评估；能力索引 | 测试用例全部 4 项 | 技术域作为筛选标签 |
| 4 | **执行** | 执行计划；运行记录；实时面板 | 详细测试过程前 3 项 | 并行执行的主战场 |

### 6.4 技术域怎么放（关键设计）

8001 的做法是"一个技术域一个一级菜单"，根因是**用例模型没有分类轴**。新平台改为：

```
用例实体：
  case_id / title / domain[] / category / priority / link / device_requirements
                 ↑
                 └── domain 取值：ethernet | rdma | qos | virt | offload | gpu | storage | base
```

- 导航上只有一个"用例库"，页内提供 `domain` 多选筛选器（芯片化）。
- 用例集（test_set）也用 `domain` 打标，执行计划可按 domain 批量筛选。
- 报告可按 domain 聚合通过率（这比 8001 的"每个域单独一个菜单看板"更省）。

**收益**：新增一个技术域，只加一个枚举值，不加菜单、不加页面、不加路由。

### 8.2 三个最值得抄的形式（与内容无关）

### 8.6 新平台特有的硬规矩（建议直接写入）

以下 6 条是从本报告结论直接转化来的，建议作为 `AGENTS.md` 的"第一条约束"：

1. **用例文本是唯一真源**。`robot_file.content` 之外不允许再存一份"结构化用例"；任何结构化视图都是运行时从文本解析出来的。
2. **编辑器改动不得越界**。`packages/editor/components/**` 与 `core/**` 视为上游代码，本地改动只能落在 `adapter/**` 与 `patches/**`。
3. **metadata 缺项即拦截**。装配 `.robot` 时缺任一项必填 metadata 直接失败；导出报告时缺项直接拒绝。
4. **租约先于执行**。任何执行请求必须先拿到 `resource_lease`（设备+端口粒度），拿不到就排队，不允许"先跑起来再说"。
5. **历史结论不得冒充本轮**。报告与看板中，历史结果与本轮结果必须分列，历史列必须带"非本轮"标识。
6. **删除必须说明影响面**。批量删除前必须列出将级联删除的对象；部分失败必须逐项返回原因。

### 8.7 文档维护机制

| 问题 | 机制 |
|---|---|
| 什么时候写 | 每次"改变了行为"的合并后，24 小时内更新对应章节；纯重构不写 |
| 谁来写 | 改代码的人写，不设"文档专员" |
| 怎么防腐化 | 每季度做一次"文档对账"：按 `AGENTS.md` 跑一遍命令，跑不通就改文档 |
| 长度控制 | `AGENTS.md` ≤ 800 行；两份 CONVENTIONS ≤ 250 行；超了就拆，不许无限增长 |
| 与代码冲突时 | **以代码为准，立即改文档**；不许出现"文档说 A、代码做 B" |
