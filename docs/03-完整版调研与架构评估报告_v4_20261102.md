## 2. 结论先行

### 2.1 一句话结论

**做，但要做「领域层」，不要做「第二个 RF 仪表盘」。**

三件套（Robot Framework / robotdashboard / RoboScope）负责「跑」和「看」；新平台负责「谁、凭什么、按什么顺序、在哪台设备上跑，以及证据是否完整可交付」——**这部分三件套一行代码都没覆盖**。而 RoboScope 的用例可视化编辑器，是本项目唯一值得源码级移植的高价值资产。

### 2.2 十四条硬结论

| # | 结论 | 证据强度 |
|---|---|---|

**（2）纠偏：`/git/` 返回 404 不是"没启用"，是该版本不提供 HTTP**

v1.0 把 `/git/ 404` 判为「通道未启用」。本次深入核查后必须更正：

| 证据 | 内容 |
|---|---|
| 套件服务脚本 | `/var/packages/Git/scripts/start-stop-status` 只有 `linkBinary` / `unlinkBinary`，**不启动任何常驻进程** |
| systemd 单元 | `systemctl status pkg-Git` → `not-found` |
| 二进制清单 | `target/bin/` 仅 `git / git-shell / git-upload-pack / git-receive-pack / git-cvsserver / scalar`，**无 `git-http-backend`** |
| 资源声明 | `/var/packages/Git/conf/resource` 只声明 `indexdb` 与 `webapi`，**无 nginx location** |
| nginx 实际配置 | `/etc/nginx/sites-enabled/` 下无任何 git 相关配置 |

**结论**：DSM 7 的 Git Server 套件本质是「提供 git 二进制 + DSM 管理界面」，**代码访问走 SSH 协议，不提供 HTTP(S) 智能协议端点**。因此 `/git/xxx.git/info/refs` 永远 404，这不是配置问题，换任何参数都开不出来。

> 这条纠正很关键：v1/v2/v3 都把「群晖 Git 打不通」列为前置风险 R8/P2。现在可以关闭它，但**方式不是"开 HTTP"，而是"用 SSH"**，并且要接受「没有网页浏览界面」这个代价。

### 5.3 关键否定结论：RoboScope 不能作为并行执行内核

```python
# backend/.../task_executor.py
max_workers = 1        # 固定
```

`POST /api/v1/runs` 的 `RunCreate` 确实带 `parallel: boolean`，字段齐整：

```
required: repository_id, target_path
fields  : parallel(bool), max_retries, timeout_seconds,
          variables, advanced_config, tags_include / tags_exclude
```

但后端执行路径固定单线程池，`runs.parallel` **只写库、不参与调度**。

**这是「接口存在、能力不存在」的典型陷阱。** 若立项方案写成「调用 RoboScope 的 runs 接口实现并行」，验收时 100% 失败，且返工点在别人的代码里，我们只能 fork——这与 N13「有机整体」直接冲突。

### 5.4 pabot 定位（并行落点）

| 项 | 结论 |
|---|---|
| 能力 | 按 suite 分片的多进程 runner，RF 生态事实标准 |
| 适用 | 单机 2-4 并发（149 上就是 2-4） |
| 局限 | **不做资源互斥**——它不知道哪条用例占哪台设备的哪个口 |
| 结论 | 用它做进程级并行，**互斥必须由我们的租约表保证**（§13.2） |

### 5.5 robotdashboard 定位

包名 `robotframework-dashboard` 2.5.0，定位是 "Output processor and dashboard generator"。无执行、无用户、无租户概念。

**用法**：作为**可选只读看板**（旁路），不参与事务，坏了可重建。**不要**把它当平台，也不要让它成为唯一数据源。

3. **危险操作视觉降级**：删除按钮红色 + 行内独立位置，与"详情/编辑"区分。

### 6.9 模式 B：最值钱的一页（双列结果并置）

```
┌ hero：TEST CASE BOARD / 测试总表看板 /
│       按总表查看历史结果、详细流程与平台新执行结果。
├ 筛选：批次下拉 / 搜索 / 历史状态下拉 / 分类下拉
├ KPI 四宫格
│       总表测试项 226      全部类别，含专项项目
│       Excel历史通过 156    导入标签，非本轮通过     ← 关键限定
│       平台本轮通过 0       原始输出完整验收结果
│       尚无本轮结果 226     未沿用历史通过           ← 缺口直接显示
└ 表格：测试编号 | 测试项目·分类 | Excel历史结果 | 平台本轮结果 | 操作
```

**为什么这一页值钱**：

- "Excel历史通过 156" 下方小字写明"**导入标签，非本轮通过**"——用一行小字堵死"拿历史结论冒充当轮证据"的路。
- "尚无本轮结果 226" 直接显示缺口，而不是显示一个漂亮的通过率。
- 两列结果独立保存，互不覆盖。

**这和我们 metadata 十项定规是同一个思想**：8001 用 UI 表达，我们用 metadata 证明。两者应合并——**看板显示本轮结论，metadata 证明本轮结论**。

| 删除部分失败 | "已删除 0 个平台任务；1 个未删除：任务属于未结束的测试集批次，请先完成或取消该批次" | ✅ 强（逐项说明） |
| 高级调试 | 折叠的"开发调试（高级）" | ✅ 强（危险能力收折叠区） |

**三条比页面本身更值钱的工程原则**：

1. **删除前必须说明影响面**，且要能"部分成功 + 逐项说明原因"，不能一句"删除失败"。
2. **高级/危险能力放折叠区**，不与主流程平级。
3. **执行规则的文字就在界面上**（每例三遍、失败即停），不藏在文档里。

### 6.11 可借鉴 / 不可借鉴总表

| 对象 | 判断 | 理由 |
|---|---|---|
| 一级菜单的具体分组 | ❌ 不可借 | 13 个一级本身是失控结果，三天改四版 |

| 失败即停 | ⚠️ 有条件借 | 串行可行；并行下改为"隔离该资源、其余继续" |

| `worker.py` 执行器 | ❌ 不可用 | 单 worker 串行 + 文件锁 |
| 免密入口 | ❌ 不可用 | 与 N4 直接冲突 |

### 6.12 三类资产的复用度（定量）

| 资产类别 | 复用度 | 说明 |
|---|---:|---|
| 前端代码 | **0%** | 源码不存在；即使存在，原生 HTML+JS 无法迁移到 Vue 3 |
| 后端代码 | **0%（直接）/ 高（设计）** | Python → Java，只能按契约重写 |

### 7.4 组件契约：String → String（方案成立的技术前提）

```ts
// RobotEditor.vue:55-64
const props = defineProps<{
  content: string        // 整个 .robot 文件文本
  filePath: string
  repoId?: number        // 可选，仅用于关键词面板
}>()

const emit = defineEmits<{
  save: [content: string]
  'update:content': [content: string]
}>()
```

```ts
// FlowEditor.vue:78-96
const props = defineProps<{
  form: RobotForm        // 纯 AST 对象，不是文件
  repoId?: number
  filePath?: string
  sidecar?: RecordedFlow | null
  dirty?: boolean
}>()
```

**结论**：编辑器不与任何数据库、任何 HTTP 接口绑死。它接收文本、吐出文本。新平台只需三步：

1. 从 MariaDB 取用例文本 → 传入 `content`
2. 监听 `save` → 写回 MariaDB + 生成版本快照
3. 传入平台自己的 `projectId`（映射为 `repoId`）→ 关键词面板恢复工作

**这正是「有机整体」最好的技术保证**：它不是被挂载的外部系统，而是一个接受我们数据模型的纯组件。

### 7.7 文本往返保真契约（决定能不能用的关键）

上游在 `CLAUDE.md` 中明确写下这条契约，且被测试固定：

> `.robot` 的解析/序列化收敛在**单一纯模块** `robotTextIO.ts`。契约是 **RF-EQUIVALENT，不是字节相同**（分隔符归一为 4 空格、tab 转空格、空行丢弃），但**永不损坏**：行内注释（含控制行）、`...` 续行、转义（`\#`、`\ `）、`${}`/`@{}`/`&{}`/`%{}` 变量、`[Template]` 数据行全部存活。

**为什么这条重要**：可视化编辑最怕"编辑一次就把文件搞乱"，导致 git diff 爆炸、评审无法比对。这条契约 + 19 个往返测试，是"拿去就能用"的实质保证。同时它反向定义了存储策略——**用例必须以 `.robot` 文本为真源**（§11.2）。

**已知技术债**：`RobotForm` / `RobotStep` 类型在 `robotTextIO.ts` 与 `flowConverter.ts` 各声明一份，加字段要改两处。移植时顺势合并，**估 0.5 人日**。

## 8. 架构原则

架构原则不是口号，每一条都要能落到具体机制，并能回答"违反它会怎样"。

| # | 原则 | 落实方式 | 违反后的后果 | 对应需求 |
|---|---|---|---|---|
| P1 | **有机整体** | 一个前端工程、一个后端工程、一个数据库；编辑器是本地 npm workspace 包，不是外部服务 | 退化为"门户 + 外挂"，鉴权、租户、视觉三套体系 | N13 |
| P2 | **零外部 API 依赖** | 运行时不调用 RoboScope / robotdashboard 的任何 HTTP 接口 | 上游改版即断链，故障域不可控 | N13 |
| P3 | **单一真源** | 用例文本存 MariaDB；执行产物存文件 + 索引；**不双写 AST** | 编辑与执行看到两份数据，必然不一致 | 工程性 |
| P4 | **可替换边界** | 编辑器与平台之间只有 `content: string` 一个契约 | 换编辑器要动业务代码，等于锁死 | 长期性 |
| P5 | **许可可追溯** | 衍生代码集中在 `packages/editor`，边界清晰 | 分不清哪些是上游、哪些是我们的，合规无从下手 | 合规性 |
| P6 | **租约先于执行** | 任何执行请求必须先拿到 `resource_lease`（设备+端口粒度） | 并行把数据跑脏，结论全部作废 | N7 |
| P7 | **证据先于结论** | 产物先落盘 → sha256 → 回填索引 → 才允许出报告 | 报告无法对外，或出了也站不住 | N11/定规 |
| P8 | **失败显性化** | 部分失败必须逐项返回原因；缺口必须在 KPI 上显示 | 用户以为成功了，问题延后爆发 | 工程性 |
| P9 | **边界内自由，边界外克制** | 上游代码 `components/**`、`core/**` 保持原样，改动只进 `adapter/**` 与 `patches/**` | 升级时 diff 一片红，等于重新移植 | 长期性 |
| P10 | **单机可运维** | 三个服务、一个数据库、一个产物目录；备份与恢复能在 30 分钟内完成 | 半年后没人敢重启 | N15 |

**原则之间的优先级**：P1/P2 是路线级（不可妥协）；P3/P6/P7 是正确性级（违反即返工）；P4/P5/P9 是寿命级（决定三年后还能不能维护）；P8/P10 是体验与运维级。

|---|---|---|---|
| ① 身份域 | 认证、角色、项目成员、租户解析 | 不碰用例与执行 | 被所有域依赖 |
| ② 资产域 | 项目、用例台账、用例集、脚本文件、版本快照 | 不直接执行 | → 身份域 |
| ③ 资源域 | 设备、端口、链路、凭据、租约发放与回收 | 不解析报告 | → 身份域 |
| ④ 执行域 | 执行器池、队列、pabot 编排、日志推送、取消超时 | 不做业务判定 | → ②③ |
| ⑤ 证据域 | 解析 output.xml、归档、sha256、metadata 门禁 | 不发起执行 | → ②④ |
| ⑥ 计划域 | cron、依赖、重试、通知 | 不直接 spawn 进程 | → ③④ |
| ⑦ 集成域 | Git 回调、Actions 回调、Webhook | 不写业务表 | → ② |

**模块化约束**：单体应用但**禁止跨域直接访问对方 Repository**，必须经由 Service 接口。这条约束写进 `CONVENTIONS-backend.md`，由 ArchUnit 测试守卫。

### 9.3 关键数据流

**（1）创建/编辑用例**

```
用户在编辑器改文本 → save(content)
  → 平台校验（语法可解析 / 必填头部）
  → 写 robot_file.content + 生成 version 快照
  → 异步提交到群晖 Git（批量，非每次 save）
```

**（2）执行一次用例集**

```
执行请求（test_set_id + 设备/端口选择）
  → 身份域校验（项目成员 + 角色）
  → 资源域申请租约（设备+端口，取不到排队）
  → 执行域生成 pabot 命令 → spawn
  → 实时 tail 日志 → WebSocket 推送
  → 结束：证据域解析 output.xml → 校验 metadata → 归档 + sha256
  → 回填 run/test_result → 释放租约 → 通知
```

**（3）出对外报告**

```
选择 run → 证据域校验 metadata 十项齐全
  → 缺项：拒绝导出，返回缺失清单
  → 齐全：渲染报告 → 导出 PDF/Word → 记录导出审计
```

### 9.4 与外部系统的边界

| 外部系统 | 交互方式 | 方向 | 失败影响 |
|---|---|---|---|
| 群晖 Git（SSH） | `git push` / `git ls-remote` | 出 | 提交失败可重试，不阻塞执行 |
| GitHub | 镜像 push；Actions 回调 | 双向 | 不影响内网主流程 |
| GitHub Actions runner | Webhook 触发平台 API | 入 | 手动触发兜底 |
| DUT / 交换机 | SSH / 实网 | 出 | 用例失败，不影响平台 |
| SMTP / 企微 | 通知 | 出 | 丢弃并记录 |

**关键设计**：所有外部依赖都是**可失败的旁路**，不允许成为执行主链路的单点。

### 11.2 用例双模模型（最易返工处）

**冲突已实证**：

| 证据 | 内容 |
|---|---|
| 8001 `test_cases` | `external_id='IM-FUN-001'`、`steps_json=["在GPU01读取两张CX7的PCI身份…"]`、`raw_json` 存 Excel 原始行 |
| 8001 代码库 | 全库 grep 无 `.robot` 写入，执行靠 `collectors/` SSH 直连 |
| RoboScope 模型 | 用例 = `.robot` 文件，编辑器 = 文本 ↔ AST 双向转换 |

**结论**：8001 的 461 条是**人工用例台账**，不是自动化脚本。只做 `.robot` 则历史资产无处安放；只做台账则 RF 内核失去意义。

**推荐模型：双模共存，`.robot` 为执行真源**

```
┌─────────────────────────────────────────────────────────┐
│  用例台账（ MariaDB: test_case ）                        │
│  · 编号 / 标题 / 分类 / 优先级 / 预置条件 / 预期结果      │
│  · 来源：Excel 导入（承接 8001 的 461 条）               │
│  · 作用：需求覆盖、评审、对外报告的主键                  │
└───────────────────┬─────────────────────────────────────┘
                    │ 1:0..1 绑定
┌───────────────────▼─────────────────────────────────────┐
│  自动化脚本（ MariaDB: robot_file ）                     │
│  · content TEXT  ← 唯一真源，编辑器读写的就是这个字符串   │
│  · 版本快照 / git_commit / sha256                        │
│  · 作用：能被 robot/pabot 直接执行                       │
└─────────────────────────────────────────────────────────┘
                    │ 执行产出
┌───────────────────▼─────────────────────────────────────┐
│  output.xml + 证据（ 文件归档 + MariaDB 索引 ）           │
└─────────────────────────────────────────────────────────┘
```

**四条关键设计**：

1. **`robot_file.content` 是唯一真源**。编辑器读写它，执行时落盘为临时 `.robot` 再跑。**不在数据库另存结构化 AST**——否则必然双写不一致。
2. **台账与脚本解耦**。一条台账可以没有脚本（纯人工用例），一个脚本也可挂多条台账（数据驱动）。`case_id` 通过 `output.xml` 的 `[Tags]` 或 metadata 回链。
3. **Git 是版本层，不是运行层**。`robot_file` 每次保存生成快照，批量提交到群晖 Git / GitHub。运行时不依赖 Git 工作区，避免"改一半就跑"。
4. **metadata 沿用十项定规**，由 `robot_file` 生成时自动注入 Settings。

### 11.3 执行与证据模型

| 表 | 关键字段 | 设计要点 |
|---|---|---|
| `run` | `run_id`(UK)、`project_id`、`test_set_id`、`trigger_type`、`status`、`started_at`、`finished_at`、`operator` | `run_id` 是三方关联唯一键 |
| `test_result` | `run_id`、`case_id`、`round`、`verdict`、`duration_ms`、`failure_msg` | 「用例 × 轮次 × 结论」支撑每例三遍 |
| `keyword_result` | `run_id`、`test_result_id`、`parent_id`、`kw_name`、`status`、`depth` | 树形存，前端递归渲染 |
| `run_artifact` | `run_id`、`kind`、`path`、`sha256`、`size_bytes`、`availability` | 与 8001 的 `case_evidence` 同构 |

**大字段策略**：`<msg>` 日志不進库，落 `artifacts/<run_id>/output.xml`，库只存路径 + sha256。理由：单次运行日志可达数十 MB，进库会让备份与查询双双退化。

### 11.4 租约与幂等

```sql
CREATE TABLE resource_lease (
  resource_key VARCHAR(128) NOT NULL,   -- 例: DUT-01/mlx5_0
  job_id       CHAR(36)    NOT NULL,
  project_id   BIGINT      NOT NULL,
  acquired_at  DATETIME(3) NOT NULL,
  expires_at   DATETIME(3) NOT NULL,
  PRIMARY KEY (resource_key)            -- 天然互斥
);
CREATE UNIQUE INDEX uk_run_case ON test_result(run_id, case_id, round);
```

- `PRIMARY KEY (resource_key)` 是互斥的物理保证，不靠应用层判断。
- `expires_at` 兜底：进程崩溃后租约自动可回收（定时任务清理）。
- 取不到租约 → 入队，不失败。
- `run_id` 唯一约束保证重复提交不产生重复运行。

### 11.5 双存储一致性

| 数据 | 存储 | 理由 |
|---|---|---|
| 项目/用例/集合/租约/审计 | MariaDB | 事务、并发、多租户隔离 |
| `output.xml` / 截图 / 原始命令流 | 文件系统（按 `RUN_ID` 分目录）+ 索引入库 | RF 生态只认文件；强行入库会破坏 `robot` 复跑 |
| 看板聚合指标 | 可选 robotdashboard SQLite（只读旁路） | 不参与事务，坏了可重建 |

**一致性规则**：流程固定为「产物先落盘 → sha256 → 回填 MariaDB → 才允许出报告」。任何一步失败则任务置 `unknown`，**不自动重跑**（沿用 8001 已验证的处置原则）。

**每日对账任务**：库有记录无产物 / 有产物无记录，两类差异都要出报表。

### 11.6 索引与容量

| 表 | 预估年增 | 索引策略 |
|---|---|---|
| `test_result` | 461 用例 × 3 轮 × 每日 1 次 ≈ 50 万行/年 | `(run_id, case_id)`、`(project_id, started_at)` |
| `keyword_result` | 约 20 倍于 test_result ≈ 1,000 万行/年 | `(test_result_id)`、按 `run_id` 分区 |
| `execution_event` | 约 200 万行/年 | `(job_id, ts)`，90 天后归档 |
| `run_artifact` | 约 5 万行/年 | `(run_id, kind)` |

> 千万级 `keyword_result` 是唯一需要提前规划的表：按 `run_id` 范围分区，或只存失败步骤 + 深度前 3 层（`【推断】`，M4 需压测确认）。

### 11.7 迁移路径（8001 的 461 条）

| 阶段 | 动作 | 产出 |
|---|---|---|
| M1 | 只导入台账字段（`external_id`/`title`/`category`/`priority`/`preconditions`/`expected`/`steps_json`） | 461 条台账可见、可检索、可评审 |
| M2 | 按 `module` 聚类，人工挑选可自动化的 Top 50，用编辑器生成 `.robot` | 50 条脚本 + 台账回链 |
| M3 | 其余保持人工，纳入执行计划（人工执行记录 + 证据上传） | 覆盖率完整（自动化率如实呈现） |

> **不建议**把 `steps_json` 的自然语言自动"翻译"成 `.robot`。语义鸿沟太大，生成质量不可控，返工成本高于人工重写 50 条。

1. **用例文本是唯一真源**。`robot_file.content` 之外不允许再存"结构化用例"。
2. **编辑器改动不得越界**。`components/**` 与 `core/**` 视为上游，改动只进 `adapter/**` 与 `patches/**`。
3. **metadata 缺项即拦截**。装配 `.robot` 缺必填项直接失败；导出报告缺项直接拒绝。
4. **租约先于执行**。拿不到租约就排队，不允许"先跑起来再说"。

## 13. 关键机制设计

### 13.1 并行调度模型

| 层次 | 机制 | 说明 |
|---|---|---|
| 进程级 | pabot `--processes N` | 单机 N=2~4 |
| 资源级 | `resource_lease` 表（设备 + 端口 + 时间窗） | **互斥的核心** |
| 队列级 | 执行器池 + FIFO 队列 | 超出容量排队，不失败 |
| 幂等 | `RUN_ID` 唯一约束 | 重复提交不产生重复运行 |

**并行粒度**：suite 级（pabot 限制）。要真正跑满，**用例集切分必须保证每个 suite 落在不同设备/端口上**——由租约表在**入队前**决定，而不是跑起来再抢。

### 13.2 资源租约状态机

```
      ┌──────────┐  申请    ┌──────────┐  执行完成  ┌──────────┐
      │  FREE    │────────►│  HELD    │──────────►│ RELEASED │
      └──────────┘         └────┬─────┘           └──────────┘
           ▲                    │ 进程崩溃
           │  过期回收           ▼
           └─────────────── EXPIRED（定时清理器）
```

| 状态 | 含义 | 转移条件 |
|---|---|---|
| FREE | 无租约记录 | — |
| HELD | 已分配，执行中 | 执行域申请成功 |
| EXPIRED | 超时未释放 | `expires_at < now`，清理器介入 |
| RELEASED | 正常释放 | 执行完成或取消 |

**幂等要求**：释放操作必须幂等（重复调用不报错），否则重试会放大故障。

### 13.3 metadata 门禁

十项定规（2026-10-31 定，全项目强制）：

| 类型 | 键 | 说明 |
|---|---|---|
| 必填（6） | `CASE_ID`、`RUN_ID`、`QA_PROJECT`、`DUT`、`LINK`、`SW_BUILD` | 缺任一项即不合格 |
| 推荐（4） | `BASELINE`、`OPERATOR`、`STARTED_AT`、`CASE_KIND` | 缺项警告 |

**实现要求**：

- 键名全大写 `[A-Z0-9_]`，值 ≤ 40 字符（RF 会在每个 test 行重复渲染）。
- 写入用 `Suite Setup` → `Set Suite Metadata`；静态值由 YAML 注入 `.robot` 的 `Settings` 段。**不用 `--metadata` 命令行**（平台触发不传）。
- 校验用 `robot.api.ExecutionResult(...).suite.metadata`，**必须递归子套件**（根套件常为空）。
- `RUN_ID` 含 `/` 会炸文件名和标签，需字符白名单。

**门禁落点**（三处，缺一不可）：

1. `robot_file` 生成 `.robot` 时 → 缺项直接失败。
2. `output.xml` 入库时 → 校验失败拒绝入库。
3. 报告导出时 → 缺项拒绝导出并返回缺失清单。

### 13.4 报告解析管线

```
output.xml (RF 7.5)
   ↓ StAX/JAXB
<suite> 树 → run / test_result / keyword_result / run_artifact
   ↓
sha256 + 归档 → artifacts/<run_id>/
   ↓
metadata 校验 → 入库 or 拒绝
   ↓
索引回填 → 报告页可查
```

| 层 | 工作内容 | 估时 |
|---|---|---|
| 解析 | `<suite>`/`<test>`/`<kw>`/`<msg>`/`<status>`，`elapsedtime`、`<tag>`、`<statistics>` | 1.2 人月 |
| 存储 | 三张表 + 产物索引；大字段落文件 | 0.5 人月 |
| API | 运行列表、详情、套件树、步骤树、失败聚合、趋势 | 0.5 人月 |
| 前端 | 套件树（递归）、步骤折叠、日志着色、失败高亮、两轮对比 | 1.3 人月 |
| **合计** | | **3.5 人月** |

### 13.5 实时日志推送

| 项 | 方案 |
|---|---|
| 通道 | WebSocket，按 `run_id` 订阅 |
| 数据源 | `tail -F <run_dir>/output.xml`（RF 流式写入）+ 进程 stdout |
| 频率 | 200-500 ms 批量推送，避免逐行刷屏 |
| 断线 | 客户端带 `last_offset` 重连，服务端补发 |
| 保留 | 内存只留最近 500 行，完整日志在文件 |

### 13.6 失败分类与重试

| 类别 | 判据 | 是否重试 |
|---|---|---|
| 环境失败 | SSH 连不上、依赖库缺失、端口占用 | ✅ 自动重试（最多 2 次） |
| 用例失败 | 断言不通过、判据不满足 | ❌ 不重试，如实记录 |
| 未知 | 超时、进程被杀、解析失败 | ⚠️ 置 `unknown`，人工判定 |

**并行下的失败策略**（改 8001 的"失败即停"）：**隔离该资源，其余继续**。理由是并行时一条用例失败不应拖累其他设备的运行。

### 13.7 幂等与取消

| 场景 | 机制 |
|---|---|
| 重复提交同一 `RUN_ID` | 唯一约束拒绝，返回既有 run |
| 取消运行 | 先置 `CANCEL_REQUESTED` → 杀进程树 → 置 `CANCELLED` → 释放租约 |
| 平台重启 | 启动时扫描 `RUNNING` 状态的 job，置 `unknown` 并释放租约 |
| 通知重复 | `notification` 表按 `(run_id, channel, type)` 去重 |

## 16. 安全与权限（8001 完全没有，必须新建）

### 16.1 认证

| 方式 | 适用 | 说明 |
|---|---|---|
| 本地账号 + 密码 | 首期默认 | BCrypt 存哈希，密码策略最小长度 8 |
| 会话 | 前后端分离 | JWT（短期 access + 刷新 token），或 HttpOnly Cookie + CSRF |
| OIDC（可选） | 企业已有 IdP | 预留扩展点，不首期实现 |
| API Token | CI / 脚本调用 | 按项目签发，可撤销，scope 限定 |

**禁止**：明文密码、URL 传 token、日志打印 token。

### 16.2 授权模型（RBAC + 项目成员）

| 角色 | 权限 |
|---|---|
| 系统管理员 | 全部；管理用户与项目 |
| 项目管理员 | 本项目内的全部操作（含删除） |
| 测试工程师 | 建/改用例与用例集、发起执行、看报告 |
| 查看者（Viewer） | 只读；不能保存编辑器内容（依赖 `readonly` prop） |
| CI 机器人 | 仅触发执行 + 读结果 |

**实现要点**：权限判定在 Service 层，不在 Controller（Controller 只做参数校验）。所有查询强制带 `project_id` 条件。

### 16.3 租户隔离实现

| 层 | 措施 |
|---|---|
| 数据 | 所有业务表带 `project_id`；组合索引含 `project_id` |
| 查询 | MyBatis 拦截器自动追加 `project_id` 条件（防手写遗漏） |
| 接口 | 每个请求解析当前用户 → 校验项目成员 → 注入上下文 |
| 文件 | 产物路径按 `project_id/run_id` 分层，禁止跨项目路径拼接 |
| 测试 | 越权测试集 ≥20 条，纳入验收（§25.2） |

**红线**：任何"按 id 查详情"的接口，必须先校验该 id 属于当前用户可访问的项目。

### 16.4 凭据管理（设备密码）

8001 的 `devices` 表直接存 SSH 凭据，且无鉴权。新平台必须改：

| 项 | 方案 |
|---|---|
| 存储 | AES-GCM 加密后入库；密钥来自环境变量或 KMS，**不入库、不进 Git** |
| 展示 | 列表只显示"已配置/未配置"，不回显明文 |
| 使用 | 执行时解密到内存，注入临时 askpass，**不写磁盘** |
| 审计 | 每次"查看/修改凭据"记审计日志 |
| 轮换 | 支持批量更新，记录轮换时间 |

### 16.5 审计

| 事件 | 必记字段 |
|---|---|
| 登录/登出/失败 | 用户、IP、UA、结果、时间 |
| 用例增删改 | 用户、项目、对象 id、变更前后摘要 |
| 执行发起/取消 | 用户、run_id、参数摘要 |
| 报告导出 | 用户、run_id、格式、是否通过 metadata 校验 |
| 凭据操作 | 用户、设备 id、动作 |
| 权限变更 | 操作人、被操作人、角色变化 |

**保留**：≥180 天；只增不改；导出需二次授权。

### 16.6 安全基线（对照 8001）

| 项 | 8001 | 新平台要求 |
|---|---|---|
| 接口鉴权 | ❌ 无 | ✅ 全接口 |
| 密码存储 | 无用户体系 | BCrypt |
| 设备凭据 | 明文（`ssh_profile`） | AES-GCM + 审计 |
| SQL 注入 | 参数化（好） | 强制参数化 + 代码扫描 |
| 越权 | 无概念 | 项目级隔离 + 越权测试 |
| 文件路径穿越 | 未验证 | 产物路径白名单校验 |
| 依赖漏洞 | 未扫描 | CI 加 SCA（OWASP Dependency-Check） |
| 日志脱敏 | 无 | token/密码/密钥禁止入日志 |

## 17. 可观测性与运维

### 17.1 日志规范

| 类型 | 落点 | 保留 |
|---|---|---|
| 应用日志 | `logs/app.log`（滚动，单文件 ≤100 MB，保留 14 天） | 14 天 |
| 执行日志 | `artifacts/<run_id>/`（output.xml + stdout） | 按保留策略 |
| 审计日志 | MariaDB `audit_log` | ≥180 天 |
| 调度日志 | `logs/schedule.log` | 30 天 |

**格式**：JSON 行，必含 `ts`、`level`、`trace_id`、`user`、`module`、`msg`。`trace_id` 贯穿一次请求，执行阶段贯穿整个 `run_id`。

### 17.2 关键指标

| 指标 | 用途 | 告警阈值 |
|---|---|---|
| 队列深度 | 判断是否够并发 | > 10 持续 10 分钟 |
| 平均等待时长 | 用户体验 | > 15 分钟 |
| 执行成功率 | 平台健康 | < 90% 连续 3 次 |
| 租约冲突次数 | 并行正确性 | > 0（应为 0） |
| 磁盘使用率 | 产物增长 | > 80% |
| JVM 堆使用 | 内存 | > 85% 持续 5 分钟 |
| 数据库连接池 | 容量 | 使用率 > 90% |
| metadata 校验失败数 | 数据质量 | > 0 |

### 17.3 健康检查

```
GET /actuator/health        → 应用 + DB + 磁盘
GET /actuator/health/exec   → 执行器可用性（venv 存在、robot --version）
GET /api/v1/system/info     → 版本、构建时间、并发上限
```

**执行器健康**要单独检查：venv 路径失效（换机、迁移）是最常见的"平台活着但跑不了"。

### 17.4 备份与恢复

| 对象 | 方式 | 频率 | 恢复演练 |
|---|---|---|---|
| MariaDB | `mariadb-dump` 全量 + binlog | 每日 02:00 | 每季度一次 |
| 产物目录 | 群晖 Hyper Backup / rsync | 每日 | 每季度一次 |
| 配置 | Git 仓库（不含密钥） | 变更即提交 | — |
| 密钥 | 独立保管，**不进备份包** | — | — |

**RPO ≤ 24h，RTO ≤ 30 分钟**（单机可接受）。

### 17.5 产物保留策略

| 数据 | 保留 | 到期动作 |
|---|---|---|
| `output.xml` / log.html | 180 天 | 压缩归档，只留摘要 |
| 失败用例产物 | 365 天 | 同上 |
| 证据截图 | 180 天 | 归档 |
| `execution_event` | 90 天 | 删明细，留聚合 |
| 性能基线 | 永久 | — |

**必须有清理任务**，否则 461 用例 × 每日 × 数十 MB 会在半年内撑满磁盘。

### 17.6 升级与回滚

```
备份 DB + 产物 → 停服务 → 部署新包 → Flyway 迁移 → 健康检查 → 恢复流量
                                                        ↓ 失败
                                                   回滚包 + DB 快照
```

**约束**：Flyway 脚本只增不改；破坏性变更必须分两版（先加列，再删旧列）。

### 18.2 编辑器移植回归（最重要的一组）

| 资产 | 用法 |
|---|---|
| 19 个 `FlowEditor*.spec.ts`（2,839 行） | **移植后先跑通再改业务**，任何一个红都不许往下走 |

**判定标准**：19 个测试通过率 **100%**；50 个往返样本可执行率 **100%**。

### 18.3 并行与租约测试

| 用例 | 期望 |
|---|---|
| 同设备同端口并发 2 条 | 后一条排队，不并行 |
| 同设备不同端口并发 | 可并行 |
| 进程被 kill 后租约 | `expires_at` 到期自动回收 |
| 平台重启时有 RUNNING 任务 | 置 `unknown`，租约释放 |
| 重复提交同 RUN_ID | 返回既有 run，不新建 |
| 4 并发 vs 1 串行 | 加速比 ≥2.5x |

### 18.4 metadata 门禁测试

| 场景 | 期望 |
|---|---|
| 缺 `CASE_ID` 生成脚本 | 生成失败，报缺失项 |
| 缺 `SW_BUILD` 导报告 | 导出拒绝，返回清单 |
| `RUN_ID` 含 `/` | 生成失败（字符白名单） |
| 子套件有 metadata、根套件空 | 校验通过（必须递归） |

### 18.5 性能压测（M2 必做）

| 项 | 方法 | 通过标准 |
|---|---|---|
| 4 并发加速比 | 100 用例集，1 串行 vs 4 并发各 3 次取中位 | ≥2.5x |
| 调度开销 | 空跑基准 vs 实际调度耗时 | <5% |
| 内存峰值 | 压测期间 `free -m` 采样 | 不触发 swap |
| 大报告解析 | 10 万行 output.xml | <10 s |
| 实时推送延迟 | 日志产生到前端显示 | <2 s |

### 18.6 UAT 场景（建议 8 条）

1. 新建项目 → 导入 100 条台账 → 检索与筛选正确。
2. 用编辑器把 1 条台账写成 `.robot` → 保存 → 重新打开无损。
3. 组成用例集 → 选 2 台设备 → 并行执行 → 无租约冲突。
4. 执行中取消 → 进程被杀 → 租约释放。
5. 查看报告 → 套件树/步骤/日志正确 → 导出 PDF。
6. 故意缺 metadata → 拒绝导出并提示缺项。
7. Viewer 角色登录 → 只能看，不能改。
8. 跨项目访问他人 run → 403。

## 20. 并行与容量测算

### 20.1 并行模型（同 §13.1，此处给测算）

### 20.2 149 容量测算（3,350 MB 基线）

| 组件 | 内存占用 | 备注 |
|---|---:|---|
| Spring Boot（JVM，`-Xmx1g`） | 700 MB | |
| MariaDB | 400 MB | 小实例 |
| OS + 缓存 | 600 MB | |
| robot 进程 × 4（pabot） | 1,170 MB | 每 worker 约 290 MB |
| **合计** | **2,870 MB** | 对 3,350 MB，余量 **14%** |

**结论**：4 并发余量仅 14%，会持续触发 swap，导致执行时间抖动与看门狗误杀。

> 相比 v1.0（含 RoboScope + robotdashboard，余量同为约 14%，但那是 5 个服务），一体化方案少了两个 Python 服务，可省 300-400 MB，余量提升到约 **25%**。**但仍不足以支撑 4 并发。**

### 20.3 两种选择

| 方案 | 并发 | 内存 | 代价 |
|---|---:|---|---|
| A（推荐） | 4 | 扩至 8 GB | 一次性硬件调整 |
| B | 2 | 不动 | 4 并发需求降级为 2，UI 限制同时提交数 |

**建议 A**。理由：N7 的原始诉求是 2-4 并发，压到 2 等于需求降级；且 8 GB 后余量约 60%，可留出压测与未来增长空间。

## 28. 报告结论

### 28.1 三句话总结

1. **技术路线成立**：源码级移植编辑器 + 自研编排/报告/计划 + RF/pabot 执行，是一个能落地、能维护、能交付的架构。
2. **最大风险不在技术，在资源与纪律**：149 只有 3.35 GB（R7）、产物无清理（R15）、编辑器边界易被侵蚀（R11）。这三条都能靠制度解决，但必须现在定。
3. **群晖 Git 已通，但要接受它的边界**：只有 SSH、没有 Web 界面、没有细粒度权限。要可视化管理就上 Gitea，别在 DSM 上折腾。
