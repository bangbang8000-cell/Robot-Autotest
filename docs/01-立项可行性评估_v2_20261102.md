## 2. 结论先行

### 2.1 一句话结论

**做，而且是"一个平台"，不是"几个工具的胶水"。** 新路线成立的关键，是本次查实了一件事：RoboScope 的可视化编辑器**不是封闭黑盒**——它是一个对外只收一个字符串、只吐一个字符串的受控组件，依赖全是 MIT 开源库，许可证是 Apache-2.0。这意味着它可以被"取下来装进我们自己的程序"，而不是"在旁边挂一个 RoboScope"。

### 2.2 七条硬结论

1. **编辑器可以真集成，不是仿制。** `RobotEditor` 的对外契约是 `content: string` 进、`save(content: string)` 出，`repoId` 还是可选参数。整个编辑体验（图形流 / 结构化表单 / 代码三视图）可以整体搬进新平台，无需重写解析器。
2. **`.robot` 解析内核在前端，不在后端。** `robotTextIO.ts`（774 行）是唯一的解析/序列化真源，纯 TypeScript。**Java 后端不需要重写 RF 语法解析器**——这是本方案最大的成本节省点，也是最容易被误判为"要重写"的地方。
3. **图编辑器不是自研黑科技，是 MIT 开源库。** `@vue-flow/core` 1.48.2 + `background` + `controls` + `minimap`，MIT 许可，可商用可闭源。所谓"可视化效果"，本质是 4,233 行 `FlowEditor.vue` 对 Vue Flow 的业务编排。
4. **复用范围可以精确到行。** 以 `RobotEditor` 为根，静态依赖闭包 47 文件 / 18,231 行；裁掉调试、录制、自愈三块可选能力（8 文件 / 2,285 行）后，**核心 39 文件 / 15,946 行**；其中需改写的 api/stores/types 共 15 文件 / 2,604 行。改造比例约 16%。
5. **必须放弃 RoboScope 的后端，也放弃它的报告与计划。** 这是"有机整体"的代价：报告渲染需自研（约 3.5 人月）、计划调度需自研（约 1.5 人月），比 v1.0 的复用方案多约 4 周。**这个代价必须让评审看见，不能藏。**
6. **真正的架构风险不是编辑器，是"用例以什么为真源"。** 参考工程 8001 的 461 条用例是 Excel 导入的人工用例（自然语言步骤），RoboScope 的用例是 `.robot` 文本。两者范式不同。若不先定模型就开工，编辑器接上去会没有稳定的数据底座——这是最容易返工的地方（§5）。
7. **149 依然撑不住 4 并发。** 3350 MB 内存的结论不变。要么扩到 8 GB，要么并发压到 2。这条不因方案变更而改变。

### 3.3 参考工程 8001 的可借鉴边界（本次修正）

实查结论：**8001 与 RF 是两套执行模型**，不能混为一谈。

| 维度 | 8001 参考工程 | RF / RoboScope | 对本项目的影响 |
|---|---|---|---|
| 用例形态 | Excel 导入台账（`IM-FUN-001`、自然语言 `steps_json`） | `.robot` 文本 + AST | **必须双模共存**（§5） |
| 执行方式 | Python SSH 采集器直连 DUT | `robot`/`pabot` 子进程 | 执行内核只取 RF，**采集器逻辑可借鉴** |
| `.robot` 生成 | **无**（全库 grep 无 `.robot` 写入） | 原生 | 编辑器不能直接吃 8001 的用例数据 |
| 数据规模 | 26,459 行 Python / 59 表 / 461 用例 / 36 集合 / 12 设备 | — | 表结构可借鉴，代码需重写（Python→Java） |

**口径澄清**：N12 说"可直接借鉴参考软件代码"。但两套参考软件都是 **Python**（8001 后端、RoboScope 后端），而新平台后端是 **Java**。因此——

- **前端（Vue）**：RoboScope 的编辑器可**源码级衍生**（同语言、同框架、Apache-2.0 允许）。
- **后端（Python→Java）**：只能**借鉴设计与模型，重写实现**，不存在"复制粘贴"。工期须按重写计。

这个区分必须写进立项文件，否则工期会被严重低估。

## 4. 用例可视化编辑器专项评估（核心章节）

### 4.1 能力构成：三视图 + 查看器

`RobotEditor.vue`（2,912 行）内部提供三个编辑视图，默认打开图形流视图：

| 视图 | 实现 | 适用场景 | 规模 |
|---|---|---|---|
| **Flow（图形流）** | `FlowEditor.vue` 4,233 行 + `@vue-flow/core` | 主视图。节点式拖拽编排，支持 IF / FOR / WHILE / TRY 控制结构的嵌套分组 | 最大 |

### 4.3 组件契约：String → String

这是本方案成立的技术前提，也是本次核查最重要的单一发现。

```ts
// RobotEditor.vue:55-64
const props = defineProps<{
  content: string        // 整个 .robot 文件文本
  filePath: string
  repoId?: number        // 可选，仅用于关键词面板
}>()

const emit = defineEmits<{
  save: [content: string]
  'update:content': [content: string]
}>()
```

```ts
// FlowEditor.vue:78-96
const props = defineProps<{
  form: RobotForm        // 纯 AST 对象，不是文件
  repoId?: number
  filePath?: string
  sidecar?: RecordedFlow | null
  dirty?: boolean
}>()
```

**结论**：编辑器不与任何数据库、任何 HTTP 接口绑死。它接收文本、吐出文本。新平台只需：

1. 从 MariaDB 取用例文本 → 传入 `content`
2. 监听 `save` → 写回 MariaDB + 生成版本快照
3. 传入平台自己的 `projectId`（映射为 `repoId`）→ 关键词面板恢复工作

**这正是"有机整体"最好的技术保证**：它不是被挂载的外部系统，而是一个接受我们数据模型的纯组件。

### 4.6 文本往返保真契约（决定能不能用的关键）

上游在 `CLAUDE.md` 中明确写下了这条契约，且被测试固定：

> `.robot` 的解析/序列化收敛在**单一纯模块** `robotTextIO.ts`。契约是 **RF-EQUIVALENT，不是字节相同**（分隔符归一为 4 空格、tab 转空格、空行丢弃），但**永不损坏**：行内注释（含控制行）、`...` 续行、转义（`\#`、`\ `）、`${}`/`@{}`/`&{}`/`%{}` 变量、`[Template]` 数据行全部存活。

**为什么这条重要**：可视化编辑最怕"编辑一次就把文件搞乱"，导致 git diff 爆炸、评审无法比对。这条契约 + 19 个往返测试，是"拿去就能用"的实质保证。同时它反向定义了新平台的存储策略——**用例必须以 `.robot` 文本为真源**（§5.2）。

**已知技术债**：`RobotForm` / `RobotStep` 类型在 `robotTextIO.ts` 与 `flowConverter.ts` 各声明一份，新增字段要两边都改。移植时应顺势合并，估 0.5 人日。

### 4.9 上游同步策略

衍生代码最大的长期风险是"上游更新了，我们跟不动"。三种策略：

| 策略 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A 一次性快照 | 复制后断链，永不同步 | 简单、无冲突 | 上游修 bug 拿不到 | 仅适合"编辑器已冻结" |
| **B 补丁集（推荐）** | 保留上游 tag 为基线，本地改动以 patch 形式维护，升级时 rebase | 改动可审计、升级可控 | 需维护 patch 队列 | **推荐** |
| C 持续 merge | 直接在上游分支上开发 | 升级最顺 | 冲突频发，易失控 | 不推荐 |

**推荐 B 的具体落地**：

```
packages/editor/
├── UPSTREAM.md          # 基线：viadee/roboscope v0.16.1，commit 记录
├── patches/             # 0001-adapter-api.patch ... 按主题拆分
├── scripts/apply.sh     # 应用补丁 / 回滚 / 升级检查
└── src/                 # 上游源码 + 已应用的改动
```

> 这套做法在本项目已有实践基础：149 上 `~/roboscope-src` 就是用「源码树 + 4 个补丁 + `apply-our-patches.sh`」维护的，机制已验证可行，可直接复用经验。

**升级节奏建议**：不追每个 minor；只在出现**安全修复**或**编辑器相关 bug 修复**时评估升级，每次升级预算 2-3 人日。

## 5. 用例数据模型决策（最易返工处）

### 5.1 冲突已实证

| 证据 | 内容 |
|---|---|
| 8001 `test_cases` 表结构 | `external_id='IM-FUN-001'`、`steps_json=["在GPU01读取两张CX7的PCI身份…"]`、`raw_json` 存 Excel 原始行 |
| 8001 代码库 | 全库 grep 无 `.robot` 写入，执行靠 `collectors/` SSH 直连 |
| RoboScope 模型 | 用例 = `.robot` 文件，编辑器 = 文本 ↔ AST 双向转换 |

**结论**：8001 的 461 条用例是**人工用例台账**（需求覆盖、执行记录、证据），不是自动化脚本。新平台若只做 `.robot`，则 461 条历史资产无处安放；若只做台账，则 RF 内核失去意义。

### 5.2 推荐模型：双模共存，`.robot` 为执行真源

```
┌─────────────────────────────────────────────────────────┐
│  用例台账（ MariaDB: test_case ）                        │
│  · 编号 / 标题 / 分类 / 优先级 / 预置条件 / 预期结果      │
│  · 来源：Excel 导入（承接 8001 的 461 条）               │
│  · 作用：需求覆盖、评审、对外报告的主键                  │
└───────────────────┬─────────────────────────────────────┘
                    │ 1:0..1 绑定
┌───────────────────▼─────────────────────────────────────┐
│  自动化脚本（ MariaDB: robot_file ）                     │
│  · content TEXT  ← 唯一真源，编辑器读写的就是这个字符串   │
│  · 版本快照 / git_commit / sha256                        │
│  · 作用：能被 robot/pabot 直接执行                       │
└─────────────────────────────────────────────────────────┘
                    │ 执行产出
┌───────────────────▼─────────────────────────────────────┐
│  output.xml + 证据（ 文件归档 + MariaDB 索引 ）           │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：

1. **`robot_file.content` 是唯一真源**，编辑器读写它，执行时落盘为临时 `.robot` 再跑。不在数据库里另存一份"结构化 AST"——否则必然双写不一致。
2. **台账与脚本解耦**：一条台账可以没有脚本（纯人工用例），一个脚本也可以挂多条台账（数据驱动）。`case_id` 通过 `output.xml` 的 `[Tags]` 或 metadata 回链。
3. **Git 是版本层，不是运行层**：`robot_file` 的每次保存生成快照，批量提交到群晖 Git / GitHub。运行时不依赖 Git 工作区，避免"改一半就跑"的混乱。
4. **metadata 沿用十项定规**：`CASE_ID`/`RUN_ID`/`QA_PROJECT`/`DUT`/`LINK`/`SW_BUILD`/`BASELINE`/`OPERATOR`/`STARTED_AT`/`CASE_KIND`，由 `robot_file` 生成时自动注入 Settings。

### 5.3 迁移路径（8001 的 461 条怎么办）

| 阶段 | 动作 | 产出 |
|---|---|---|
| M1 | 只导入台账字段（`external_id`/`title`/`category`/`priority`/`preconditions`/`expected`/`steps_json`） | 461 条台账可见、可检索、可评审 |
| M2 | 按 `module` 聚类，人工挑选可自动化的 Top 50，用编辑器生成 `.robot` | 50 条自动化脚本 + 台账回链 |
| M3 | 其余保持人工，纳入执行计划（人工执行记录 + 证据上传） | 覆盖率完整（自动化率如实呈现） |

> **不建议**把 `steps_json` 的自然语言步骤自动"翻译"成 `.robot`。语义鸿沟太大，生成质量不可控，返工成本高于人工重写 50 条。

### 7.3 与 pabot 的配合（并行落点）

```

        → pabot --processes N --outputdir <run_dir> <suite...>

        → 结束后解析 output.xml，释放租约
```

**并行粒度**：pabot 按 suite 级并行。要真正跑满，用例集切分必须保证每个 suite 落在不同设备/端口上——这由租约表在**入队前**决定，而不是跑起来再抢。这是 v1.0 已论证的结论，方案变更后依然成立。

## 8. 并行与容量（结论沿用）

### 8.1 并行模型

| 层次 | 机制 | 说明 |
|---|---|---|
| 进程级 | pabot `--processes N` | 单机 N=2~4 |
| 资源级 | `resource_lease` 表（设备 + 端口 + 时间窗） | **互斥的核心**，防止两条用例打同一端口 |
| 队列级 | 执行器池 + FIFO 队列 | 超出容量排队，不失败 |
| 幂等 | `RUN_ID` 唯一约束 | 重复提交不产生重复运行 |

### 8.2 149 容量测算（不变）

| 组件 | 内存占用（估） |
|---|---:|
| Spring Boot（JVM，-Xmx1g） | 700 MB |
| MariaDB | 400 MB |
| OS + 缓存 | 600 MB |
| robot 进程 × 4（pabot） | 1,170 MB |
| **合计** | **2,870 MB / 3,350 MB（余量 14%）** |

**结论不变**：4 并发余量仅 14%，风险偏高。建议扩至 8 GB；若不扩，并发上限设 2，并在 UI 上限制同时提交数。

> 方案变更后少部署 RoboScope + robotdashboard 两个 Python 服务，可省约 300-400 MB，余量从 14% 提升到约 25%。这是"一体化"的意外收益，但仍不足以支撑 4 并发。

### 11.2 关键路径与并行建议

```
M0 ──► M1(台账) ──► M2(编辑器) ──► M4(报告)
         │                │              ▲
         └──► M3(执行并行) ──────────────┘
                          └──► M5(计划) ──► M6
```

- **M2 与 M3 可并行**（不同人、不同技术栈：Vue 移植 vs Java 调度），这是 30 周能压缩的关键。
- **M4 依赖 M3 的产物格式**，不能提前。
- **建议单设 2 周 spike**：在 M2 结束后立即用真实用例验证"编辑器产出的 `.robot` 能被 pabot 正确执行"，把 R1/R3 提前暴露。
