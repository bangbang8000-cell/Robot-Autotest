## 1. 版本划分的三条原则

### 1.1 按「用户能拿到什么」切，不按技术模块切

技术模块切出来的版本没人能验收。「IAM 完成」「EXE 完成」是开发语言，不是交付语言。所以每一版都必须能回答一句：**上一版做不到、这一版能做到的事是什么。**

| 反面例子（不采用） | 本方案 |
|---|---|
| 「v0.2 完成领域层」 | 「v0.2 能登录、能录设备、能导 461 条用例、能按技术域筛」 |
| 「v0.3 完成前端组件」 | 「v0.3 用例能在平台里改，改完还能跑」 |
| 「v0.4 完成执行引擎」 | 「v0.4 点一下就能跑，4 条同时跑不打架」 |

### 1.2 一个版本 = 一个门禁单元

版本边界与 G 门**一一对应**，不额外发明验收口径。版本验收就是附录 B 的检查单，不多一条、不少一条。

好处很直接：**不存在「版本发了但门禁没过」这种状态**。要么两者同时成立，要么这版不算发。

### 1.3 每个版本都必须「能力不倒退」

第 N 版交付的能力，在第 N+1 版必须是回归基线的一部分。这条比新增功能更重要——AI 开发最容易出的问题是「改 B 弄坏 A」，而 A 没人测。

对应的硬约束写在 §4「能力阶梯」：每上一级台阶，就把上一级的证据固化成回归用例，跑不过不许发版。

## 3. 版本号与发布物规则

### 3.1 版本号语义

```
v0 . 3 . 2
│    │   └── 快照序号：同一主线内的内部构建，不进交付清单
│    └────── 主线号：与 G 门一一对应（0.1→G1 ... 1.0→G7/迭代评审）
└─────────── 0 = 建设期，1 = 可对外
```

| 版本段 | 含义 | 对外可见 | 发布条件 |
|---|---|---|---|
| `v0.x.y` | 建设期内部快照 | ❌ 不对外 | CI 全绿即可出快照，随时 |
| `v0.x`（无 y） | 主线版本达成 | ❌ 仅内部评审 | **对应 G 门通过** |
| `v1.0.0` | 首个可交付版本 | ✅ 对外 | G7 通过 + 试点迭代评审结论闭环 |
| `v1.x.y` | 运营期功能包 | ✅ 对外 | 季度发布窗口 + 发布检查单 |

### 3.2 发布物形态（每版必须齐五样）

| # | 发布物 | 形态 | 缺失后果 |
|---|---|---|---|
| 1 | 可运行包 | 后端 jar + 前端 dist + Flyway 迁移脚本 | 无法部署 |
| 2 | 数据库迁移 | `V<版本>__*.sql`，单向、可回滚 | 升级即事故 |
| 3 | 版本说明 | `CHANGELOG` 段落：新增 / 变更 / 已知问题 | 使用方不知道变了什么 |
| 4 | 验收证据包 | 对应 `TEST-PLAN.md` 的证据清单实际产物 | 门禁无法核验 |
| 5 | 回滚说明 | 回滚到上一版的命令与前提 | 出事只能硬扛 |

### 3.3 版本节奏（不排日期，排触发条件）

| 事件 | 触发条件 | 谁批准 |
|---|---|---|
| 出内部快照 `v0.x.y` | CI 全绿 + 该任务包 `待验` | AI 自行（不对外） |
| 主线版本达成 `v0.x` | 门禁检查单全绿 | 大师（G2/G5/G7）、silence（G1/G3/G4/G6） |
| 对外发布 `v1.0.0` | G7 通过 + 迭代评审闭环 | 大师 |
| 运营期功能包 | 待办池排序前 N 项 + 发布检查单 | 大师 |

**明确不做的事**：不承诺「每两周一版」。AI 推进下按批次快、按门禁慢——**快在实现，慢在验证**，这个不对称是故意的。

## 4. 能力阶梯（每版必须守住的既有能力）

> 这张表是**回归测试的基线来源**。第 N 版交付的每一行，都要变成后续版本每次发版必跑的一组用例。跑不过，不许发。

| 版本 | 新增能力（必须一次做对） | 从此不可倒退的红线 | 固化成的回归集 |
|---|---|---|---|
| v0.1 | 一键拉起、分层可拦、迁移可回滚、**环境自检可复现** | `make bootstrap` 一把过；`scripts/env-probes.sh` 八探针绿 | `REG-BOOT`（构建 + ArchUnit + 环境探针） |
| v0.2 | 登录、RBAC、租户隔离、台账、461 导入 | **跨项目越权 0 例**；导入条数/字段零丢失 | `REG-AUTH`（越权 20 条）、`REG-IMPORT`（对账） |
| v0.3 | 三视图编辑、往返保真、版本快照 | **50 样本往返后可执行率 100%**；只读拦截 100% | `REG-ROUNDTRIP`（50 样本） |
| v0.4 | 队列、租约、pabot、实时日志、取消 | **同设备同端口冲突 0 次**；取消后进程真死 | `REG-LEASE`（并发抢锁）、`REG-CANCEL` |
| v0.5 | 解析、双列并置、导出、保留策略 | **metadata 齐全率 100%**；历史不冒充当轮 | `REG-META`（十项校验）、`REG-EXPORT` |
| v0.6 | cron、依赖、CI 触发、回写 | 定时触发成功率 100%（连续 7 天） | `REG-SCHEDULE` |
| v1.0 | 权限矩阵、审计、回滚、运维手册 | 回滚 RTO ≤30 分钟；关键写操作 100% 留痕 | `REG-FULL`（全量回归 + UAT 8 条） |

**执行规则**：`REG-*` 全部脚本化，进 CI 的 `regression` job。每版发布前必须全绿；日常 PR 只跑与本包相关的子集。

## 5. 版本间的兼容性策略

### 5.1 四条不可破坏的契约

| 契约 | 冻结时点 | 之后只能怎么改 | 破坏的代价 |
|---|---|---|---|
| **`.robot` 文件内容格式** | v0.3（G3） | 只允许新增 Settings 行；语义不变 | 往返保真失效，历史用例全部要人眼复核 |
| **产物目录结构**（`artifacts/<run_id>/`） | v0.4（G4） | 只允许新增文件类型；路径不改 | 报告与清理任务同时崩 |
| **`output.xml` 解析契约** | v0.5（G5） | 只允许扩字段 | 历史报告无法回看 |
| **CI 回调接口**（`/api/ci/trigger`） | v0.6（G6） | 只允许加可选参数 | 外部流水线断裂 |

### 5.2 数据库变更规则

| 类型 | 允许时点 | 做法 | 例 |
|---|---|---|---|
| 加表 | 任一新版本 | Flyway `V<ver>__add_*.sql` | v0.4 加 `execution_queue` |
| 加列（可空或有默认值） | 任一版本 | 同上，旧代码不受影响 | v0.5 加 `run.export_count` |
| 加列（非空无默认） | ❌ 禁止一步到位 | 三步：加可空列 → 双写 → 回填后加约束 | — |
| 改列类型/改名 | 需 ADR | 新增列 + 双写 + 切换读 + 删旧列，跨两个版本 | — |
| 删表/删列 | 需 ADR + 至少隔一个版本 | 先标 `deprecated` 注释，下一版删 | — |

**底线**：**任何一版的迁移都必须能在上一版的库上直接跑通**，且 `flyway undo` 或手写 down 脚本可用。做不到就不许进这一版。

### 5.3 接口变更规则

- `v0.x` 期间接口可改，但**改动必须当次写进 `CONVENTIONS-backend.md`**，不允许「代码改了文档没改」。
- 一旦被外部调用方接入（v0.6 的 CI 回调是第一例），接口即冻结，破坏性变更要走版本化路径（`/api/v2/...`）。
- 前端只调平台自己的接口，**不直连任何外部服务**（N13 硬约束，v0.1 起 CI 扫描）。

## 6. 六份产物怎么用

### 6.1 分工

> 「环节」列对应 `docs/process/版本开发流程.md` §2 的七道编号。

| 产物 | 环节 | 回答 | 主要读者 | 什么时候翻 |
|---|---|---|---|---|
| `00-RESEARCH.md` | ① | **用户实际怎么干、现有系统能到哪、哪些是猜的** | AI（起草）、技术负责人 | 版本启动第一件事，先于任何结论 |

| `PRD.md` | ③ | **要什么、给谁、凭什么算做到了** | 大师（决策）、使用方（预期） | 版本启动前定范围；验收时对标准 |
| `DEV-PLAN.md` | ④ | **怎么做、先做哪一步、怎么算这一步做完** | AI（执行）、silence（评审） | 每个任务包认领前 |
| `TEST-PLAN.md` | ⑤ | **怎么验、验到什么程度算够、证据长什么样** | AI（写用例）、门禁裁决人 | 任务包开发前先写用例；发版前执行 |
| `05-TEST-REPORT.md` | ⑥ | **实际过没过、证据在哪、留了什么坑** | 门禁裁决人、下一版 | 测试后立即产出；**缺它版本不算完成** |

⑦ 文档回写不新增文件：把实测结果写回上述五份（含评估报告被推翻的假设、PRD 验收状态、开发计划偏差、测试计划差异）。

### 6.2 三份核心文档的锚点是同一个编号

```
PRD: FR-v0.4-03  「4 条用例集并发执行，租约互斥」
  ├─► DEV-PLAN: 说明由 EXE-02 实现，验收命令 `mvn test -Dtest=LeaseConcurrencyIT`
  └─► TEST-PLAN: 用例 TC-v0.4-011 ~ 018，证据 `docs/evidence/v0.4/lease-report.md`
```

**规则**：PRD 里每一条 `FR-*` 必须能在 DEV-PLAN 找到实现任务包、在 TEST-PLAN 找到验证用例。**三处缺一，这条需求不许进版本**。这条检查在版本启动评审时做一次。

### 6.3 编号规则

| 对象 | 格式 | 例 |
|---|---|---|
| 功能需求 | `FR-<版本>-<序号>` | `FR-v0.2-07` |
| 非功能需求 | `NFR-<版本>-<序号>` | `NFR-v0.4-02` |

## 8. 版本规划怎么改

| 变更 | 级别 | 谁批 | 要做什么 |
|---|---|---|---|
| 版本内任务包顺序调整 | L1 | AI 自决 | 改 `WBS-STATUS.md` 的下一步，版本表不动 |
| 某任务包在版本间挪动 | L2 | silence + 学徒 | 改本文 §2 与两份受影响版本的 DEV-PLAN |
| 版本合并/拆分/增减 | **L3** | **大师（CCB）** | 升本文版本号 + ADR + 重算体量 |
| KPI 或门禁检查项下调 | **禁止** | — | 不在可变更范围内（规划 §1.2 规矩 6） |

**版本重排的理由必须写清楚是「发现依赖错了」还是「范围变了」**。前者是纠错，正常；后者是蔓延，要走 CCB 砍功能。
