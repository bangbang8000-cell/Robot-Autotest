## 3. 典型场景

**S1 存量 pytest 工程接入**
工程师把 `tests/` 目录（含 `conftest.py`、fixture、参数化）打成 zip 上传 → 平台预检给出「38 条可执行 / 2 条缺依赖 `pytest-mock` / 1 条路径写死」→ 工程师装依赖或改用例 → 项目默认内核设为 pytest → 选中设备执行 → 结果落 `test_result`，`external_id` 保留 nodeid → 执行报告可下钻到失败断言。

**S2 同一项目混用两种内核**
项目默认 RF，其中「性能回归」用例集设为 pytest；工程师一次选 3 个用例集发起 → 平台按用例集拆成 2 个 run（RF / pytest 各一），共享同一设备租约 → 两个执行报告分别呈现，统一进入「本次执行」视图。

**S3 对外交付**
项目经理选最近 5 次 run → 生成测试报告（模板 `EXTERNAL`）→ 平台冻结快照（剔除 IP/命令/账号）→ 导出 PDF，页眉含版本号与冻结时间 → 30 天后源 run 被保留策略清理，报告仍可打开（快照自包含）。

**S4 跨项目复用**
平台管理员把「PFC 无损基线」用例集设为 `PUBLIC` → A、B 两个项目引用（只读）→ A 项目需要改造，另存为项目副本 → 平台库升级后，B 项目看到「有新版本」提示，A 项目的副本不受影响。

**S5 组织与越权**
新同事加入「网络测试组」→ 组已授权 3 个项目（member 角色）→ 登录后可切换这 3 个项目 → 在未授权的第 4 个项目 URL 直接访问 → 403 且不泄露存在性 → 管理员把他的组授权改为 viewer，下一次请求立即生效。

**S6 AI 辅助**
工程师在失败 run 页面打开右侧面板 → 面板已带当前项目/run/失败用例上下文（IP 已打码）→ 让智能体分析失败原因 → 智能体给出「fixture 未清理导致端口占用」+ 补丁建议 → 工程师点「发起重跑」需二次确认且校验执行权限 → 动作写入审计。
