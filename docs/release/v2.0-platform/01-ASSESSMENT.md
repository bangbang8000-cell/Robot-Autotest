## 2. 逐条评估

### R1 执行报告 / 测试报告分开管理与渲染

**现状差距（证据）**
- 无 `report` 实体表，报告是 run 的只读派生（`ReportRepositoryJdbc:48-50`）。
- 只有一套页面与一套导出（PDF/DOCX，`ExportFormat:15-17`）。
- 无法回答：这份对外报告对应哪几次 run、何时冻结、源数据重跑后是否变化。

**结论：接受。** 但必须先把两种东西的**生命周期**定清楚，否则会做成「同一份报告的两种皮肤」。

| 维度 | 执行报告（内部） | 测试报告（对外） |
|---|---|---|
| 数据形态 | run 的实时派生视图，不落库 | 实体 + 冻结快照，落库 |
| 引用关系 | 1 run ↔ 1 报告 | 1 测试报告 ↔ N run（聚合） |
| 可变性 | 随 run 变化 | 冻结后不可变，只能出新版本 |
| 受众 | 测试工程师 / 开发 | 项目经理 / 客户 / 验收方 |
| 内容 | 命令、原始输出、关键字树、产物、重试 | 结论、通过率、覆盖、趋势、证据引用、免责声明 |
| 导出 | 原始产物直下 | PDF/DOCX/HTML + 水印 + 版本号 |

**隐含要求（不做就会返工）**
1. **快照必须自包含**：冻结时把渲染所需数据物化成 JSON + HTML 制品，不能冻结后还去查 `test_result`（源 run 可能被保留策略清掉）。
2. **必须记录 run 集合与各自的结果摘要**，否则无法解释「通过率 92% 是怎么算的」。
3. **必须有字段白名单**，对外报告默认剔除 IP、账号、命令原文、内网路径。
4. **历史数据策略**：老 run 不自动生成测试报告（避免批量伪造冻结时间），只提供「按 run 生成」入口。

**补充的关联/潜在需求**
- P-R1-1 报告模板与品牌（页眉、水印、免责声明、多语言）→ 本版做最小模板（`DEFAULT` / `EXTERNAL`）。
- P-R1-2 冻结后的作废与重出（revoke + 新版本，不修改旧版）→ 本版做「作废」状态。
- P-R1-3 分享链接有效期与水印溯源 → 本版做「登录可见」，匿名分享延后。
- P-R1-4 报告保留策略与归档存储 → 复用 `retention_policy`，本版只加「测试报告也受策略约束」。

**关键风险**：把「测试报告」做成可自由编辑的富文本 → 无法保证与 run 的一致性与可审计性。**不做自由编辑**，只做「选择 run + 选模板 + 生成」。

### R2 菜单系统重新评估与优化 + 系统设置 + 关于 + 版本迭代

**现状差距（证据）**
- 6 个一级项，四套分类口径混装（`navigation.ts:49-142`）。
- 权限只有 `adminOnly` 两档（`:206-220`），无项目角色维度。
- 顶栏无项目选择器（`App.vue:173-266`），切换散落在各页。
- 无设置/关于/版本页，无命令面板。

**结论：接受。** 但重排顺序不是重点，**先定信息架构（IA）规则**再动代码。

**建议 IA（6 个一级项，最多 2 层）**

| 一级 | 子项 | 归属理由 |
|---|---|---|
| 工作台 | 总览、我的待办/最近 | 以「人」为中心，不绑资源类型 |
| 资产 | 设备、链路、凭据、环境、平台资产池 | 资源域统一 |
| 用例 | 用例库、用例集、场景、文件工作区、导入 | 内容域统一（场景从执行域上移） |
| 执行 | 运行、计划、执行报告 | 过程域统一 |
| 报告 | 测试报告、模板、分享 | 结果域统一，与执行报告分家 |
| 管理 | 项目与成员、用户与用户组、系统设置、审计、关于、版本迭代 | 管理域下沉，非管理员隐藏 |

> 6 个一级项是上限：再合并会牺牲可发现性，再拆分会让常用项落到二级。

**隐含要求**
1. **菜单必须由「能力」驱动**，不是 `adminOnly` 布尔：`nav.permission = { resource, action }`，由后端 `PermissionMatrix` 判定。
2. **项目选择器上移到顶栏**，切换后当前页在「跨项目页」保持，在「项目页」跳到该项目同名页或总览。
3. **设置项必须分级**：平台级（端口、并发、保留策略、AI 开关）与项目级（默认内核、默认超时、标签集）分开，不能混在一个表单里。
4. **关于页必须可机检**：版本号、构建时间、commit、依赖版本、许可证来自构建产物，不允许手写。
5. **版本迭代页读 CHANGELOG 文件**，不读数据库，避免「版本历史」被运行时改掉。

**补充的关联/潜在需求**
- P-R2-1 命令面板（Cmd/Ctrl+K）：搜索菜单、项目、用例、run。
- P-R2-2 菜单收藏与最近访问（localStorage 即可，不落库）。
- P-R2-3 菜单项与路由的 i18n 键一一对应，禁止硬编码中文（沿用 UX-03）。
- P-R2-4 设置变更审计（谁在什么时候把并发从 4 改成 8）。
- P-R2-5 「关于」页承载环境自检入口（DB/执行器/内核/AI CLI 四行状态）。

### R3 双内核（pytest + Robot Framework），按项目/用例切换

**现状差距（证据）**
- 全仓 `pytest` 零命中。
- 内核细节渗在 `PabotCommandBuilder:42-73`（命令）、`PabotOrchestrator:41-90`（进程与判成功）、`RunTimeoutMonitor:44`（超时）、报告解析（`output.xml`）。
- 结果模型 `test_result` 无 `kernel` / `external_id` 字段。

**结论：接受，且是本版最高优先级。** 但要把「双内核」拆成三个独立问题，否则一定做成两套执行域：

1. **内核契约（SPI）**：`probe(env)` / `collect(source)` / `buildCommand(ctx)` / `parse(artifacts)` / `classifyFailure(exit, logs)`。
2. **结果归一**：所有内核产出同一种 `NormalizedRun`（suite 树 + case 列表 + 状态 + 时长 + 消息 + 附件），再落 `test_result`。
3. **选择与编排**：选择粒度、并发、租约、超时、取消、重试全部在平台层，内核不感知。

**选择粒度（建议四级，后者覆盖前者）**

| 层级 | 存储位置 | 说明 |
|---|---|---|
| 系统默认 | `system_setting` | 新项目默认内核 |
| 项目默认 | `project_setting` | 本项目大多数用例用什么 |
| 用例集/场景 | `test_set.kernel` | 一套 pytest 用例集不会被 RF 执行 |
| 单用例 | `test_case.kernel` | 例外覆盖，需在 UI 显式标注「已覆盖」 |

**隐含要求**
1. **一个 run 只能有一个内核**。混跑 = 两个 run 或一个「编排计划」，否则结果语义无法解释。
2. **pytest 用例标识用 nodeid**（`tests/test_a.py::TestX::test_y`），RF 用 `suite.test` 长名；两者都存 `external_id`，重命名后靠 `case_source_item` 映射回平台用例。
3. **pytest 结果主通道 `--json-report`，兜底 `--junitxml`**；插件缺失时自动降级并在 run 上标注 `degraded=true`。
4. **参数化用例要展开**（pytest 一个函数 N 组参数 = N 条 test_result），否则通过率失真。
5. **超时/取消必须真杀进程树**（pytest 会 spawn 子进程，现有 `destroyForcibly` 只杀直接子进程）。
6. **历史 run 的内核归属不可变**：`run.kernel` 写入即冻结，切项目默认不影响历史。

**补充的关联/潜在需求**
- P-R3-1 内核能力矩阵（是否支持参数化、fixture、标签筛选、分片、dryrun）→ 本版做静态矩阵，UI 据此禁用不支持的选项。
- P-R3-2 执行环境镜像化（保证双内核可复现）→ 延后，本版只记录 `python_version` / 包清单哈希。
- P-R3-3 用例级 dryrun 预检（RF `--dryrun` / pytest `--collect-only`）→ 本版做到「导入预检」里，执行前不做。
- P-R3-4 失败分类（断言失败 / 环境错误 / 用例错误 / 超时）→ 本版先做四类粗分，供测试报告统计。

### R4 设备/用例/项目解耦 + 原生用例集合导入

**现状差距（证据）**
- 资产已有平台共享（`project_asset`，V7_3），但 `test_case.project_id` / `test_set.project_id` / `run.project_id` 仍在。
- `test_case` 不持 `device_id`（优点，但无断言守护）。
- 导入只有 Excel preview/commit（`CaseImportService:33`），无目录/zip；RF 文件只有单文件上传（`FileController:25,64`）。

**结论：接受，分两步。**
- **第一步（本版）**：解耦 + 导入 + 预检 + 受控执行。
- **第二步（延后）**：AI 自动适配补丁（生成 diff 建议，人工确认后才写入）——本版只做「建议文本」，不做自动改写。

**解耦的准确含义（避免过度设计）**
- 「设备与用例解耦」= 用例不携带设备身份，执行时通过「计划/场景/运行时选择」绑定设备。**本版加 schema 断言 + 执行时必须显式给目标设备或标签选择器。**
- 「用例与项目解耦」≠ 用例全局共享。**用例仍归属项目**（`project_id` 保留），但支持「平台用例库 → 分配到项目」的引用模式（复用 `project_asset` 的思路，新增 `case_source` 的 `visibility=PUBLIC/PROJECT`）。
- 真正的目标：**同一条用例换项目不用复制**，且「平台库更新 → 项目内可见新版本」（只读引用 + 可覆盖副本）。

**导入安检（缺一项就等于开后门）**

| 检查 | 判据 | 不通过 |
|---|---|---|
| 路径穿越 | 任何条目含 `..` 或绝对路径 | 整包拒绝 |
| 符号链接 | zip 内 symlink 条目 | 整包拒绝 |
| 体积/数量 | ≤ 200 MB、≤ 2000 文件、单文件 ≤ 20 MB | 整包拒绝 |
| 可执行文件 | `.so/.dll/.exe/.bat/.sh`（除声明的 fixture 脚本） | 默认拒绝，可白名单 |
| 依赖 | `pytest --collect-only` / `robot --dryrun` 在隔离 venv 内 | 允许导入，标 `blocked_reason` |
| 硬编码敏感信息 | 正则扫 IP/密码/token | 允许导入，报告里列出 |
| 许可证 | 来源必填（URL/负责人/许可证） | 必填，否则不可导入 |

**补充的关联/潜在需求**
- P-R4-1 导入源登记（来源、版本、校验和、许可证）→ 本版必做。
- P-R4-2 重导入 diff 与三方冲突（平台改 / 源改 / 都改）→ 本版做「只读源 + 项目副本」两态，冲突提示人工处理。
- P-R4-3 导入用例的敏感信息扫描 → 本版做正则级，不做语义级。
- P-R4-4 用例配额（每项目用例数/存储）→ 延后。
- P-R4-5 资产分配审批流（申请-审批-回收）→ 延后（当前是管理员直接分配）。

### R5 项目组织形式（组 / 公用 / 项目内 / 超管）

**现状差距（证据）**
- 无 `user_group` / `group_member` / `project_group`；角色全局 + 项目成员两层（`AccessControlService:44-72`）。
- 项目切换纯前端 localStorage（`stores/auth.ts:17,95-99`），超管无跨项目聚合视图。
- 无项目模板；「测试场景」无实体（用例集 `test_set` 只是平铺集合）。

**结论：接受，但只做「能解释清楚」的部分。**

| 子需求 | 结论 | 理由 |
|---|---|---|
| 用户组（组含多人） | 接受 | 批量授权的最小单元 |
| 一组可含多项目 | 接受 | `project_group` 多对多 |
| 项目内用户组与用户 | 接受 | 组授权 + 个人授权叠加取高 |
| 公用资产/用例/场景 | 接受（复用 `project_asset` 思路） | 避免每个项目复制一份 |
| 超管全局视图 | 接受 | 已有 admin 判定，缺聚合接口与页面 |
| 租户/多组织（SaaS） | **不做** | 当前单实例自用，`org_id` 已有扩展位，不实现 |

**有效角色算法（必须一次定死，否则越权）**

```
effective_role(user, project) =
  admin（全局）                     → OWNER(全部)
  project_member.member_role        → 直接授权，最高
  max(project_group 中该用户所在组的 group_role)  → 间接授权
  global role（role/user_role）      → 兜底
```

- 优先级：**admin > 直接成员 > 组授权（取最高）> 全局角色**。
- 移除组成员必须**立即失效**（不缓存，或缓存带版本号）。
- `TenantGuard` 元测试必须覆盖 `user_group` / `group_member` / `project_group` / `test_scene` / `test_report` / `case_source` 六张新表。

**补充的关联/潜在需求**
- P-R5-1 组织变更审计（建组、授权、移除成员）→ 本版必做。
- P-R5-2 项目模板（新建项目带默认设置/用例集/场景/标签）→ 本版做最小模板（3 个开关）。
- P-R5-3 组织级统计与成本分摊 → 延后。
- P-R5-4 组内角色（组管理员/普通成员）→ 本版不做，组由平台管理员维护。
- P-R5-5 项目归档/只读 → 本版做 `status=ARCHIVED`，归档后禁止新建 run。

### R6 右侧 AI 智能体面板

**现状差距（证据）**
- 无抽屉组件、无会话表、无 agent 配置。
- 前端已有 `AppearanceDialog` / `AboutDialog`，可复用弹层与焦点管理。

**结论：部分接受。** 本版做「面板 + 只读建议 + 受控执行」，**不做**「自动改代码/自动合并/自动改平台」。
理由：① 本机 CLI 的非交互能力未实测（Q6）；② 让智能体改平台代码，在没有评审门禁前不可控。

**分层设计（从低到高，逐层解锁）**

| 层 | 能力 | 本版 | 前置 |
|---|---|---|---|
| L1 | 解释当前页面 / 当前 run 的失败原因 | ✅ | 上下文打包 |
| L2 | 评估用例质量、给优化建议（文本 diff 建议） | ✅ | 用例读取权限 |
| L3 | 发起执行（需二次确认）、跟踪状态 | ✅ | 执行权限 + 审计 |
| L4 | 生成用例补丁并写入工作区（人工确认后） | ⏳ 延后 | 编辑器 diff + 回滚 |
| L5 | 修改平台自身代码并提 PR | ❌ 不做 | 需代码评审门禁，超出平台职责 |

**安全边界（硬约束）**
1. cwd 固定为项目工作区，**不得**指向仓库根或 `~`。
2. 环境变量白名单注入，**不传** `CRED_MASTER_KEY` / `DB_PASSWORD` / 设备密码。
3. 上下文默认脱敏（IP 打码、账号隐藏、命令截断），可在设置里关（需管理员）。
4. 所有「写」动作（发起 run、写文件）必须**用户显式确认**，且校验当前用户权限。
5. 全量动作写 `ai_action_log`（谁、哪个 agent、什么动作、结果、耗时），不含完整思维链。
6. 进程超时/失控可一键终止；面板崩溃不影响主界面（独立路由域/iframe 或独立进程）。
7. 未安装任何 CLI 时，面板显示「未检测到智能体」+ 安装指引，**主功能零影响**。

**补充的关联/潜在需求**
- P-R6-1 智能体配置档（命令、参数、模型、工作目录）→ 本版落 `ai_agent_profile`。
- P-R6-2 会话摘要与回放（不含思维链）→ 本版存摘要 + 动作序列。
- P-R6-3 多 agent 并存与切换 → 本版支持探测多个，选择其一。
- P-R6-4 MCP 工具化（把平台能力暴露给 agent）→ 延后。
- P-R6-5 提示词版本登记（保证建议可复现）→ 延后。

### R8 前端服务端口 8001

**现状差距（证据）**
- 后端 8081 正在监听；8001 无监听；前端生产承载不存在（无 nginx/静态 handler/deploy 脚本）。
- dev 5173，可由 `VITE_DEV_PORT` 覆盖。

**结论：接受，但定义为「统一入口 8001」**，并把它作为「生产前端承载」的落地载体：

```
浏览器 → :8001（静态资源 + SPA fallback + /api、/ws 反代） → :8081（Spring Boot）
```

- **不改后端 8081**：现有脚本、健康检查、CI、文档全部指向 8081，改它只会制造无收益的回归面。
- 8001 必须提供：`/healthz`（前端静态）、`/api/health`（透传后端）、gzip/brotli、静态资源指纹缓存（`index.html` no-cache）。
- 报告打印页的 base URL 需从旧值改为 8001（否则 PDF 导出拿到的是内网旧地址）。
- 开发环境默认仍 5173（避免与生产入口抢端口）；需要时 `VITE_DEV_PORT=8001` 显式覆盖。

**补充的关联/潜在需求**
- P-R8-1 反代与 TLS（证书、HSTS、同源 Cookie）→ 本版做 HTTP + 反代；TLS 由外层网关承载，文档给配置样例，不代签发。
- P-R8-2 部署脚本与回滚（`deploy.sh` / `rollback.sh` / systemd unit）→ 本版必做。
- P-R8-3 端口矩阵写入「关于」页与运维手册 → 本版必做。
- P-R8-4 旧地址兼容（8081 仍可访问 API）→ 保留，不做重定向。

## 4. 不做 / 范围外

| 不做的事 | 理由 |
|---|---|
| pytest ↔ RF 用例自动互转 | 语义不可逆（fixture/setup/teardown 无法一一映射），转出来的用例是负债 |
| 浏览器内执行用户代码 | 导入用例一律由后端在受控工作区内执行，不在前端沙箱跑 |
| 测试报告自由富文本编辑 | 破坏与 run 的一致性与可审计性 |
| 多租户 SaaS / 计费 / 组织隔离 | 当前单实例自用；`org_id` 扩展位保留，不实现 |
| AI 自动改平台代码并自动合并 | 无代码评审门禁，风险不可控；本版只出建议 |
| AI 远程 API Key 托管 | 本版只接本机 CLI，密钥留在用户本机 |
| 移动端 / 平板适配 | 工位场景，最小 1280×720 |
| 内核插件市场 / 第三方内核 SDK | 防止内核契约在稳定前被外部依赖绑死 |
| 8001 上的多版本灰度/蓝绿 | 单机自用，回滚靠部署脚本与备份即可 |
| 历史 run 批量补生成测试报告 | 会伪造冻结时间与审计链，只提供手动单次生成 |

## 8. 评估结论一句话

**8 条需求全部成立，但都不是「加页面」级别的工作：**
R1 是把报告从「派生视图」升级为「可冻结实体」；R3 是把 pabot 私有逻辑抽成内核契约；R4 是把导入从「Excel 解析」升级为「带安检的工程接入」；R5 是补一层会放大越权面的组织模型；R6 是引入一个拥有本机权限的外部进程；R7/R2 是一次 IA 与视觉的系统收口；R8 是补上从未落地的生产前端承载。
**建议按 W1 端口与菜单 → W2 报告分离 → W3 双内核 → W4 导入 → W5 组织 → W6 AI → W7 界面收口 推进，双内核与导入是价值核心，组织与 AI 是风险核心。**
