## 2. 现状核查（逐条给证据，不靠记忆）

### 2.1 报告域：只有「执行的派生视图」，没有独立测试报告实体

- `[已核实]` 全库 47 张表（`db/migration/*.sql` 实测枚举）中**没有 `report` / `test_report` 表**；报告由 `run` 只读派生：`ReportRepositoryJdbc:48-50` 直接以 run 为查询主体。
- `[已核实]` 明细落在 `test_result` / `keyword_result`（`V1__baseline.sql:473,491`），`test_result` **无 `project_id`**，跨项目聚合只能靠 join run。
- `[已核实]` 导出格式只有 **PDF / DOCX** 两种（`ExportFormat:15-17`），PDF 走无头 Chrome。
- `[已核实]` 前端页面只有一套：`/reports`、`/reports/:runId`、`/reports/:runId/print`（`frontend/src/router/index.ts`）。
- `[推断]` 因此「执行报告」与「测试报告」今天**是同一份东西的两个名字**，无法回答「这份给客户的报告对应哪几次运行、什么时候冻结、冻结后源数据重跑会不会变」。这正是 R1 的痛点，不是命名问题。

### 2.2 菜单：两级结构已具备，但语义混装、无设置位、无搜索

- `[已核实]` 菜单唯一真源 `frontend/src/config/navigation.ts:49-142`，当前 6 个一级项：总览 / 资产（3 子项）/ 用例 / 执行（2 子项）/ 报告 / 系统（2 子项）。
- `[已核实]` 权限只打 `adminOnly` 布尔（`navigation.ts:206-220`），没有「按项目角色」「按能力」两维；`filterNav` 只有两档。
- `[已核实]` 顶栏**无项目选择器**（`App.vue:173-266`），项目切换散落在各页 `ProjectPicker`；`stores/auth.ts:17,95-99` 用 localStorage 存 `projectId`。
- `[已核实]` 无命令面板 / 全局搜索；无「关于」「版本迭代」「系统设置」路由。
- `[推断]` 菜单当前的问题不是「项太少」，而是**分类口径不统一**：资产与执行是「资源域」，用例是「内容域」，报告是「结果域」，系统是「管理域」——四套口径混在一个平面里，再加 4 个新页面必然变成 10+ 个一级项。

### 2.3 执行内核：只有 pabot，且内核细节渗到命令装配层

- `[已核实]` 全仓 `pytest` **零命中**（`grep -rIl pytest --include=*.java --include=*.ts --include=*.vue --include=*.xml` 返回空）。
- `[已核实]` 入口链路：`RunController`（`:139 /quick-run`、`:81`、`cases/run:114`）→ `RunService.create:78` → `ProjectRunDispatcher:34,53,115`（每项目线程池 + `PriorityBlockingQueue`，并发默认 4）。
- `[已核实]` 命令装配 `PabotCommandBuilder:42-73` 直接拼 `pabot --outputdir ... --processes N --name ... [--test|--include] <suitePaths>`，并在 `:65-71` 注入 PATH/TZ/LANG/PYTHONUNBUFFERED。
- `[已核实]` 进程 `ProcessLauncherImpl:16-19`、`PabotOrchestrator:41-90` 双线程写 `stdout.log` / `robot_stderr.out` / `run.log`；**退出码不可信，以 `output.xml` 为准**（`:86-90`）；超时 `destroyForcibly`（`:76-79`）；`RunTimeoutMonitor:44` 三级超时（run 3600s / 用例 1800s / 静默 900s）。
- `[推断]` 现在换内核不是「加一个 if」，而是要把「怎么拼命令、怎么判成功、怎么解析结果、怎么判超时」四件事从 pabot 里抽出来。R3 的真实工作量在**统一结果模型**，不在启动进程。

### 2.4 解耦与导入：资产已半解耦，用例导入只到 Excel

- `[已核实]` 资产已支持平台共享：`project_asset` 表存在（`V7_3`），`device/link/credential` 有 `owner_scope`；存量按项目插入引用。
- `[已核实]` 但 `device.project_id`、`test_case.project_id`、`test_set.project_id`、`robot_file.project_id`、`run.project_id` 仍在（`V1__baseline.sql:150,271,307,338,455`）。
- `[已核实]` `test_case` **不持有 `device_id`**，DUT 在执行时绑定——这是既有优点，但目前没有 schema 断言把它钉住。
- `[已核实]` 导入只有 Excel 两步 `preview/commit`（`CaseController:119,126`；`CaseImportService:33`），仅 `xls/xlsx`，**无 CSV、无目录、无 zip**。
- `[已核实]` RF 文件只有单文件上传/编辑（`FileController:25,64`），**无目录导入、无批量**。
- `[推断]` 「原生用例集合直接导入」缺的不是解析器，而是**三层东西**：来源登记（哪来的、什么版本、什么许可证）、沙箱（不能把任意文件写进平台目录）、适配报告（缺依赖/缺 fixture/路径写死，要能提前说清）。

### 2.5 组织模型：有项目成员，无用户组

- `[已核实]` IAM 表：`app_user` / `role` / `user_role` / `project` / `project_member` / `project_setting` / `api_token` / `user_preference`；**无 `user_group` / `group_member` / `tenant`**（47 表实测）。
- `[已核实]` 角色全局（`role` + `user_role`），项目内另有 `project_member.member_role`；4 个内置角色（`RoleCode:8-11`）。
- `[已核实]` 有效角色口径：超管 = `user_role` 含 admin（`AccessControlService:44-47`），优先级 admin > 项目角色 > 全局角色（`:50-72`）。
- `[已核实]` 租户隔离靠 `TenantContext` + 路径 `projectId`（`AccessControlService:105`），不是 DB 行级策略。
- `[推断]` 增加「组」会**扩大越权面**：组授权是间接路径，`TenantGuard` 元测试若不覆盖新表，会出现「有 project_id 但查不到校验」的静默越权。

### 2.6 AI 智能体：平台内零接入，但本机 CLI 生态可用

- `[已核实]` 前端无右侧抽屉组件，只有 `ConfirmDialog` / `AppearanceDialog` / `AboutDialog`（`frontend/src/components/`）。
- `[已核实]` 后端无任何 LLM / agent 依赖与配置项（47 表中无会话表；`application.yml` 无相关键）。
- `[推断]` 「嵌入本机已配置的 CLI」意味着平台不做模型托管，只做**进程编排 + 上下文注入 + 输出流式呈现**。这比接 API Key 简单，但安全边界完全不同：CLI 拥有本机文件权限，必须限定 cwd、环境变量与可执行动作。

### 2.7 界面体系与端口

- `[已核实]` 主题 token 已在 UX-01 落地（`docs/plan/多项目与体验基线-评估与设计-20261104.md` §3，113 处硬编码清零、`check_contrast.py` 守门），但**字体阶梯 / 间距 / 密度 / 三栏布局未系统化**。
- `[已核实]` 后端端口 `${SERVER_PORT:8081}`（`backend/src/main/resources/application.yml:21`、`application-prod.yml:11`）；前端 dev 5173，可用 `VITE_DEV_PORT` 覆盖（`frontend/vite.config.ts:19-20`）。
- `[已核实]` **生产前端承载尚未落地**：无 nginx 配置、无静态 handler、无 deploy 脚本（`OPS-MANUAL` 待回填）。
- `[已核实]` 目标机 8001 **当前无监听**（`ss -ltnp` 实测只有 8081/java、无 8001/5173）；`8081` 正被运行中的后端占用。
- `[推断]` R8 的真实内容是「补上生产前端承载」，端口号只是它的外在表现。只改一个数字会得到一个**打不开的 8001**。

## 3. 同类产品与技术调研

### 3.1 报告双实体（执行报告 vs 测试报告）

| 参考 | 做法 | 对本项目的启示 |
|---|---|---|
| Allure / ReportPortal | 「一次运行」与「一次发布的质量结论」分离，后者靠标签聚合 | 测试报告应是 run 的**聚合快照**，不是另一份明细 |
| TestRail / Xray | Test Run（执行）与 Test Report（对外交付物）分属两个模块 | 对外报告要能冻结、能版本化、能分享链接 |
| GitLab Pipeline | Job 日志（内部）与 Release Evidence（对外）分离 | 内部视图允许出现 IP/命令；对外视图必须有字段白名单 |

`[推断]` 结论：**执行报告 = 派生视图（不落库、实时反映 run）；测试报告 = 实体（落库、冻结、可版本化）**。两者不是并列的两个页面，而是两种生命周期。

### 3.2 双内核

| 参考 | 做法 | 启示 |
|---|---|---|
| pytest | `--json-report` / `--junitxml`；nodeid 唯一标识用例；`-x`、`--timeout`、`-k/-m` 选择 | 用 junitxml 做兜底（插件缺失也能跑），json-report 做主通道 |
| Robot Framework | `output.xml` 是权威结果；`--dryrun` 做语法预检；`pabot` 做分片 | 现有「以 output.xml 为准」的判断必须上移为内核契约 |
| pytest-xdist / pabot | 都改变进程拓扑，但结果可合并 | 并发归「编排层」，解析归「内核层」，别混在一条命令里 |
| Jenkins / GitHub Actions | Runner 抽象 + 结果协议（JUnit） | 用 SPI + 归一化结果，而不是给每个内核写一套 service |

`[推断]` 结论：内核契约应包含 `probe / collect / buildCommand / parse / classifyFailure` 五个动作，编排、租约、日志、超时全部留在平台层——否则第二个内核会把现有执行域复制一遍。

### 3.3 AI 智能体接入

| 参考 | 做法 | 启示 |
|---|---|---|
| Claude Code / Codex CLI | 非交互模式读 stdin/参数，流式 stdout，工作目录即上下文边界 | 平台可作为「编排器」，cwd 固定为项目工作区 |
| MCP（Model Context Protocol） | 工具以协议暴露，客户端可枚举 | 可选增强：把「查用例/发起运行」做成 MCP 工具，但**不是本期前置** |
| ACP / agent 会话协议 | 会话、消息、工具调用三段式 | 平台侧只需存会话摘要与动作审计，不存完整思维链 |

`[假设]` 本机至少有一个 CLI 已登录且支持非交互调用（`claude -p` / `codex exec` 一类）。**这一条未实测**，是 R6 的最大不确定性；若全部只能交互式 TUI，则平台只能做「唤起终端」，功能要降级。

### 3.4 菜单 IA 与工作区

| 参考 | 做法 | 启示 |
|---|---|---|
| GitLab | 左侧「上下文切换（组/项目）+ 固定主导航 + 设置下沉」 | 项目选择器应在顶栏，不在每个页面里 |
| Linear | 命令面板（Cmd+K）+ 收藏 + 最近访问 | 菜单项变多后，搜索比层级更重要 |
| VS Code | 活动栏 + 侧栏 + 编辑区 + 右侧辅助面板（可折叠） | 右侧 AI 抽屉与三栏布局可以共存，但必须有最小宽度与折叠策略 |

`[推断]` 结论：R2 与 R7 是同一件事的两面——**菜单解决「找得到」，布局解决「放得下」**。菜单重构若不伴随项目选择器上移与命令面板，只是换了个顺序。
