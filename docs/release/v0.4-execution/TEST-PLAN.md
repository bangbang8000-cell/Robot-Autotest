## 1. 测试目标

### 1.1 三个必须成立的数字

| 指标 | 目标 | 为什么是它 |
|---|---|---|
| 4 并发加速比 | **≥2.5x** | 不并行，平台就只是个用例仓库 |
| 同设备同端口冲突 | **0 次** | 冲突 = 测出脏数据，且事后查不出 |
| 实时日志 P95 延迟 | **<2 s** | 看不见进度，人就会去 SSH 手工看，平台被绕开 |

### 1.2 本版的特殊要求：「失败要失败得像」

执行域最危险的 bug 是**假成功**：进程报成功、产物是空的、报告显示 0 用例。所以本版有整整一节（§3）专测「**平台能不能正确报错**」，而不是只测正常路径。

> 一个只会走 happy path 的执行域，比没有执行域更危险——因为它会让你相信错误的结果。

### 1.3 不测什么

| 不测 | 原因 |
|---|---|
| 报告渲染与导出 | v0.5 |
| 定时与 CI 触发 | v0.6 |
| 多执行节点（分布式） | 不做 |
| 执行器池的负载均衡 | 本版不做池化 |
| Windows 作为执行节点 | 执行节点只有 149 |

## 3. 故障注入（本版最重要的一节）

### 3.1 八种故障与期望

| ID | 注入方式 | **必须**观察到的现象 | 不允许出现的现象 |
|---|---|---|---|
| TC-v0.4-301 | PATH 不前置 venv/bin | 错误信息含「找不到 robot / No such file or directory」 | 「执行完成」+ 空产物 |
| TC-v0.4-302 | `--include` 过滤掉全部用例 | 判 `failed`，原因「no tests executed」 | 判 `finished`，用例数 0 |
| TC-v0.4-303 | suite 文件语法错误 | 错误信息含 RF 的原始解析错误与行号 | 只说「执行失败」 |
| TC-v0.4-304 | 产物目录不可写（`chmod 500`） | 创建运行即被预检拒绝 | 跑完才发现没产物 |
| TC-v0.4-305 | 磁盘不足（用 `fallocate` 造满） | 预检拒绝或运行中明确报磁盘满 | 静默写坏产物 |
| TC-v0.4-306 | 子进程被 `kill -9` | run 标 `failed(interrupted)`，租约在 TTL 内回收 | 永远 `running`，租约永久占用 |
| TC-v0.4-307 | 服务端端口不足（并发 8，端口仅 4） | 创建即拒绝并提示端口数 | 静默失败、部分分片无产物 |
| TC-v0.4-308 | pabot 版本不兼容（临时换 venv） | 预检报「pabot 版本不匹配」 | 运行中报莫名其妙的错 |

### 3.2 为什么每条都要「必须 / 不允许」两列

「报错了」不是合格标准。**报错必须指向真实原因**，否则运维看到「执行失败」还是要去翻日志半小时。这两列就是判据。

**现场演示要求**：silence 现场看 TC-v0.4-301 与 TC-v0.4-302 两条完整过程（从触发到看到错误信息），计时 ≤2 分钟定位到原因。

## 4. 租约并发测试（T2，本版正确性的地基）

### 4.1 用例

| ID | 用例 | 期望 |
|---|---|---|
| TC-v0.4-101 | 100 线程抢同一 `resource_key` | 成功 **1**，失败 99，且失败原因是「被占用」而非异常 |
| TC-v0.4-102 | 100 线程抢 10 个 key（每 key 期望 10 个赢家前先到先得） | 每 key 恰好 1 个持有者，总成功 10 |
| TC-v0.4-103 | 释放后立刻重抢 | 成功 |
| TC-v0.4-104 | **释放必须带 job_id** | A 任务尝试释放 B 的租约 → 影响行数 0，B 的租约仍在 |
| TC-v0.4-105 | 心跳续约 | 持有 5 分钟（超过 TTL），期间租约不被回收 |
| TC-v0.4-106 | 心跳停止 | TTL（120 s）后被回收，run 标 `failed(lease_expired)` |
| TC-v0.4-107 | 部分申请失败 | 拿到 2 个后第 3 个超时 → **已拿到的 2 个被释放**，run 标 `failed(lease_timeout)` |
| TC-v0.4-108 | 连续 20 轮 4 并发 | 冲突次数 **0**（查 `resource_lease` 历史，同 key 无重叠持有） |
| TC-v0.4-109 | 强制释放（管理员） | 租约消失，原 run 标 `failed(lease_revoked)`，审计有一条 |

### 4.2 冲突的判定方法（不能靠「看起来没冲突」）

```sql
-- 冲突 = 同一 resource_key 在时间轴上有重叠的两个持有记录
SELECT resource_key, COUNT(*) c
FROM resource_lease_history
GROUP BY resource_key, run_id
HAVING c > 1;
-- 期望：0 行
```

**必须保存租约历史**（`resource_lease_history` 表或审计日志），否则「0 冲突」无法证明。这是本版要额外加的表，DEV-PLAN 的迁移里要有。

## 5. 4 并发压测（EXE-07）

### 5.1 压测设定（固定，不许改）

| 项 | 值 |
|---|---|
| 用例集 | 4 个 suite × 2 条用例，每条 `Sleep 6s` |
| 串行基线 | `robot` 跑全部（≈48 s + 开销） |
| 并行 | `pabot --processes 4` |
| 轮次 | 20 轮（每轮前清库、清产物） |
| 环境 | 149，8C / 7.4 GB，无其他负载 |

### 5.2 用例

| ID | 用例 | 期望 |
|---|---|---|
| TC-v0.4-201 | 串行基线 | 记录实际耗时（用于算加速比的分母） |
| TC-v0.4-202 | 4 并发 20 轮 | 平均加速比 ≥2.5x；**最差一轮 ≥2.2x** |
| TC-v0.4-203 | 调度开销 | <5%（并行总耗时 vs 最慢分片耗时） |
| TC-v0.4-204 | 冲突统计 | 20 轮累计冲突 **0** |
| TC-v0.4-205 | 内存峰值 | 4 并发峰值 <6 GB（留 1.4 GB 余量） |
| TC-v0.4-206 | 2 并发对照 | ≈1.6-1.8x（与历史实测 1.61x 一致，证明无退化） |

### 5.3 结果的正确解读方式（写进报告，防止误用）

| 用例形态 | 加速比预期 | 说明 |
|---|---|---|
| 12 s/例 | 3.0-3.5x | 本次压测形态 |
| 6 s/例 | 2.5-3.0x | 启动开销开始显形 |
| 1 s/例 | 1.2-1.5x | 主要是开销，并行无收益 |

**报告必须包含这段说明**。否则有人拿「3.2x」去承诺「不管什么用例都能 3 倍」，然后被现实打脸。

**延迟测量方法**（必须这样测，不能靠肉眼）：

```

前端侧：收到时记 ts_recv
延迟 = ts_recv - ts_gen
取 4 并发运行中所有行的 P95
```

## 13. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 只测正常路径，故障注入走过场 | 上线后「执行完成但没结果」查不出原因 | 故障注入 8 条写进退出标准，现场演示 2 条 |
| 加速比只跑 1 轮 | 碰巧一次好看，长期不达标 | 20 轮 + 最差轮次也设门槛 |
| 租约冲突靠「日志里没看到」判断 | 冲突已发生但无记录 | 必须存租约历史并 SQL 查询 |
| 取消只改状态不杀进程 | 设备被幽灵进程占用 | `ps` 验证 + 取消后立即重跑 |
| 失败分类用关键词硬猜 | 把真 bug 当环境问题重试掉 | 30 条样本 + 100% 准确率门槛 |
| 压测期间跑其他任务 | 加速比不可比 | 压测环境独占，写进流程 |
| DUT 掉线用回放糊过去 | G4「实网通过」是假的 | 证据首行标注 `[REPLAY]`，大师书面接受才可 |
