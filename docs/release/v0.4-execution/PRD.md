## 1. 版本定位

### 1.1 一句话

> **点一下就能跑起来：4 条用例集在不同设备上同时跑，互不抢端口，日志实时往外冒，想停能停得住。**

### 1.2 这一版是整个平台的价值分水岭

前三个版本做的都是「把东西管起来」。这一版开始，平台第一次**真的在跑测试**。它的失败模式也和前面完全不同：

| 前面版本的错误 | 本版的错误 |
|---|---|
| 显示不对、筛选不准、保存失败 | **测出来的结论是错的**，而且看不出错 |
| 用户看一眼就能发现 | **失败要几周后才在报告里被发现** |
| 重做一次即可 | 已发出的报告要追回，对外信誉受损 |

所以本版的验收不靠「功能能点」，靠三个数字：**加速比 ≥2.5x、端口冲突 0 次、日志延迟 <2 s**。

### 1.3 本版最容易被做错的地方

| 做错的方式 | 后果 | 本版怎么防 |
|---|---|---|
| 一上来就做执行器池、负载均衡 | 三个版本都在调池子，一条用例都没真跑通 | **先做最小闭环**（一条 suite → 一个 pabot 进程 → output.xml → 落库），通了才谈并发 |
| 用「进程起来了」判断执行成功 | pabot 子进程静默失败，`output.xml` 是空的，报告显示 0 用例 | **退出码不可信**，必须校验产物（见 §3.3） |
| 租约在「要跑的时候」才抢 | pabot 是**先切分后执行**，切分时不知道端口已被占，跑起来才冲突 | 租约必须在**调度前**按切分结果申请 |
| 取消 = 把状态改成 canceled | 进程还在跑，设备还占着，下一个任务拿不到端口 | 取消必须**杀进程组 + 释放租约**，并用 `ps` 验证 |

## 2. 用户与场景

| 角色 | 场景 | 本版能力 |
|---|---|---|
| **测试工程师**（主） | 用例写好了，想跑一次看结果 | 选用例集 → 选环境 → 设并发 → 跑 |
| 测试工程师 | 跑到一半发现选错设备了 | 点取消，进程立即停，设备立即释放 |
| 测试工程师 | 一条失败，想知道是环境问题还是断言失败 | 日志里能看到失败分类与原始 stderr |
| **测试负责人** | 想知道昨晚 4 条并行的实际耗时 | 运行记录里看每轮耗时与并发度 |

**核心场景（本版验收必走）**：

1. 张工选用例集「RDMA 冒烟」（8 条用例，分属 4 个 suite）；
2. 选环境「RoCE 互通」，设置并发 4；
3. 点「开始」→ 平台先按 suite 切分，为每个分片申请 `设备+端口` 租约；
4. 4 个分片并行启动，日志区实时滚动，**延迟不超过 2 秒**；
5. 跑到第 30 秒，张工点「取消」→ 4 个进程组全部被杀，租约全部释放；
6. 再点「开始」→ 能立刻重新拿到同样的设备（证明释放是真的）；
7. 跑完 → 运行记录显示总耗时、每分片耗时、通过/失败数。

## 4. 非功能需求

| ID | 需求 | 目标 | 验收方式 |
|---|---|---|---|
| NFR-v0.4-01 | 4 并发加速比 | **≥2.5x**（固定用例集） | 压测报告，脚本可复跑 |
| NFR-v0.4-02 | 同设备同端口冲突 | **0 次**（连续 20 轮压测） | 数据库查租约历史 + 日志 |
| NFR-v0.4-03 | 实时日志延迟 | P95 <2 s（4 并发） | 打时间戳比对 |
| NFR-v0.4-04 | 调度额外开销 | <5%（总耗时 vs 纯执行耗时） | 压测报告 |
| NFR-v0.4-05 | 取消响应 | 点击到进程消失 ≤5 s | 实测 |
| NFR-v0.4-06 | 租约回收 | 进程异常退出后 ≤TTL 回收（默认 120 s 心跳 ×3） | 造 kill -9 场景 |
| NFR-v0.4-07 | 单 run 日志上限 | 落盘 ≤500 MB，超出滚动 | 造大日志用例 |

> **加速比口径必须写死**：不同用例集测出的加速比不可比（用例越短，固定开销占比越大，加速比越难看）。压测固定用「4 个 suite × 2 条 sleep 6 s 用例」，并在报告里写明这个前提。

## 5. 交互与信息架构

| 约定 | 内容 |
|---|---|
| 「执行」菜单三个二级页：执行计划（本版只做手动运行入口）、运行记录、实时面板 | 计划任务在 v0.6 |
| 运行状态用统一颜色：排队灰、运行蓝、通过绿、失败红、取消黄 | 与报告一致，避免两套语义 |
| 失败必须给「下一步做什么」 | 环境类 → 「检查设备连通性」；断言类 → 「查看日志第 N 行」 |
| 危险操作：取消与强制释放都要二次确认 | 会中断正在跑的任务 |
| 设备占用在资产页可见 | 避免「谁在占着」只能问人 |

## 6. 不做什么

| 不做 | 原因 | 何时 |
|---|---|---|
| 定时/触发式运行 | 计划域是 v0.6 | v0.6 |
| 报告与导出 | v0.5 | v0.5 |
| 分布式执行（多执行节点） | 单机 4 并发够用；多节点是运营期的事 | 运营期按负载评估 |
| 执行器池 + 负载均衡 | **本版明确不做**：先最小闭环，池化会拖死进度 | 若 4 并发稳定后再评估 |
| 用例失败自动修复建议 | 属于 AI 分析，不在范围 | 运营期 |
| 容器化执行 | 本地 WSL 按最小依赖约定不装 Docker | 不做 |

## 7. 验收清单（G4 执行门）

- [ ] 一条 suite 最小闭环跑通：pabot → output.xml → 落库 → 可查
- [ ] 4 并发固定用例集压测：**加速比 ≥2.5x**
- [ ] 连续 20 轮 4 并发：**同设备同端口冲突 0 次**
- [ ] 4 并发下日志 P95 延迟 <2 s
- [ ] 取消后 `ps` 无残留进程，租约立即释放，可马上重跑
- [ ] 故意去掉 PATH → 报「找不到 robot」，不是「执行完成无产物」
- [ ] 造「退出码 0 但产物为空」→ 平台判失败并说明
- [ ] 平台重启后无僵尸 running，租约表无残留
- [ ] 一条真实 DUT 链路端到端跑通，日志无明文口令
- [ ] 无 P0/P1 未关闭缺陷
