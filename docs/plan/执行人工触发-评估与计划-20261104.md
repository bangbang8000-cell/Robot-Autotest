# 执行域「一次人工触发」· 评估与计划

**文档编号** RA-EXEC-2026-001 ｜ **日期** 2026-11-04 ｜ **状态** 待评审（只评估与更新计划，不开发）

**大师反馈（2026-11-04）**：执行在界面上也有问题；测试项更多情况需要的是**一次人工触发执行**。

---

## 1. 现状盘点（全部代码核实）

### 1.1 三条链路的真相

| 链路 | 入口 | 会真正执行吗 | 结论 |
|---|---|---|---|
| 计划手动触发 | `POST /api/plans/{id}/trigger-now` → `PlanService.triggerNow` → `PlanScheduleService.triggerManual` → `RunDispatcher.dispatch` → `RunExecutionService` → pabot | **会** | 正常 |
| 计划 cron 调度 | `PlanScheduler`（@Scheduled）→ 同上 | **会** | 正常 |
| **无计划直建 run** | `POST /api/execution/runs` → `RunService.create` | **不会**——只落库 `queued`，全仓无消费者：`RunQueuePolicy` **0 个调用点**、`RunDispatcher` 只被 `PlanScheduleService` 使用 | **坑**：调用即产生僵尸 run |

### 1.2 界面缺口

- 全前端**唯一**的触发入口在 `PlansView`（`triggerNow` 两处按钮）。必须**先建计划**才能跑。
- `RunsView` 是纯只读列表（列表/详情/日志），没有任何触发动作。
- `CasesView` / 资产页没有「跑一下」入口。
- 这就是「界面上也有问题」的实体：**UI 把「临时跑一次」逼成了「先建一个计划对象」**——计划是调度实体（cron/时区/依赖/重叠策略），被挪用来承载本应一次性的动作。

### 1.3 模型缺口（比 UI 更深一层）

- 执行的真实输入是 **`suitePaths`**（robot_file 工程内相对路径）+ 环境设备；`testSetId` 只是计划上的组织信息。
- **台账 `test_case` 与 `robot_file` 脚本之间没有直接关联字段**（ADR-0005 两真源并列）。因此「勾选 N 条台账用例 → 直接跑」当前**没有解析路径**，必须先补「用例 → 脚本路径」的绑定或约定。

## 2. 方案评估

| 方案 | 做法 | 判定 |
|---|---|---|
| A（**推荐**）：`quick-run` 一次性执行 | 新端点 `POST /api/execution/quick-run`：入参 `suitePaths`（必填）/ `environmentId` / `deviceKeys` / `concurrency` / `timeoutSeconds` / `includeTag`；后端校验 `EXECUTION:EXECUTE` 权限 → 组装 `CreateRunCommand` → `RunService.create`（`trigger_type=manual`、`plan_id=NULL`）→ **立即走同一条 `RunDispatcher` 派发链** → 返回 `RunRecord`。不落计划实体 | 复用预检/超时/取消/日志全链；UI 一步触发；计划语义不被污染 |
| B：前端隐式建计划再 trigger-now | 不新加端点 | **否**：计划列表积累一次性垃圾对象；cron/依赖字段全空，语义脏 |
| C：给 `POST /execution/runs` 补消费者 | 修僵尸端点 | **并入 A 的实现**（见 2.1），但**不把 C 当作 UI 方案**——该端点是裸 `CreateRunCommand`，无权限语义校验入口，直接暴露给 UI 不妥 |

### 2.1 随 A 一并处理的两个既有问题

1. **`POST /api/execution/runs` 的定位收编**：明确为 **CI 触发专用**（对应 `ci_trigger` 域），文档标注「落库后由 quick-run 同款的派发 worker 消费」——即本包把派发 worker 从 `PlanScheduleService` 私有提升为公共组件，两条链共用。**这也正面解决此前挂起的「是否补执行队列」决策**：不新建独立队列系统，`RunDispatcher`（串行 worker + 去重）即消费者；`RunQueuePolicy` 若在实现中确无用处则删除，不留死代码。
2. **台账用例 → 脚本路径绑定**：本包范围只做「按套件路径 / 按用例集」的人工触发；「勾选台账用例直接跑」依赖用例↔脚本绑定，**单列为 EXEC-02**（依赖 CAS-06 用例脚本关联设计，避免本包范围膨胀）。

### 2.2 交互设计（对应 PRD 验收标准）

- **执行页（RunsView）**：页头加「手动执行」按钮 → 抽屉/内联表单：套件路径多选（文件树或粘贴路径列表）、环境（默认项目默认环境）、设备（可选，空=自动收集）、并发（默认 1）、超时（默认全局值）。提交 → 跳转 run 详情页。
- **用例集**：用例集详情页「立即执行」= 以该集合**已映射的套件路径**触发（若集合内用例未绑定脚本，给出明确报错引导，不静默跳过）。
- **触达反馈**：触发成功 toast + 跳转；预检失败（DUT 不可达 / 无套件）在表单内联 `InlineAlert` 显示，不弹原生框。

| ID | 需求 | 优先级 | 验收标准 | WBS |
|---|---|---|---|---|
| FR-v0.2-59 | **一次人工触发**：无需创建计划，直接按套件路径集触发执行；`trigger_type=manual`、`plan_id=NULL`；走与计划触发同一条派发链（预检 / 超时 / 取消 / 日志全量可用） | P0 | 建一个 run 后**不建任何计划**，run 状态从 queued 推进到 running/finished，产出 output.xml | EXEC-01 |

| FR-v0.2-61 | **僵尸端点收编**：`POST /api/execution/runs` 落库后由公共派发 worker 消费（CI 链路真实可用）；`RunDispatcher` 提升为执行域公共组件 | P0 | 直调该端点创建的 run 不再永久 queued | EXEC-01 |
| FR-v0.2-62 | **人工触发可追溯**：quick-run 与手动表单触发均写 `audit_log`（`action=RUN_TRIGGER`，detail 含来源页面 + 套件数 + 操作者） | P1 | 触发后审计可查到对应记录 | EXEC-01 |
| FR-v0.2-63 | **用例集立即执行**：以用例集内已绑定脚本的套件路径触发；存在未绑定用例时明确报错并列出，不静默跳过 | P1 | 混合集合触发 → 400 且错误信息含未绑定用例编号列表 | EXEC-01（EXEC-02 前置告知） |
