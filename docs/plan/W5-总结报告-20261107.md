6 条示例用例真正进了 `robot_file`，计划编排有了四类冲突检测与批量启停，失败聚类从「单轮看」升级到

## 2. 为什么做这三件事

| 缺口 | 表现 | W5 的解法 |
|---|---|---|
| 空库不可用 | 新环境装完平台，用例列表空的，演示与试点无处下手 | 6 条离线示例用例经 API 入 `robot_file`，开箱即跑 |

## 3. 交付内容

### 3.1 示例用例（W5.1）

`examples/` 下 6 个纯离线 Robot 套件，覆盖变量/列表/算术/字符串/字典/时间六类基础操作，
每个都带 `Metadata CASE_ID`、`CASE_KIND` 与 `Force Tags sample`，本地实跑 **12 tests / 12 passed**。

写入走平台既有 `PUT /api/projects/{id}/files`（`tools/seed_sample_cases.py`），不直插数据库：
写前 GET 比对内容，相同则跳过。实测首轮写入 6 条，后续修改 3 条产生 `version 2`；
本次复跑 `SEED_RESULT PASS written=0 skipped=6 total=6`，幂等可用。

### 3.2 计划编排冲突与批量启停（W5.2）

四类判定，全部是**可确定**的问题，不做启发式猜测：

| 类型 | 严重级 | 判定 |
|---|---|---|
| `INVALID_CRON` | FAIL | cron 无法解析，计划永远不会触发 |
| `DISABLED_DEPENDENCY` | FAIL | 依赖的计划处于 `PAUSED`，永远等不到 |
| `DUPLICATE_TARGET` | WARN | 多条启用中的计划目标完全相同，会重复执行 |
| `SAME_SLOT` | WARN | 未来触发时刻相同，会挤占执行队列 |

`SAME_SLOT` 按「参与撞点的计划集合」聚合，只报最早时刻 —— 同一组计划往往在未来 3 个触发点全部撞上，
逐点报会把面板刷满，看起来像 3 个独立问题。

批量启停 `POST /api/plans/batch`：`@Audited("schedule:batch")` + 事务；
`PAUSED` 清空 `next_fire_at`，`ENABLED` 重算并置 `last_fire_at`；
单条脏 id 不中断整批，已处于目标状态返回 `changed=false`。

前端计划页底部「编排冲突」卡片：严重级左侧色条、勾选组合、批量暂停/启用、回执「成功 N 条 / 未变更或失败 M 条」。

### 3.3 跨 run 失败聚类（W5.3）

`GET /api/failure-clusters/recent?projectId=&runs=5`（`runs` 1..20）把最近 N 轮的失败行交给
同一套归一化规则合并，返回作用域标记 `runId="recent:N"`。

前端失败聚类页新增双口径切换：

- **单轮**：沿用原 `runId` 查询，可按簇重跑；
- **最近 N 轮**：不要求 runId，摘要显示「最近 N 轮共 X 条失败，合并成 Y 个类别」；
  跨轮簇**禁用重跑**（后端按簇重跑要求单轮 runId，合并簇拿任意一轮去跑会破坏统计口径）。

## 5. 过程中修掉的问题

1. **`SAME_SLOT` 逐触发点重复报**：两条计划在 3 个未来触发点全撞上时产出 3 条同名冲突。
   改为按计划集合聚合、只报最早时刻。
2. **批量启用 `nextFireAt` 测试期望算错时区**：cron 是 `Asia/Shanghai` 的 02:00，
   `NOW=00:00Z` 时应为次日 02:00+08 = `18:00Z`，原期望写成 `02:00Z`。属测试期望错误，已在用例内写明换算。
3. **CSS 用了白名单外的 `96px`**：门禁 `06-lint` 直接红，改为既有档位 `90px` 后通过 —— 说明 px 白名单在起作用。

## 6. 已知边界

| 边界 | 影响 | 建议 |
|---|---|---|
| 跨轮簇不能重跑 | 想重跑需切回单轮口径 | 可接受；若将来要做「跨轮簇重跑」，需按多轮 caseIds 交集另建接口 |
| 冲突检测只覆盖四类 | 时间重叠但不同 cron、资源争用等未建模 | 先观察试点里的真实误判/漏判，再决定是否加类型 |
| 示例用例为离线套件 | 证明「能进库、能跑、能出报告」，不证明外部 DUT 场景 | 真机用例接入时按同口径补 metadata 与证据 |
| 冲突检测每次全量分页拉取（上限 500 条） | 计划数量极大时检测耗时会线性增长 | 计划规模过千时再改为 SQL 侧聚合 |
