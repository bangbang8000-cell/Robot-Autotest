# 总览页真实化 · 评估与设计

**文档编号** RA-PLAN-2026-004 ｜ **日期** 2026-11-04 ｜ **状态** 已评审（大师 2026-11-04 批准推进）

**关联** v0.2 PRD §1.3「总览 🟡 基础版」、WBS `OVW-01`、ADR-0006（租户隔离）

---

## 1. 问题

`frontend/src/views/OverviewView.vue` 全文 43 行：一个标题、一句「占位」提示、一个后端 ping 探针。
登录进来第一屏什么都说明不了——**用户必须点 6 个菜单才能拼出「我现在有什么、跑过什么」**。

这与「可用、好用、可便捷高效」的目标直接冲突：总览是唯一能一屏回答「这个平台现在是什么状态」的页面，
只做 ping 等于把导航首页浪费了。

## 2. 现状核查（不是猜的）

| 事项 | 实测结果 | 证据 |
|---|---|---|
| 总览页实现 | 43 行，仅 `healthPing()`，无任何统计 | `frontend/src/views/OverviewView.vue` |
| 后端聚合接口 | 0 个（`/api` 下 27 个 Controller，无 overview/dashboard） | `find backend/src/main/java -name "*Controller.java"` |
| 可统计的数据 | 用例 226、设备 3、端口 0、链路 2、凭据 2、环境 0、用例集 0、运行 0、结果 0 | `robot_dev` 真库 `COUNT(*)` |
| 执行域是否有数据 | **没有**，一次 run 都没创建过 | 同上（`run` = 0） |

**结论**：后端数据全都在，缺的只是一个聚合读接口和一个像样的页面。执行区当前必然为空，
**空态必须设计成引导，而不是一排 0**（见 §7）。

## 3. 方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 前端拼装 | 页面并发调 `/cases`、`/assets`、`/runs`、`/reports` 各自分页接口，前端数 `total` | ❌ 需要 5~6 次往返；`total` 是分页总数不是聚合；趋势/通过率前端算不出来；每次加指标都要改前端 |
| B. 后端聚合读接口 | `GET /api/projects/{id}/overview` 一次返回全部指标 | ✅ 一次往返；口径集中在 SQL / 服务层，前后端不会各算一套；易加缓存 |
| C. 物化统计表 | 定时任务预聚合到 `overview_stat` 表 | ❌ 数据量在 1e4 内，`COUNT + GROUP BY` 走索引毫秒级；多一张表、多一个不一致来源 |

**选 B**。C 留到数据量真上来（>10 万 run）再评估，现在做是过度设计。

## 4. 指标口径（本版定稿，改口径必须改本节）

总览最容易出的问题不是「算不出来」，而是**同一件事在两个页面算出两个数**。先把口径钉死：

### 4.1 用例

| 指标 | 口径 |
|---|---|
| 用例总数 | `test_case` 中 `status = 1`（在用）的行数；停用不计 |
| 按优先级分布 | 同上，`COALESCE(NULLIF(priority,''), '未标注')` 分组 |
| 按评审状态分布 | 同上，`review_status` 分组（draft/pending/approved/rejected） |
| 技术域 Top N | 同上，`domain_tag` 分组取前 6；**其余不合并展示**（总览不是报表，别造「其他」这个假桶） |

### 4.2 资产

| 指标 | 口径 |
|---|---|
| 设备 | `device.status = 1` |
| 端口 | 归属在用设备的 `device_port` 行数（端口表无 `project_id`，join `device` 取租户） |
| 链路 | `link.status = 1` |
| 凭据 | `credential` 全部（凭据无软删，只有密文有无） |
| 环境 | `env_profile` 全部 |
| 用例集 | `test_set.set_status = 'active'` |

### 4.3 执行（最容易撒谎的地方）

- **「完成」= `run_status IN ('finished','failed')`**。
  `finished` 是 pabot 退出 0 且产物校验通过，`failed` 是执行失败但**确实跑过**；两者都进通过率分母。
  `queued/preparing/running/canceled` **一律不进分母**。
- **通过率 = 用例级 `PASS / (PASS+FAIL+SKIP)`，不是 run 级**。
  原因：一次 run 里 8 条用例 7 过 1 挂，run 级只能记一个「失败」，看不出 87.5%。用例级更接近用户直觉。
  数据源用 **`test_result` 明细**，不用 `run.pass_count` 缓存字段（缓存可能没回填，读缓存会静默少算）。
- **没有完成记录时通过率为 `null`，不是 `0%`**。展示「暂无」——`0%` 会被读成「跑过且全挂」，是错误信息。
- **近 N 天** 默认 30 天，按 `COALESCE(started_at, enqueued_at)` 落在窗口内计数。
  用例级通过率也按**同一个窗口**算（页面上写「近 30 天 · 用例级」），避免「累计通过率」混进当期读数。
  趋势点的三个计数都是**运行数**（`finished`/`failed`/`canceled`），不是用例数——字段名就按这个语义取。
- **平均耗时** 只统计 `finished/failed` 且 `started_at`、`finished_at` 都非空的 run；样本 0 时 `null`。
- **近期执行** 默认 8 条，按 `COALESCE(started_at, enqueued_at) DESC, id DESC`。

### 4.4 顺手修掉的一个既有缺陷

`TrendRepositoryJdbc` 的通过率 SQL 写的是 `run_status IN ('passed','failed')`，
但 V4_1 之后状态枚举里**根本没有 `passed`**（`RunState` 只有 queued/preparing/running/finished/failed/canceled）。
实际效果：`finished` 的成功 run 全被漏掉，趋势页通过率**恒偏低**。
本版一并改为 `IN ('finished','failed')`，并在 `TrendService` 的测试里补一条断言。

> 这属于「验证在说谎」的同一类问题：SQL 合法、接口有响应、数字看起来正常，但口径是错的。
> 不改的话，总览和趋势页会对同一段时间给出两个通过率。

## 5. 接口契约

`GET /api/projects/{projectId}/overview?recent=8&days=30`

```jsonc
{
  "projectId": 1,
  "generatedAt": "2026-11-04T02:10:00Z",
  "windowDays": 30,
  "cases": {
    "total": 226,
    "byPriority": [{ "key": "P2", "count": 226 }],
    "byReviewStatus": [{ "key": "draft", "count": 226 }],
    "topDomains": [{ "key": "iperf", "count": 60 }]
  },
  "assets": { "devices": 3, "ports": 0, "links": 2, "credentials": 2, "environments": 0, "testSets": 0 },
  "runs": {
    "total": 0, "inWindow": 0, "running": 0,
    "finished": 0, "failed": 0, "canceled": 0,
    "casePass": 0, "caseFail": 0, "caseSkip": 0,
    "passRateBp": null,          // 基点（1/10000），null = 无样本
    "avgDurationMs": null,
    "lastRunAt": null
  },
  "recentRuns": [],
  "dailyTrend": [
    { "date": "2026-11-04", "finished": 0, "failed": 0, "canceled": 0 }
  ]
}
```

**为什么通过率用基点（`passRateBp`）**：避免浮点在不同语言/序列化下出现 `66.66666666666667`；
也避免用 `-1` 表示「无样本」这种约定被前端漏判。整数 + `null`，语义无歧义。

**参数边界**：`recent` 夹在 1~20，`days` 夹在 1~90。超界不报错，按边界值处理（总览不该因为参数让人看到 400）。

## 6. 权限与隔离

- 入口 `access.bindProject(projectId)`：校验项目属于当前用户，跨项目直接 403 且不泄露资源是否存在。
- 再 `require(CASE, READ)`：四个预置角色（管理员/项目经理/测试工程师/访客）都有该项，等价于「项目成员可读」。
- 每条 SQL 显式带 `project_id`，全部过 `TenantGuard.requireProjectScope`；
  端口 / 用例结果这类无 `project_id` 的表一律 join 主表取租户，不例外。
- 只读接口，不写审计（读操作不进审计，避免每个首页刷新刷一条）。

## 7. 空态设计（「有数据」之外的另一半）

真实库现在 `run = 0`。如果总览照常渲染 0 / 0% / 空表格，用户看到的是「坏了」而不是「还没开始」。

| 区域 | 有数据 | 无数据 |
|---|---|---|
| 用例卡片 | 226 + 优先级/评审状态分布 | 「还没有用例 → 去用例库导入台账」 |
| 资产卡片 | 3 设备 / 2 链路 / 2 凭据 | 分项显示 0，附「去资产台账录第一台设备」 |
| 执行卡片 | 通过率 + 近 30 天运行数 + 最近一次时间 | 「还没有执行记录」+ **不显示 0%**，显示「—」 |
| 近期执行 | 表格 8 行 | 一行引导：「在『执行』页发起一次运行」 |
| 趋势条 | 近 30 天柱状 | 说明文字「有执行记录后这里会出现趋势」 |

原则：**空态必须告诉用户下一步点哪里**，不能只写「暂无数据」。

## 8. 不做什么

| 不做 | 原因 |
|---|---|
| 图表库（ECharts/Chart.js） | 一条 30 根柱子的 CSS 柱状图足够；v0.5 已定「不引图表库」 |
| 实时刷新 / WebSocket 推送 | 总览是快照页，刷新按钮 + 进入页面拉一次即可 |
| 自定义卡片布局 / 拖拽 | 10 人规模的内部平台，没有这个需求 |
| 跨项目汇总 | 与 ADR-0006 冲突，且无业务场景 |
| 「我的待办」列表 | 需要任务/评审工作流数据，v1.0 HRD 再评估；本版用「待评审用例数」代替（已在评审状态分布里） |

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| `test_result` 明细缺失（执行域未回填） | 用例级通过率算不出来 | 回退到 `run.pass_count + fail_count`，并在响应里标 `passRateSource`；本版先按明细，回填在 v0.5 |
| 指标越加越多，总览变成报表 | 首页加载慢、信息噪音 | 本版锁定 4 个区域、8 个指标；新增指标须改本文 §4 |
| 空态被当成「功能没做」 | 误判进度 | 空态文案明确写「还没有执行记录」，并在证据里留截图 |
