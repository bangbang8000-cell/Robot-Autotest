## 二、逐项说明

### D1 · 门禁优先 G1→G2

- **为什么**：G1 的五项里有**全项目唯一从未验证过的前提**——「新机器按文档 30 分钟跑起空壳」。若这条不成立，后面所有门禁的结论都建在沙地上。G2 则集中了「461 导入对账 + 越权 36 条 + 明文凭据扫描」三项可脚本化的硬判据，人 20 分钟能看完。
- **怎么做**：① 先做 `ENV-01~05`（F0，AI 独担）；② 出 G1 核验纪要（重点补「干净环境跑起」与「CI 三绿或明确降级为 `make ci-local`」）；③ 再出 G2 纪要。
- **不做的事**：不按 WBS 编号顺序逐包审 48 个 `待验`——那会把 56 个包摊成 56 次上下文切换。

### D2 · 461 条先用合成数据

- **为什么**：真实 Excel 现在不在仓库（2026-11-03 实测），而导入链路（字段映射、整批事务、行级错误、重导幂等）可以先验。卡着不动，等于用一个数据缺失拖住整个 G2。
- **边界（写死，防滥用）**：
  - 合成数据必须 **461 行、同表头、含中英文别名列、含 ≥5 行故意错误**；
  - 合成跑通只能证明「链路可用」，**不能证明「真实 461 条的字段一个没丢」**；
  - **`CAS-03` 保持 `待验`，真实 Excel 对账通过前不得置 `已完成`**；
  - 合成数据文件必须标注 `SYNTHETIC`，避免半年后被当成真实台账。
- **落地**：`fixtures/ledger/`（`ENV-04`）。

### D3 · 数据库口径改 ADR

- **为什么**：ADR-0002 写 MariaDB，实际跑 MySQL 8.0。文档与事实不符比「用错引擎」更危险——后人会按文档准备 MariaDB 环境，然后发现迁移脚本在两边行为不同。
- **做法**：ADR-0002 加修订记录（引擎放宽为「MySQL 8.0 已验证 / MariaDB 待验」），**选型结论（真实库、独立库、不用 H2、不容器化）一个字不改**。
- **未关闭的风险**（已写进 ADR）：`uk_resource_lease_key` 并发语义、`DATETIME(3)`、`ON UPDATE CURRENT_TIMESTAMP` 两引擎实现细节不同；交付到 MariaDB 环境前须重跑全量迁移 + `mvn -Pit test`。

### D5 · 台账条数先不定

- **为什么**：计划书通篇写「461 条」，但在手的 `基本功能导入测试v0.2.6.0.1.xlsx` 实测只有 **226 条**（`TN-IMP-001~226`，去重后仍是 226），且字段与 461 的描述不一致——多了「A端命令 / B端命令 / 交换机配置 / 当前环境适配」，少了「优先级」。**在没弄清两套表关系前，任何数字都是猜的**，而把猜的数字写进验收判据，就是把错误永久化。
- **边界**：
  - 226 条**只当样本**，用于验证导入链路能读、能映射、能对账；
  - **不据此改 461 的口径**，也**不据此把 `CAS-03` 置 `已完成`**；
  - 若后续确认 226 即全集，再走一次口径变更（改 ADR-0005 与 v0.2 的 PRD/DEV-PLAN，留修订记录）。

### D6 · 解禁线定在 G5

- **为什么**：执行域过了（G4）只说明「能把脚本跑起来」，不等于「跑完能留下可读证据」。**没报告的用例执行等于没跑**——失败原因、复现步骤、产物链全无。G5 报告域通过后解禁，才能让每一次真实执行都产生可用证据。
- **代价（承认）**：真实链路的格式/适配问题推迟到 G5 之后才暴露。

### D7 · 开发期验什么

- **两条腿**：
  | 腿 | 内容 | 证明什么 |
  |---|---|---|
  | 合成 | `fixtures/bench/4suite-2cases/suite{1..4}.robot`（4×2，每条 6s）+ 后续合成用例 | 可重复回归，不依赖设备在线 |
  | 真实 L0 | 从 226 条中筛出的 **10 条只读用例** | 平台能吃真实台账的写法 |
- **L0 的 10 条**：`TN-IMP-002 / 016 / 017 / 021 / 025 / 027 / 029 / 046 / 048 / 049`。机检 + 人工逐条看过命令原文。
- **口径**：合成用例证明「稳定」，真实 L0 证明「适配」，两者不能互相替代。

### D8 · 做成强制门禁

- **落在三处**：
  1. `docs/adr/ADR-0013-执行安全分级与开发期禁跑令.md`（决策凭据与实测数据）；
  2. 规划附录 B · **G2** 加两项：台账分级齐全且机检可复现、**L2 在执行入口被拦截（须有被拒实测记录）**；
  3. 规划附录 B · **G4** 加一项：执行记录只含合成或 L0，**L1/L2 执行痕迹必须为 0**。
- **为什么不只写文档**：只写文档的规则，在赶进度时第一个被忘掉；写进检查单，才有人核。

### 顺带修掉的三个「验证在说谎」

F0 执行过程中发现的问题不在功能代码，而在**验证手段本身不可信**——比缺功能更危险，因为会让人据假数据下结论。

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **`mvn -Pit test` 空跑** | `Tests run: 0 / BUILD SUCCESS`，文档里「用 -Pit 跑集成测试」一直是空话 —— `SchemaIT` 不符合 surefire 默认 `*Test` 命名，从未被扫描过 | pom 加 `**/*IT.java` include；现 `SchemaIT` 真跑 **5/5** |
| **`ArtifactVerifier` 假绿** | 只判 `totalTests > 0`，8 条丢 2 条时 6>0 仍返回 `ok` → 部分丢失被放行 | 新增 `verify(path, expectedCaseCount)` + `checkShards(dir)`；`success` 现在要求 `exit==0 && 条数够 && 分片齐`；单测 5→**11 条** |
| **`check_import_header` 假红** | 正则跨不过 `//` 注释，夹注释的 `alias("caseCode", …, "测试编号")` **整条被丢弃**，别名统计错报 30/8（正确 36/9）→ 据此得出的「caseCode 认不出来」是假结论 | 改为**先剥注释再解析 + 调用点计数自检**；用「部分可解析」样例验证自检会拦（`2 处调用只认出 1 条`） |
