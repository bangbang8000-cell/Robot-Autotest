# 第一部分 规划本身

## 1. 规划定位：这份文件怎么用

### 1.1 三条定位

1. **唯一任务来源**。开发做哪一行代码、测试写哪一条用例，都必须指向本文的一个 WBS 编号（如 `EXE-02`）。没有编号的工作，默认不做；确需增加，走 §13 的变更流程。
2. **排期与治理的最高依据**。本文在**排期、门禁、验收、变更、度量**五件事上取代基线报告 §23/§24/§25 的对应内容；**技术与架构结论仍以基线报告为准**（本文不重复论证，只引用章节号）。
3. **可被审计**。任何时点问「现在该做什么、做完没有、凭什么算做完」，答案必须能在本文找到（§5 阶段、§6 WBS、§8 质量、附录 B 门禁检查单）。

### 1.2 五条硬规矩（违反即视为流程缺陷）

| # | 规矩 | 落地方式 | 检查点 |
|---|---|---|---|
| 1 | **任务必须挂编号** | Issue 标题 `[EXE-03] pabot 编排`；分支 `feat/exe-03-pabot-orchestration` | PR 模板必填字段 |
| 2 | **测试用例必须有 ID 且映射 KPI** | `TC-EXE-012`，用例头部注明对应 KPI（如「4 并发加速比 ≥2.5x」） | 每 G 门检查 |
| 3 | **门禁不过不进下一阶段** | 附录 B 检查单逐项签字，缺一项即 blocked | G0-G7 评审会 |

| 5 | **变更必须留痕** | 改本文即升版本号 + 写 ADR；口头变更无效 | CCB 记录 |

## 2. 目标体系

### 2.1 北极星指标

> **一条真实链路的完整证据链，从「选中用例」到「对外 PDF 报告」不超过 3 次点击、不超过 5 分钟。**

这句话同时约束四件事：编辑器要好用（少点击）、执行要快（并行）、报告要能直接对外（metadata 齐全）、权限要无感（不反复登录）。

## 8. 测试与质量策略

> 这一段是「测试也基于本规划」的落点：**测试不是开发的尾巴，而是门禁的证据来源**。每个 G 门的通过与否，由测试结果说话。

### 8.1 测试分层与归属

| 层 | 范围 | 工具 | 谁写 | 何时跑 | 门禁作用 |
|---|---|---|---|---|---|
| L1 单元 | 领域逻辑、状态机、解析器 | JUnit 5 + AssertJ | 开发 | 每次提交 | G1 起每门必查 |
| L2 集成 | Repository、事务、租约并发 | Spring Boot Test + Testcontainers(MariaDB) | 开发 | 每次 PR | G2 起 |
| L3 契约 | 编辑器往返保真、组件 props 契约 | Vitest + 19 个上游测试 | 前端 | 每次 PR | **G3 硬指标** |
| L4 端到端 | 登录→建用例→跑→看报告 | Playwright | 测试 | 每夜 + 发布前 | G5/G7 |
| L5 性能 | 4 并发、日志延迟、调度开销 | 自写压测脚本 + pabot | 后端 + 测试 | M3 末、M6 | **G4 硬指标** |
| L6 安全 | 越权、口令、注入、凭据泄漏 | 越权用例集 + 扫描 | 测试 | 每 PR（越权）+ 发布前（全量） | G2/G7 |
| L7 UAT | 8 条真实链路场景 | 人工 + 记录表 | 使用方 + 测试 | G7 前 | **G7 硬指标** |

### 8.2 覆盖率红线（不是越高越好，是「关键处必须覆盖」）

| 范围 | 红线 | 说明 |
|---|---|---|
| `domain/execution`（状态机、租约） | 行覆盖 ≥ 85%，分支 ≥ 80% | 并发核心，必须高 |
| `domain/report`（解析、门禁） | 行覆盖 ≥ 80% | 证据链核心 |
| 其余后端 | 行覆盖 ≥ 60% | 不追求数字 |
| 前端平台页 | 关键交互有 E2E 即可 | 不追单元覆盖 |
| `packages/editor` | 以 19 个上游测试为准 | 不额外追覆盖率 |

### 8.3 缺陷分级与响应（SLA）

| 级别 | 定义 | 响应 | 修复 | 谁能定级 |
|---|---|---|---|---|
| **P0 阻塞** | 数据错、报告错、越权、跑不起来 | 30 分钟 | 4 小时（含回滚） | 任何人可提，大师确认 |
| **P1 严重** | 主流程可用但结果不可信，或性能不达标 | 2 小时 | 1 个工作日 | 测试负责人 |
| **P2 一般** | 功能缺陷但有替代路径 | 1 个工作日 | 当前迭代内 | 开发自评 |

### 8.4 准入 / 准出（DoR / DoD，完整版见附录 A）

## 9. 分支、构建与发布

### 9.1 分支模型

| 分支 | 用途 | 生命期 | 保护 |
|---|---|---|---|
| `main` | 唯一集成分支，永远可构建 | 永久 | 受保护：PR + 1 审批 + squash + 线性历史 |
| `feat/<wbs>-<简述>` | 功能 | 合并即删 | 无 |
| `fix/<wbs>-<简述>` | 缺陷 | 合并即删 | 无 |
| `docs/<简述>` | 文档 | 合并即删 | 无 |
| `release/x.y` | 发布固化（运营期启用） | 长期 | 仅 cherry-pick |

**命名必须带 WBS**：`feat/exe-03-pabot-orchestration`。不带编号的分支不予评审（§1.2 规矩 1）。

### 9.2 提交与 PR

| 项 | 规则 |
|---|---|
| 提交信息 | Conventional Commits：`type(scope): 描述`，scope 用 WP 小写（`exec`、`editor`、`report`） |
| PR 大小 | 单 PR ≤400 行改动；超了拆（文档与生成代码除外） |
| PR 必填 | WBS 编号、验收标准、测试证据（截图/日志/命令输出） |
| 评审 | 至少 1 人；涉及执行/报告核心逻辑建议 2 人 |
| 合并 | 只允许 squash；合并后源分支自动删 |

### 9.3 版本与发布

| 阶段 | 版本号 | 发布节奏 | 发布窗口 |
|---|---|---|---|
| 建设期 | `v0.x.y` | 每周一次内部快照（不对外） | 周四 16:00 |
| 上线 | `v1.0.0` | 一次性 | G7 通过后首个周四 |
| 运营期 | `v1.x.y` | 每两周一次；紧急修复随时 | 周四 16:00（紧急除外） |

**发布检查单（每次发布必过）**：① 全量回归绿；② P0/P1 清零；③ 数据库迁移可回滚；④ 备份已完成；⑤ 回滚命令已就绪；⑥ 变更说明已写。

**回滚**：镜像/包回退 + 数据库 down 迁移 + 产物目录不受影响。演练 RTO ≤30 分钟（HRD-04 作证）。

### 13.1 变更分级

| 级别 | 定义 | 审批 | 时限 | 记录 |
|---|---|---|---|---|

### 13.2 CCB（变更控制委员会）

- **组成**：大师（主持）、silence、学徒。必要时邀使用方。
- **触发**：任一 L3 变更、任一 G 门未通过且需带条件通过、任一 P0 缺陷导致返工。
- **输出**：决议（批准/驳回/降级）、影响评估（人日、里程碑）、ADR 编号。
- **原则**：**宁可降范围，不降质量红线**。若必须砍，先砍 §3.2 之外的边缘功能，绝不砍 metadata 门禁、租约互斥、往返保真。

### 13.3 已知降级预案（提前写好，避免临时慌乱）

| 触发条件 | 降级动作 | 影响 | 谁批 |

| W20 时 4 并发加速比 <2.0x | 并发上限降为 2，`MAX_PARALLEL=2`，UI 限制同时提交 | 需求 N7 从 4 降为 2 | CCB |
| W13 时 19 个上游测试未全绿 | 编辑器先只上「文本视图 + 只读查看器」，表单与流程视图延后 | 体验下降，功能不缺 | CCB |
| W24 时导出仍缺项 | PDF 先出，Word 延后到运营期 Q1 | 对外交付形式受限 | CCB |
| P3 runner 未定 | CI 只做 lint + 单测，E2E 与压测人工在 149 跑 | 自动化程度下降 | 大师 |
